# Module interfaces: summary

A summary of the inputs, outputs and gates of the top level and the modules. The main flow is ① Data → ② Train & tune → ③ Compare → ④ Deliver → ⑤ Judge & decide → top-level check → stop & deliver; ③ Compare (module name `compare`) is a code module, a fixed command the engine runs with no agent, on only when the task definition has a `compare` section (task.md) and a report only, never a gate; training and tuning were merged into one module (the train module, module name `train`, skill `rsi-train`), and an old workspace's `tune` dispatches and artifacts are read as usual but no longer dispatched. The main flow is decided by code (`rsi/flow.py`, see engine.md), and the inputs each module gets are given by the brief the code builds (`rsi/briefs.py`); the authority is the "Inputs", "Outputs" and "Gates" sections of each module's `SKILL.md`; the artifact fields are in README.md, datasets.md, models.md, delivery.md, evaluation.md and record.md, and this document does not repeat the field tables. Each module skill also has a "Running standalone" section saying how its owner runs the module in their own sandbox on copies of registered artifacts. Each module's skill, code, references and tests are in its own folder `modules/<module>/`, and the engine gives the full text of `modules/<module>/SKILL.md` to the module agent when it dispatches it; the module template is `modules/_template/SKILL.md`.

## Inputs, outputs, gates

Every module but `compare` is an agent the engine dispatches (`rsi run`, one session each time; `compare` runs the same dispatch protocol as a fixed command): it reads only the artifact paths the brief lists, writes its artifacts into the output directory the brief gives (manifest `id` null, `round` as the brief says), validates them with `rsi validate` before handing back, computes the metrics, baselines and deltas of its report with `rsi score` (the definitions are fixed in code, see "Metric definitions" in task.md), runs no other `rsi` command and does not read the workspace. The engine does the registration. For every improvement experiment, each module also hands in a `record`. A module may also write `progress.json` in its output directory at any time (optional, the brief's `progress_file`), which the progress pages and the status line of `rsi run` show as it is; format in progress.md.

| Part | Inputs (artifact kinds) | Outputs (artifact kinds) | Gates |
|---|---|---|---|
| Top level | The user's request; the artifacts the modules hand back | `task`; version registry; the run report and the delivery at the stop | Validation, spot checks, registration, promotion decisions, closing rounds, approvals, the stop and the run report, all done by `rsi` commands |
| `rsi-data` | `task`; the raw data of round 1's sets dispatch (the brief's `sources`, read only by this dispatch) and, when it is continued, the registered `corpus` and `pool`; optional `trainset`, `plan`, `feedback`; in later rounds also `valset`, `pool`, the current best version's candidate (`best_candidate`, when there is one: dgen scores the pool with it), the brief's `dgen`, `features` and `resources` (`gpu_ids`: dgen's pool scoring runs on an idle card of them), and this module's `record`s of earlier rounds; for an approved evalset refresh, `corpus` and the `inputs.jsonl` of earlier `evalset`s | `trainset`; in round 1 also `task` (only when it filled in the split rule), `corpus`, `pool`, and in round 1 or an approved refresh also `testset`, `evalset`, `valset` (with an `inputs.jsonl` without labels); `record`; the engine registers them in the order `task`, `corpus`, `testset`, `evalset`, `valset`, `pool`, `trainset` | The data quality checks of the task definition's `quality_checks` (a failed `trainset` is registered only as evidence and never becomes the current trainset); no repeats between sets; `evalset` and `testset` moved into the workspace at registration, with no copies kept |
| `rsi-train` (train module) | `task`, `trainset`, `valset`; the registered `candidate`s and `search`es (by id), the current best version's candidate (`best_candidate`), the `plan` that opened this round; the task's `search_space`, `search`, `resources.onejev`, `resources.gpu_ids`; this module's `record`s of earlier rounds (an old workspace's tune records included); the budget left | One dispatch is one search, handed back in two parts: first the `candidate`s of all successful trials of this search (with `config_request`) and a `record`; once they are registered, the same session gets `# Continue: the second part of the hand-back` and hands back the `search` | Train gate: the primary metric on the valset strictly better than the baselines the task definition lists (a failed `candidate` cannot be sent to evaluation, and registration refuses its `delivery`); metrics and baselines computed with `rsi score` and recomputed at registration; the candidate carries a directly runnable prediction entry `model.predict`, the training code's version `code_version` (`entry` being the task's train command) and the fully resolved `config`, with `config_request` inside the task's `search_space`. Tune gate: the best config not worse than the default config on the valset, else the default config's result is handed back (`rsi validate` checks that the best is not worse than the default and that the gain equals their difference); a trial's `metric_val` is taken from its candidate's primary metric (checked at registration); all trial candidates come from the same version of the training code (the same `code_version.sha256`, checked at registration) |
| `rsi-compare` (③, code, on with the task's `compare` section) | `task`, the round's chosen `candidate`, the current `trainset` and the `valset` (with labels), the `inputs.jsonl` of the `evalset`, every registered `baseline` (by id) but those with testset predictions; the task's `compare` settings, `policy`, `features`, `resources.onejev`, `resources.gpu_ids` and the train command. At the milestone (`milestone_compare`): the best version's `candidate` and `comparison`, each `baseline` of it, the rows of the `trainset` and `valset` they name, and the `inputs.jsonl` of the `testset` | Handed back in two parts in one session: first the `baseline`s it trained (a registered one whose spec and sets match is reused), then, once they are registered, the `comparison` of the candidate with them on the valset; at the milestone, a `baseline` with `predictions_test` for each baseline of the best version's comparison, all in one hand-back (GPU baselines run as one long job first) | Report only, no gate: a failure or refusal is `skip`ped at the return limit and the flow goes on to ④; every number recomputed at registration with `rsi.metrics`; a `baseline` with `predictions_test` needs a `use_testset` approval (the engine writes it, quoting the user's milestone answer) |
| `rsi-deliver` | `task`, `candidate`, the `inputs.jsonl` of the `evalset`, the `inputs.jsonl` of the candidate's `valset`, this module's `record`s of earlier rounds; with approval also the `inputs.jsonl` of the `testset` | `delivery`, optional `feedback`, `record` | The model package loads; the delivery package's predictions on the valset inputs reproduce the candidate's `predictions_val` (checked row by row at registration); the delivery package is in the delivery directory or is an `external` entry with sha256; no labels touched |
| `rsi-judge` | `task`, `candidate`, `delivery`, the `search` when there is one, `evalset` (with labels), the `trainset` of the candidate sent to evaluation (only for the baselines), the current best version's `evaluation` and `delivery`, `feedback`, all `record`s, and for the evaluation also the `plan` that opened this round (to judge whether it worked); with approval also `testset`. When this round was closed by `rsi close-round` there is no `delivery`, and it gets all of this round's `candidate`s (including those that failed the train gate), `search`es and `record`s | `evaluation`, `plan`, `record`; when the round was closed, only `plan` and `record`, with the `plan`'s `evaluation_id` null and the issues and evidence taken from the train gate results and experiment records of this round's candidates | Metrics, baselines, deltas and intervals computed with `rsi score` and recomputed at registration; the recommendation agrees with the promotion rule; attributions take only the values allowed; every issue of the plan has evidence and exactly one attribution |

A `candidate`'s `config_source` is "default" or the id of a registered `candidate` or `search` (an old workspace also has "tune", see models.md).

**Train & tune in a round.** This round's ② is done = this round has registered a `search` and at least one candidate passed the train gate; attempts count only `search`es (`stop.max_attempts_per_round`). When no trial of a search passes the train gate, the options of the decision point `train_gate_failed` are `train` (back to the same train session to search once more, one return), `data` (dispatch rsi-data for a new trainset) and `ask`; once the attempts are used up the round is closed. When training runs in the background, the module hands back `long_job`; when the task's `flow.checkin_minutes` turns check-ins on, the engine has the same session check the environment on schedule (the feedback starts with "# Check-in", not a return, see `flow` in task.md).

|---|---|---|---|---|---|
| `trainset` | produces it | reads it (with labels) | reads the current one (with labels); at the milestone the rows of those its baselines name | does not read | reads that of the candidate sent to evaluation (only for the baselines) |
| `valset` | produces it in round 1, reads it later (dgen's `leak_val` check reads only its `inputs.jsonl`) | reads it (with labels) | reads it (with labels) | reads only `inputs.jsonl` | does not read |

| `testset` | produces it in round 1, keeps nothing once handed over; a trainset dispatch (dgen included) gets nothing of it, not even its inputs | does not read | at the milestone (`milestone_compare`, the user's yes), reads only `inputs.jsonl` | with approval, reads only `inputs.jsonl` | with approval, reads it (with labels) |

## Train command

`rsi-train` provides a train command that needs no agent. Location: the task definition's `resources.train_command` (optional, an absolute path or a path relative to the repository root) when given, otherwise `<repo root>/modules/train/train` (`<repo root>` comes from the brief, whose "Train command" line gives the actual path). The caller runs it with `PYTHONPATH=<repo root>` in the environment, by which it runs `python3 -m rsi score`. It is implemented by the owner of `rsi-train` and trains one config with the same code as trsi: the `code_version.entry` of every candidate of `rsi-train` names it, and the owner calls it for a single training by hand. `rsi-data` does not train and does not call it: whether a new trainset is better is judged by this round's `rsi-train` training on it and by `rsi-judge` comparing with the current best version on the evalset. The contract is written in the section "Train command (interface contract)" of `modules/train/SKILL.md`:

- Input: the task definition, the trainset directory, the valset directory, a config file, plus the artifact ids, `config_source`, the round, `--producer` (only `train` is accepted; an old workspace's candidates may also have `data`, which can still be read, but registration refuses new ones), the candidate directory and the `--marker` argument.
- Output: the candidate directory is itself a `candidate` artifact directory (`id` null) that passes `rsi validate candidate`; with an executable prediction entry `model.predict` (called as models.md says), `code_version` (the train command's path and sha256), the fully resolved `config` and the `config_request` asked for.
- Completion marker: the file given by `--marker`, outside the candidate directory, first line ok or failed; exit code 0 if and only if ok.
- It can run unattended in the background; it reads only the trainset and the valset.
- Progress: written into `progress.json` in the directory of `--out` (see progress.md).

The config file's format is set by the owner of `rsi-train`.
