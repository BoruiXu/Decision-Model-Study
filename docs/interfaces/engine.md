# Flow engine interface

`rsi run <ws>` runs the flow engine: the main flow is code (`next_action` in `rsi/flow.py`), and agents implement the modules. This document describes the interface between the engine, the module agents and the operator: action types, the engine's records in STATE, decision points and default choices, runners, returns to the same session, page refresh and status lines while waiting, exit codes and locks. The format of the artifacts themselves is in README.md and the artifact documents; the settings of the task definition that concern the engine (`flow`, `decisions`, `runner`) are in task.md.

## The loop

`rsi run` does three things over and over: `next_action(ws)` works out the next action (a pure function that only reads the workspace); the action and its result are logged in `<ws>/work/run.jsonl` and the action is carried out; the progress pages are rewritten, and when the state changed a status line goes to stderr (see "While waiting"). It stops when it must ask the user, wait for a long job, wait for a manual hand-back, the run ends or `--max-steps` (default 200) is used up, and prints why it stopped. All state is in the workspace, so after the process is killed or the machine restarts, running `rsi run` again picks up where it left off: agents already launched are found again (the runner reattaches by the recorded process id), nothing is dispatched twice and nothing is registered twice. "What the run waits for" on the progress page comes straight from the same `next_action`, so it cannot disagree with the engine.

## Action types

`next_action` returns a dictionary whose `type` is one of the following; each action also carries `step` (its place in the main flow, for the pages and the log).

| `type` | Fields | What the engine does |
|---|---|---|
| `dispatch` | `module`, `purpose`, `reason`; for compare and deliver also `candidate_id` | Writes the dispatch record, builds the brief, launches the agent |
| `resume` | `dispatch_id`, `feedback`, `mode` | Sends this dispatch back to its session. `mode`: `resume` (a return, counted in `flow.max_returns`); `followup` (the second part of a two-part hand-back: train's search, compare's comparison, judge's plan; a normal continuation, not a return); `answer` (sends back the user's answer to its questions; the artifacts of that hand-back are not registered yet; not a return); `checkin` (the long job's completion marker has not appeared and a check-in is due: the session checks the environment once and hands back again; not a return, see below) |
| `wait_agent` | `dispatch_ids` | Polls the running agents (and `pending` records not launched yet: launches them first) until one ends (manual runner: stops at once) |
| `wait_long_job` | `dispatch_id`, `marker`, `checkin_at` | The long job's completion marker has not appeared. Without check-ins (`checkin_at` is null): stops with status `waiting_long_job`; with check-ins on (the task's `flow.checkin_minutes`): does not exit, but waits in the process until the completion marker appears, `checkin_at` (the time of the next check-in, UTC, rounded up to the second) comes or the run is stopped, then takes the next step |
| `process_handback` | `dispatch_id` | A hand-back with questions asks the user first and registers nothing; a hand-back whose candidates would take the compute used over the budget while this round has no `over_budget` approval also registers nothing and asks `over_budget` first; otherwise validates and registers the hand-back's artifacts and handles refusals and failures |
| `decide` | `point`, `options`, `default`, `dispatch_id`, `reason` | Chooses at a decision point and carries the choice out (see below); `options` are the decision point's, with `skip` before `ask` for a compare dispatch (`rsi.flow.decision_options`) |
| `ask` | `kind` (`approval` or `question`), `what`, `ref`, `question`, `options` | Writes STATE's `waiting` and stops with status `waiting_user` |
| `promote` | `evaluation_id` | The promotion decision (the logic of `rsi promote`) |
| `close_round` | `reason` | Closes this round (the attempts are used up and still no candidate passed the train gate) |
| `next` | `reason` | Checks the stop conditions, opens the next round or stops (the logic of `rsi next`) |
| `report` | — | Writes `<ws>/REPORT.md` |
| `done` | — | Stopped and the report written: status `done` |

Order (the first that holds): stopped → report or done; STATE has a waiting question → ask it again; a hand-back whose questions the user has answered → send it back to its session with the answer (`resume`, `mode` `answer`); a hand-back to process, a failed dispatch (a decision point), a running or pending agent, a long job → the matching action; the round not decided yet → `promote` of the evaluation, `close_round` once the attempts are used up, the first unfinished step of the main flow (① Data, ② Train & tune, ③ Compare, ④ Deliver, ⑤ Judge & decide; an evalset at its use limit and going over the budget ask the user first); the round decided → at a stop the milestone release and `next`, otherwise judge writes the plan, the plan approval, `next`.

**③ Compare** is on only when the task definition has a `compare` section (task.md); without one (an old workspace, or a task that wants none) the flow goes from ② to ④ as before and the pages draw `③ Compare (off)`. It is a report, never a gate: nothing waits on its numbers. It is due in an undecided round whose entry is data or train once ② is done; the evalset's use limit is checked first, as before ④, and the budget (`over_budget`, see spend.md) before a new compare dispatch. It is done when the round holds a `comparison` of the chosen candidate (the one ④ delivers) on the current evalset, or when a decision of the round chose `skip` on its compare dispatch. Its hand-back comes in two parts in one session, like train's search: first the `baseline`s it trained (when every baseline is reused, the comparison at once), then, after they are registered, a `followup` (feedback "Baselines registered as <ids>: write the comparison and hand it back.") for the `comparison`; asked again, it is a return. A hand-back that brings no comparison is `handback_failed` ("rsi-compare handed back without a comparison"). At the milestone, when the user said yes, the task has `compare` and the best version's candidate has a comparison that lists at least one baseline (`rsi.flow.milestone_comparison`; one whose baselines were all skipped has nothing to score, and the milestone question then counts no compare step), a compare dispatch with purpose `milestone_compare` runs between the milestone delivery and the milestone judge: it scores the baselines of that comparison on the testset's inputs (a new `baseline` with `predictions_test` for each, all in one hand-back, each registration with its own `use_testset` approval quoting the user's milestone answer, as the milestone delivery's; its GPU predictions are not held by the compute budget, which the milestone question says); it is done once a baseline with `predictions_test` is registered in the round or a decision chose `skip`, and the milestone judge then lists what was registered.

## The engine's records in STATE

STATE.json gains three items, which the pages, `rsi status` and the engine read; every write to them happens in a transaction under `STATE.lock`.

**`dispatches`**: dispatch records, in order of id (`d-0001`…).

| Field | Meaning |
|---|---|
| `id`, `round`, `module`, `purpose` | Number, round, module (`data`, `train`, `compare`, `deliver`, `judge`; an old workspace also has `tune`, read as usual but no longer dispatched: before upgrading the framework, let any open tune dispatch finish, or `rsi stop`, since carrying it on (return, resume, check-in, new session) rebuilds its brief and fails with `unknown module 'tune'`), purpose (`sets`, `trainset`, `refresh`, `train`, `compare`, `deliver`, `judge`, `plan`, `milestone_deliver`, `milestone_compare`, `milestone_judge`; an old workspace's tune dispatch has `tune`) |
| `outdir` | The output directory, relative to the workspace: `work/round-<n>/<module>[-k]/` (with a suffix when the same module is dispatched again in the same round); it holds `brief.md`, `brief.json` (whose top-level field `dispatch_id` is this dispatch's id), `prompt-<n>.md`, `agent-<n>.log`, `agent-<n>.exit` (the `code` runner: the command's exit status), `feedback-<n>.md`, `registered-<n>.json` (the second part of a two-part hand-back: what the first part registered, see "Returns to the same session"), `history-<n>.md`, `handback.json` (the current one) and `handback-<n>.json` (written by launch n, renamed and kept before the next launch) |
| `denied` | The read-deny list worked out from the brief of the latest launch (absolute paths, directories or single files); recomputed at every launch (including returns, resumes and new sessions, after the brief is rebuilt) and also written into the `launch` event of run.jsonl; never written into the brief. Only the `claude` runner enforces it; `mock`, `manual` and `code` only record it |
| `runner`, `session`, `pid` | Runner name (`code` for a code module's dispatch, see "Runners"), session id (for `claude` a uuid the engine makes and records first, `--session-id`; for `code` a made-up `code-<hex>`), process id |
| `status` | `pending` (record written, agent not launched yet), `running`, `handed_back` (handed back, not registered yet; a hand-back with questions stays so until the user answers; one held over the budget stays so until it is registered after the approval or the run stops), `long_job`, `failed`, `done` |
| `launches`, `launch_mode` | Number of launches (including returns, resumes, continuations, answers, check-ins and new sessions; a launch closed before it started does not count); how the latest launch went: `first`, `resume`, `continue`, `followup`, `answer`, `checkin`, `fresh` |
| `returns`, `continued`, `followups`, `answered`, `checkins`, `capped` | Times sent back to the session (only these count in `flow.max_returns`); times resumed to wrap up a long job; times of the second part of a two-part hand-back (continuation); times the user's answer was sent back to the session; long-job check-ins (capped by `flow.max_checkins`); `max_continues` when `flow.max_continues` made it fail |
| `started_at`, `launched_at`, `ended_at`, `exit_code` | Times and the agent's exit code; `launched_at` and `status: running` are written together before the runner is called, and a `pending` record has no `launched_at` |
| `marker`, `errors`, `feedback`, `candidate_id` | The long job's completion marker, the error texts of refused registrations and the like, the feedback file of the latest launch, the candidate to compare or deliver for a compare or deliver dispatch |
| `long_job_since`, `long_job_launch` | `launched_at` and the launch number (its stamp `.launch-<n>`, see "The completion marker appears") of the launch that started the long job: recorded when it first hands back `long_job` with this completion marker; a later `long_job` hand-back with the same marker (a check-in) leaves them, and one with a new marker (or with the same marker already seen ended, recorded in `marker_seen`: that is a new long job) switches them to that launch's; a stop uses them to confirm the long job's process (see "Stopping mid-run") |
| `marker_seen` | The marker (written as `marker` is) recorded when a long job's hand-back was processed and its completion marker read (first line `ok` or anything else): this long job has ended, so even if the marker file is later deleted it no longer counts as a running long job, and a stop or a closed dispatch does not look for it. Cleared by the next `long_job` hand-back (even with the same marker path): that is a new long job |
| `registered`, `refused` | The registered artifacts (`dir`, `kind`, `id`, `launch`) and the refused ones (`dir`, `kind`, `error`, `launch`); `launch` is the launch that handed it back |
| `asked` | For a hand-back with questions: `launch` (that launch), `question_id` (the id of STATE `waiting`), `questions`; none of the artifacts of this hand-back is registered before the user's answer |
| `held_budget` | For a hand-back held over the budget: `launch` (that launch), `question_id` (the id of STATE `waiting`), `dirs` (the candidates that would go over the budget, subdirectory names in the hand-back), `cost` (the compute hours registering them would add; sources whose identical cost was already counted when refused are not added again), `used` (the compute used at the time), `budget` (`budget.compute_hours`). After the approval they are registered as usual and this item stays as a record: the hand-back is still held while its `launch` is the dispatch's current `launches`, the dispatch is still `handed_back` (or `long_job` for a long job), this round has no `over_budget` approval yet and the run has not stopped (`rsi.flow.budget_held`) |
| `long_job_stop` | The long job had not ended when the run stopped or the dispatch was closed: the `pid` of the completion marker's pid file, `pid_file`, `result` (`terminated`; `gone`: the process no longer exists; `unconfirmed`, `no_pid_file`, `bad_pid_file`, `error` (an error while terminating): not terminated, it may still run; `pending`: the dispatch has been closed but the job not terminated yet, and then there are only `result`, `context`, `at`), `why`; `others`: pid files in the output directory whose marker does not exist (new long jobs not handed back yet), each also with `pid`, `pid_file`, `result`, `why` (`[]` when none); `at`; `context`: `stop` (the run stopped, or the user chose `stop`) or `close` (`new_session`, `close_round` or `rsi close-round` closed the dispatch); old records have no `others` or `context` and are read as `stop` (see "Stopping mid-run") |
| `spend_lines`, `spent_launches`, `spent_sessions` | The spend ledger (spend.md): how many lines of the dispatch's `spend.jsonl` have been read and counted (absent: none; counted when its hand-back is processed, when it fails, and when a stop or a close closes it, after its long job is terminated); the launches whose agent cost is counted in `budget_used.agent_usd`, each once; and for each session id the cumulative cost counted so far (the `claude` runner's `total_cost_usd` is the session's total, a resumed launch's included: a launch adds the increase over it) |
| `closed` | Why a dispatch that is not carried on was closed (the user chose `new_session`, `close_round` or `stop`, or the run was stopped in the middle of this step; a compare dispatch closed by `skip` has `skipped: ③ Compare is report only`); a closed dispatch has status `done`, and `capped` is cleared |

**`decisions`**: decision records. Fields: `point` (decision point, or `plan`, `milestone`, `handback`, an approval item name), `options`, `choice`, `by` (`code`, `agent` or the answering user's name), `reason`, `quote` (the user's own words, when the user answered), `round`, `at`, `dispatch_id` (for an answer to a question held over the budget, the held dispatch), `key` (the key that identifies the same decision: round, decision point, dispatch, number of launches, number of dispatches, number of artifacts this round; a rerun after an interruption and the user's answer reuse the same decision through it).

**`waiting`**: the question the engine waits on, `null` when none. Fields: `id` (`q-NNNN`, one per new question, counted by STATE's `waiting_seq`; unchanged when the same question is asked again), `kind` (`approval` or `question`), `what` (decision point or approval item), `ref` (dispatch id or plan id), `dispatch_id` (optional: for an `over_budget` asked while a hand-back is held over the budget, the held dispatch; then `ref` is still `null`, so `rsi approve <ws> over_budget` answers it without `--ref`), `question`, `options`, `since`. `rsi answer` and `rsi approve` clear it once they answer it. Once a question is moot the flow no longer waits on it and the engine clears it: the approval has been recorded; for an approval question with a `dispatch_id`, its dispatch is closed or unknown; for a decision-point question, the flow worked out again without `waiting` no longer gives a `decide` at the same decision point for the same dispatch (the dispatch was carried on or replaced, the step is done, the round is decided, e.g. after a manual `rsi close-round`), or the dispatch it names is closed, unknown or of another round; for a milestone question, there is already an answer (including a `use_testset` approval recorded after the decision in a manual flow); for a check-in question, its dispatch is closed, is no longer a long job, its completion marker has appeared, or the user has answered already. When the return limit is reached and the dispatch is `done` but the step is not done (e.g. train handed back trial candidates without writing a search yet), the question is not moot and the answer is carried out as usual.

## Decision points and default choices

The code makes a choice at these places, each with a default the code computes; the task definition's `decisions.<decision point>: "agent"` can make a decision agent judge instead (it must choose one of the options the limits allow and give a reason; an invalid answer falls back to the code's default). `ask` is always among the options; when the limits allow only `ask`, no agent is called. The limit is `flow.max_returns` (default 2) per module per round.

| Decision point | Options | The code's default | When it becomes a question for the user |
|---|---|---|---|
| `train_gate_failed` (this round's search is registered, no candidate passed the train gate, attempts are left) | `train`, `data`, `ask` | `train`: back to this round's train session to search the config space once more (the next attempt) | train has reached the return limit; or the latest launch of this train dispatch registered only experiment records (`record`, no new trial candidates or search, e.g. trsi has already said STOP: another return would only do the same) |
| `quality_gate_failed` (this round's new trainset failed the quality gate) | `resume_data`, `ask` | `resume_data`: back to data's session | No dispatch record to return to (a workspace run by hand); data has reached the limit |
| `handback_refused` (registration refused an artifact a module handed back) | `resume`, `ask` (a compare dispatch: `resume`, `skip`, `ask`) | `resume`: back to the same session with the registration's error text; for a compare dispatch at the limit, `skip` | The module has reached the limit; never for compare, which is skipped then |
| `handback_failed` (the step is still not done after the hand-back) | `resume`, `ask` (a compare dispatch: `resume`, `skip`, `ask`) | `resume`; for a compare dispatch at the limit or `capped`, `skip` | The module has reached the limit, or `flow.max_continues` made this dispatch fail (`capped`); never for compare, which is skipped then |

Notes on how the code actually behaves:

- **The default after a failed train gate has no "choose `data` when quality-related" rule.** The design said "dispatch data when the candidate report has a quality-related failure flag", but a candidate's manifest has no such structured flag for the code to compute, so the default is `train`; `data` is still an option, open to a decision agent or the user.
- **The decision after a failed train gate is recorded on this round's latest train dispatch** (so a `new_session` from it opens a new rsi-train session); when this round has no train dispatch (the candidates were registered by hand), on the dispatch of the last candidate, or null when there is none.
- **The question to the user after a failed train gate has no `resume` option.** Choosing `train` or `data` already goes back to that module's session of this round (or a new dispatch with `feedback-1.md` when there is none), so a `resume` would duplicate one of them. The questions of the other decision points have `resume`.
- **A failed or refused compare is never a block.** ③ Compare is report only and never stops the run to ask: at the return limit, and when `flow.max_continues` made it fail (`capped`), the code's default is `skip`, which closes the compare dispatch (status `done`, `closed` `skipped: ③ Compare is report only`) and lets the flow go on to ④ without a comparison (or, at the milestone, to the milestone judge without the testset baselines); the user can also choose `skip` when asked. `rsi.flow.compare_skipped` reads the recorded decision.
- **When no trial of a search passes the train gate, the search is registered before the decision.** One dispatch of the train module is one search: once it hands back its trial candidates, the flow first has the same session write the search (the second part), and only when the search is registered (one attempt) does `train_gate_failed` come; once the attempts are used up the round is closed (`close_round`), so returns never go on without end.

Carrying out a choice: STATE is read again first, and when the run has been stopped nothing is launched (see "Stopping mid-run"). `resume` and `resume_data` send the dispatch back to its session (one more return); `skip` closes a compare dispatch as skipped (`rsi.decisions.skip_compare`; a long job of it that may still run is ended as for `new_session`), and the user's `skip` answer does so at once in the transaction of `rsi answer`; `train` and `data` go back to that module; `new_session` closes the dispatch in trouble and opens a new dispatch of the same module (and, for deliver, the same candidate), whose purpose is the current part of the step: once the round is decided a judge dispatch becomes one that writes the plan (`plan`), once round 1's other three sets are registered a data dispatch becomes one for the trainset (`trainset`), otherwise the old dispatch's purpose is kept (train writing a search is still `train`, with the registered trial candidates in the brief); the feedback gives the reason, the old dispatch's errors and the failed gates; `close_round` and `stop` have the effect of `rsi close-round` and `rsi stop`; when `stop`, `new_session` or `close_round` closes a failed dispatch (`rsi.decisions.close_dispatch`) whose long job has not written its completion marker yet (e.g. a check-in failed), the save that closes the dispatch (the whole transaction of `rsi answer`; for `stop` and `close_round`, the same save that stops the run or closes the round) only records `long_job_stop: {"result": "pending", "context", "at"}`, and after the save succeeds the long job is terminated as in step 4 of "Stopping mid-run" and `long_job_stop` is saved again (`rsi.decisions.terminate_after_commit`; `context`: `stop` for `stop`, `close` for `new_session` and `close_round`); when the save fails (e.g. closing the round is refused) nothing changes and the long job is left alone. If it is interrupted after the save and before the termination, the record stays `pending`: at the start of every `rsi run` step (where the registry is repaired), at the next close of a dispatch (`terminate_after_commit` also handles every `pending` one) or at the report step after a stop (`settle_after_stop`) it is terminated, whatever the dispatch's status; the process is confirmed by its start time, so terminating again hurts nothing. An error while terminating is recorded as `error` (not terminated), and the other dispatches are handled as usual. Like `rsi close-round`, `close_round` also first closes this round's other dispatches that failed and whose long jobs may still run. The reason printed when the run ends lists these long jobs as well; `REPORT.md` lists those of `close` as "When its dispatch was closed, long job …" and those of `stop` as "At the stop, long job …" (the event log of the progress pages likewise says "when its dispatch was closed" or "at the stop"); `ask` writes STATE's `waiting` and stops. The options of a question to the user are these ways out (`resume`, `skip` (a compare dispatch), `new_session`, `close_round` (while this round can still be closed), `stop`, plus `train` and `data` after a failed train gate), and the question's text says what each option means.

Approval questions (`plan`: `approve`, `revise`; `refresh_sets`: `approve`, `close_round`, `stop`, where after an approval rsi-data is dispatched to refresh the evalset before delivery and evaluation; `over_budget`: `approve`, `stop`, asked before ① a trainset, ② and a new ③ dispatch when the use of a resource with a budget has reached it (the question names each one, see spend.md), where after an approval this round goes on to its decision, and after the decision the stop check stops the run because the budget is reached) and the milestone (`yes`, `no`) are `ask` too; the texts of questions and options say only what really happens after a choice: when `close_round` would make a stop condition hold (`Workspace.stop_check_if_closed`), its option says that the run stops after the round is closed and why, not that judge writes a plan; questions a module asks in its hand-back (`questions` in `handback.json`) have the option `answered`: a hand-back with questions asks the user first, and **none of the artifacts of this hand-back is registered** (the dispatch stays `handed_back`, and the record's `asked` says which launch asked). After the user answers, the next `rsi run` sends the answer back to **the same session** (`resume`, `mode` `answer`, `answered` plus 1, not a return; the feedback file says that the artifacts of that hand-back are not registered yet, and gives the user's questions and own words); the module changes or confirms things by the answer and hands back again, and only that hand-back is registered (refusals and the like handled as usual). A hand-back with questions only and no artifacts works the same way: the answer goes back and the module carries on. The questions in a long job's (`long_job`) hand-back are asked only once the completion marker is there; when it lists no artifacts, the answer goes into the long job's wrap-up feedback ("# Long job finished", `continue`), and when it lists artifacts it goes back as `answer` too. The user's words are delivered only once: into the feedback of this dispatch's next launch; only when this dispatch is closed before the answer goes back are they written into the brief of any later dispatch of the same module with the same purpose (`purpose`), in any round (the section "The user's answers to this module's earlier questions" of `brief.md`, `answers` of `brief.json`); once delivered, the answer's decision record gets `delivered_to` and is not delivered again. A hand-back still waiting for an answer when the run stops: only its experiment records (`record`) are registered, the dispatch is closed and the question is dropped. When judge writes the plan (a `plan` dispatch, or the judge session carried on after this round's decision), its brief lists every module's questions and answers of this round ("The user's answers to the modules' questions this round", `round_answers` of `brief.json`).

`rsi answer <ws> <option> [--ref <question id>] --by <name> --quote <user's own words>`: the option must be one of `waiting.options`, and `--by` and `--quote` are required; a `--ref` that is not the question waiting now is refused (the question has changed), and so is a question that is moot; it records the answer as a decision and clears `waiting` in one transaction (the `answer` line of `run.jsonl` is written before the save, and one more line `answer_failed` when the save fails; the `approve` line of `rsi approve` likewise): the approvals `approve`, `stop` and `close_round`, and `skip` (a compare dispatch, closed as skipped), take effect at once, and what needs an agent (going back to a session, a new session, `revise`) is carried out by the next `rsi run`, which meets the same decision point and reuses this answer. An answer holds only for the state it was given in: when the state changes (e.g. there is a new dispatch), the question is asked again.

## Runners

The runner decides how a module agent is launched (`rsi run --runner <name>`; the task definition's `runner.claude` configures `claude`). `claude` adds `--model claude-opus-5-5 --effort xhigh` by default; a `--model` or `--effort` written in `runner.claude.args` is used instead.

**Code modules.** A code module (`rsi.flow.CODE_MODULES`: `compare`) has no agent: its dispatches run a fixed command through the `code` runner (`rsi.runners.code.CodeRunner`, configured by the task definition's `runner.code`), whatever `--runner` says (`Engine.runner_for`; the dispatch record's `runner` is `code`). The exception is `--runner mock`: there every module, compare included, is the script `<mock dir>/<module>.py`, so flow simulations stay self-contained. Everything else is the dispatch protocol of the agent modules: the brief (and the read-deny list, recorded), `handback.json`, registration, the two-part hand-back, long jobs with their completion marker, check-ins, returns and a stop. The engine still builds the prompt of a first launch from `modules/<module>/SKILL.md`, which is the command's contract; the `code` runner ignores it. A later `rsi run` finds a record's agent with the runner the record names (`code` for a command still running after `rsi run` was killed).

| Runner | How |
|---|---|
| `claude` (default) | A headless Claude Code session. The command is `claude -p --dangerously-skip-permissions --output-format json` (module agents get all permissions), followed by the task's extra arguments, then (with a deny list) `--disallowedTools <rules…>`, and last `--session-id <uuid>` for a new session or `--resume <session id>` for a return. The prompt (the full text of the module skill `modules/<module>/SKILL.md` plus `brief.md` plus the hand-back format; for a return, the feedback file) is written into `prompt-<n>.md` in the output directory and given on standard input; the working directory is the output directory. The agent runs in its own process group and survives a killed `rsi run`; a small shell first writes the pid into `agent-<n>.pid`, then execs `claude`; output goes to `agent-<n>.log` |
| `mock` | Starts `<module>.py` from `--mock-dir` as a child process (in its own process group) and returns at once; the engine polls it as it does `claude`, so a stop can terminate it; after `rsi run` is killed, the next run finds a script that is still running by the recorded process id (its command line holds this dispatch's `--outdir` and its start time matches). For tests and flow simulations; it calls no model |
| `manual` | Only writes `prompt-<n>.md` and launches nothing; the agent counts as ended once `handback.json` appears in the output directory. Status `waiting_manual` |
| `code` (no `--runner` choice: a code module's dispatches) | Runs the module's command, the task's `runner.code.commands.<module>` or else `<repo root>/modules/<module>/run`, as `<command> --brief <outdir>/brief.json --outdir <outdir> --mode <launch_mode> [--feedback <outdir>/<feedback file>]`: `launch_mode` is the record's (`first`, `resume`, `continue`, `followup`, `checkin`, or `fresh`, which the command treats as `resume`; `answer` never comes, a code module asks nothing), `--feedback` whenever the record has a feedback file for the launch (`feedback-<n>.md`, `history-<n>.md` for `fresh`, or the `feedback-1.md` of a dispatch a decision made). A relative path as the command's first word is taken from the repository root. It starts and is polled, stopped and found again like `mock` (its own process group in the output directory, output to `agent-<n>.log`; a later run finds a command still running by the recorded process id, its command line holding this dispatch's `--outdir` and its start time matching, and never launches it again); a small shell writes its own pid to `agent-<n>.pid` first (a run killed before it recorded the pid still finds the command by that file) and the command's exit status to `agent-<n>.exit`, so a run that attached to it also learns how it ended. A command whose executable does not exist fails at once (exit code 127). The session id `code-<hex>` is made up and never passed; there is no session to lose, so a resume never fails. `runner.code.timeout_s` (default 6 hours) limits one launch |

A decision agent uses the same command plus `--json-schema <schema>`, starts in its own process group and is checked every 0.5 seconds: when the run is stopped it is terminated at once, and it runs at most `min(timeout_s, 1800)` seconds; its files are in `work/decisions/<n>-<decision point>/`; `manual` has no decision agent and uses the code's default.

**Read-deny rules (only a guard against the agent's own tools reading by mistake, not isolation).** From this launch's brief, the `claude` runner passes rules against reading what the agent should not get to `--disallowedTools` (Claude Code's documentation says deny rules still apply under `--dangerously-skip-permissions`). The list is worked out by `denied_paths(ws, brief)` in `rsi/briefs.py`: each registered artifact under the workspace's `artifacts/` (any kind; the brief is the only legitimate input) with no path of the brief's `inputs` inside its directory, as a whole directory; for a trainset, valset, evalset, testset, corpus or pool of which the brief gives only some files (e.g. deliver gets only `inputs.jsonl`), the other data files of the manifest's `files`, one by one; an artifact whose whole directory the brief gives, or one of another kind of which it gives a file (the task's `task.json`), is not listed. So train cannot read the evalset, the testset, a trainset or valset that is not current, nor the delivered predictions, evaluations, feedback, plans and other artifacts the brief does not give; the brief gives data, train and deliver their own experiment records of earlier rounds (`record`, only their own; train also gets an old workspace's tune records) and gives judge's evaluation the plan that opened this round (last round's `plan`), and those are not on the list, while other modules' records, this round's records and the other plans still are; deliver cannot read the evalset's `labels.jsonl`; judge cannot read the testset (except the milestone judge, whose brief gives it the testset's labels). The task's raw data (the `data.sources` paths of every registered task version) is on the list of every dispatch except data's round 1 sets dispatch (the brief's `sources`, of the current version only); the corpus is given only to data's refresh and to a continued sets dispatch (with the corpus registered), the pool only to data dispatches that produce a trainset and to a continued sets dispatch (with the pool registered), and the other dispatches are denied them by the rules above. The output directories of data's dispatches (under the workspace's `work/`, which may still hold unregistered labelled sets: refused hand-backs, a `redo/` not deleted) are on the list too, except the dispatch's own. A decision agent's (`decide`) list is all dataset directories (corpus and pool included), all delivery, evaluation and feedback artifacts, the output directories of data's dispatches and the raw data paths. `deny_rules(paths)` gives each directory `Read(//<absolute path>/**)` and `Edit(//<absolute path>/**)`, each file `Read(//<absolute path>)` and `Edit(//<absolute path>)` (a single leading slash is relative to the session's directory, hence the two slashes), and a path whose type cannot be told (missing, or under a directory set to `chmod 000`) gets both forms; when the workspace root is a symlink (e.g. `/tmp`, `/var` on macOS), both the real path and the written path are given. A path on the list that contains `(`, `)`, `*`, `?` or `[` (or starts with `!`) would be misread by the rule parser, so the `claude` runner refuses to launch (RsiError, the dispatch record writes no launch), and the workspace must be moved to another path. Each rule is a separate argument in argv; `--disallowedTools` is variadic (`<tools...>`, it takes arguments up to the next one starting with `-`), so it always sits at the end of the command line, right before or after `--session-id` / `--resume` (`--json-schema <schema>` for a decision agent), and the rules cannot swallow another option; the prompt goes on standard input. **Known scope: this is a guard against the agent's own tools (Read, Edit and commands that name a file, such as `cat`) reading by mistake, not isolation.** Child processes the agent starts (`open()` in `python`, `grep -r`, `find`, `cp`, and so on) are not restricted. Stronger limits need a system sandbox or a separate user.

**Module agents carry your Claude Code configuration.** `claude -p` is the same program you use day to day: it reads your user settings as usual (`~/.claude/settings.json`, including hooks, permissions and MCP servers), the project settings and `CLAUDE.md` of every directory above the output directory, and your memory. Module agents may therefore see instructions about your own work. To limit which settings files it reads, list the sources to read in the task definition's `runner.claude.setting_sources` (one or more of `user`, `project`, `local`, passed to the CLI's `--setting-sources`); it governs only settings files, and `CLAUDE.md` and memory are read as usual. For stronger isolation, run as a separate system user or in a container.

When a module agent hands back, it writes `handback.json` in the output directory (format in `HANDBACK_FORMAT` and `read_handback` of `rsi/briefs.py`, also written in the "Outputs" section of the module skills):

| Field | Meaning |
|---|---|
| `status` | `ok`, `failed`, `long_job` |
| `artifacts` | Subdirectory names under the output directory, one per artifact; the engine registers them in dependency order (task, corpus, testset, evalset, valset, pool, trainset, candidate, search, baseline, comparison, delivery, feedback, evaluation, plan, record) and skips those already registered. A subdirectory with `task.json` and no `manifest.json` is a new task version; only rsi-data may hand one back, and it is registered only as a fill of the split rule (TASK.md checked byte for byte by `Workspace.split_fill_errors` on the staged copy, using no `task_change` approval), with `producer` `data` in the registry; otherwise it is refused with the error "rsi-data may hand back a new task version only as a fill of the split rule, and this one is not: " and the reasons. When the hand-back's task, corpus, a set or the pool is refused (or there is a subdirectory whose kind cannot be told, which comes first), none of those after it is registered, and they are recorded as refused ("… of this hand-back was refused, so the sets that depend on it are not registered", said once in the description of the decision point `handback_refused`, followed by the kinds not registered); `record` is registered as usual |
| `marker` | Absolute path of the long job's completion marker; required for `long_job`, otherwise `null` |
| `notes` | The report (gate numbers, cost, problems); for `failed` it must give the reason |
| `questions` | What the user needs to decide; `[]` when none |

Processing: a wrong format, a missing `handback.json`, or a module process that exited without one, is a failed hand-back (decision point `handback_failed`). When `questions` is not empty the user is asked first and nothing is registered before the answer (see above). Refused artifacts stay in the dispatch record, and the decision point `handback_refused` decides on the spot.

The order of processing one hand-back: questions (`questions`) → resuming to wrap up a long job → holding over the budget → registration.

**Holding a hand-back over the budget.** When the task's `approvals` include `over_budget`, `budget.compute_hours` is not `null` and this round has no `over_budget` approval yet, before registering a hand-back the engine works out whether the hand-back's candidates not yet registered (`manifest` `kind` `candidate`, with `cost.compute_hours` a number) together would take the compute used over the budget (`Workspace.budget_overrun`, the same judgement as the check at registration). If so, **none of this hand-back is registered** (not even the experiment records), and it does not count as a refused registration: the dispatch stays `handed_back`, the record gets `held_budget`, STATE `waiting` asks `over_budget` (`kind` `approval`, `ref` `null`, `dispatch_id` this dispatch, options `approve`, `stop`), and `rsi run` stops with exit code 10. The question's text gives the dispatch, the candidates, the compute they need, the compute used and the budget, and says: `approve` approves going over the budget, registers this hand-back's artifacts, and this round goes on to its decision, after which the run stops because compute is over the budget; `stop` stops the run now (as `rsi stop`), and this hand-back's candidates are not registered. After an approval with `rsi answer <ws> approve` or `rsi approve <ws> over_budget`, the next `rsi run` registers **the same hand-back** without training again (log `budget_released`); an approval within a round holds for the later hand-backs of that round too. When the hand-back also has questions, the questions come first; once the answer has gone back to the session and the module has handed back again, the budget is judged then. If `rsi run` is interrupted while a hand-back is held and run again, it is still the same question (the same `q` number), asked once and not dispatched again. Choosing `stop` (or `rsi stop` after the approval and before the registration) ends the hold and the hand-back is not registered: the held candidates were trained, so the same save that stops the run counts them in the compute used as refused candidates are counted (see below); the run's stop wrap-up goes on as usual: the hand-back's experiment records are registered and the dispatch is closed.

**The spend ledger.** STATE's `budget_used` holds `compute_hours`, `api_usd`, `agent_usd` and `annotation_items` (a workspace made before the last three reads them as 0) and STATE's `decision_costs` the decision agents' costs counted (decision key → dollars). When an agent ends, the cost its runner reports is its session's cumulative total: `agent_usd` grows by the increase over the session's last counted total, once per launch (the record's `spent_launches` and `spent_sessions`); a decision agent's cost, read from its log, goes there once per decision key and is logged as `cost_usd` on its `decision_agent` (or `decision_agent_failed`) event. The new lines of a dispatch's spend file `<outdir>/spend.jsonl` (the brief's `spend_file`) are counted when its hand-back is processed, when it fails, and when a stop or a close closes it, after its long job is terminated (the record's `spend_lines`); STATE's `spend_problems` counts the lines with a problem. Format, enforcement and display: spend.md.

**Compute of refused candidates.** A candidate refused at registration was trained too: its `manifest`'s `cost.compute_hours` (when a number) counts in the compute used `budget_used.compute_hours` and is recorded in STATE's `budget_used.refused` (`{real path of the candidate's source directory: hours}`; an old workspace without this item reads as empty; `Workspace.refused_compute_hours()` is its sum). It counts once per source directory: the same directory refused again with the same cost is the same training and is not added again; a changed cost counts as a new training and is added. When that directory later registers successfully it is removed from `refused`; with the same cost as when refused it is not added again (fixed in place, not retrained), with a different cost it is added as usual. Not counted: a registration refused because the run has stopped (`StoppedError`), a `manifest` that cannot be read or whose cost is not a number, a source already registered or content identical to a registered artifact. When a stop closes a dispatch whose hand-back has not been processed (held over the budget, waiting for an answer, handed back and not processed), the candidates the hand-back lists that are not registered are counted the same way (once per source directory and cost; registered sources are not counted): `rsi stop` (also via `rsi answer … stop`) counts those already handed back in STATE, and the wrap-up of `rsi run` after the stop counts those it finds handed back only then (still running in STATE at the stop); both go by the same key and never count twice. This amount is recorded in a save of its own and is not rolled back when a registration fails. `long_job`: once the marker is written and its first line is `ok`, the listed artifacts are registered, or, when none are listed, the same session continues to collect them (`continued` plus 1, at most `flow.max_continues` times; at the limit it is recorded as failed); a marker that is not `ok` is recorded as failed. Before a milestone release's registration that uses the sealed testset (a delivery or a baseline with `predictions_test`, an evaluation with `uses_testset` true), the engine writes the `use_testset` approval quoting the user's words in answer to the milestone question.

**The completion marker appears.** The marker counts as there only when the file exists and its modification time is not earlier than the launch that started the long job (`rsi.flow.marker_done`). That launch's time is its stamp: before every agent launch the engine writes `.launch-<n>` in the output directory (`<n>` is the record's `launches`), on the same file system as the marker, with modification times from the same clock (on NFS the server's clock, which may differ from this machine's by a few seconds); the two files' times are compared without any slack (a marker whose modification time is not earlier than the stamp's counts; on a file system with whole-second file times, a marker written in the same second as the stamp counts too); the dispatch record's `long_job_launch` says which launch it was. Only without that stamp (old records, old workspaces) is the local clock used: `long_job_since`, or `launched_at` without it, allowing 2 seconds early. An earlier file is left from an earlier long job (the module reused the marker path without deleting it first): the hand-back is not processed, and a stop still terminates this long job. So each long job uses a new marker path, and `rm -f <marker> <marker>.pid` comes before it starts.

**The long job's pid file.** When a module starts a long job in the background, it writes `<marker>.pid` beside the completion marker (before handing back `long_job`): the first line is the long job process's id, the second its start time (Unix seconds, e.g. `date +%s`; a UTC time such as `2026-11-23T20:15:00Z` is accepted too). The second line may be left out, but without it confirmation rests only on "the process is still alive and started no earlier than this dispatch", and a reused process id may be mistaken, so write it. The process id must be that of the long job process itself, written by the job: e.g. `sh -c 'printf "%s\n%s\n" $$ "$(date +%s)" > <marker>.pid; exec <command>' > <log> 2>&1 &` (`exec` lets the command keep this process id), or a Python job writing `os.getpid()` and `int(time.time())` at its start; do not use the background process id the shell gives, which may be a wrapper process in an interactive shell. Better run the long job in its own process group (e.g. `subprocess.Popen(..., start_new_session=True)`), so a stop terminates the whole group; when it is not a process group leader, only that one process is terminated. When the run stops, the engine uses it to terminate long jobs that have not ended (see "Stopping mid-run").

## Stopping mid-run

The user can stop the run at any time from another process (`rsi stop`, or answering `stop`), even while `rsi run` waits for an agent or a decision agent. Stopping stops the agents:

1. Before launching or carrying on any agent, before making and carrying out a decision, and before handling a refused registration on the spot, the engine reads STATE again: when the run has stopped it launches nothing more, the dispatch it was about to launch or carry on is closed (status `done`, with the reason in `closed`), and the step ends. A registration refused because the run has stopped is no refused artifact (not `handback_refused`): this dispatch is closed, the subdirectories not registered are written in `closed`, its long job, if it has not written its completion marker yet (e.g. a check-in handed back part of the artifacts), is terminated as in step 4; the hand-back's experiment records (`record`, still allowed after a stop) are registered as usual.
2. While waiting for agents, `rsi run` reads STATE again at every poll, and checks once a second between polls: when the run has stopped it waits no more and goes straight to the report step. A decision agent is checked every 0.5 seconds and is terminated the same way.
3. The report step first handles every dispatch still `pending` or `running`: a `pending` one (not launched yet) is just closed, and that launch does not count in `launches`; for a `running` one, the process handle is used when this process launched it, and others (e.g. left by a killed `rsi run`) are found again through their runner. An agent that has already ended has its result recorded first; one still running and confirmed to be the process of this launch (its own child process, or the runner's process identification: for `claude`, the program and the start time match; for `mock` and `code`, the command line holds this dispatch's output directory and the start time matches) has its whole process group terminated (SIGTERM first, SIGKILL a few seconds later), and the record is closed as "agent terminated"; one done by hand, or whose process cannot be found, only has its record closed. Then the other dispatches still open (hand-backs not registered, failures, long jobs) are all closed, and the hand-back's `record` is registered first.
4. Long jobs whose completion marker has not appeared (dispatches with a `marker` in the record, whose marker has not appeared (see "The completion marker appears") and that are not `marker_seen`, whatever their status: `long_job`, a check-in running, failed or not launched yet, a return after a long job's dispatch failed): `<marker>.pid` is read; only when the process is still alive (a zombie that has ended and not yet been reaped by its parent does not count as alive; on Linux, a zombie whose other threads still run (a multithreaded process whose main thread exited first), or a process group leader whose group still has a process that is not a zombie, counts as alive), started no earlier than the launch that started the long job (the dispatch record's `long_job_since`, or `launched_at` for old records without it; a check-in relaunching the session does not change it; compared in whole seconds, allowing 2 seconds early, since Linux's `ps` works the start time out from the boot time and may be a second early) and no later than the pid file's time (the start time on the file's second line, or the file's modification time when it is not written: the file is written after the long job starts; 2 seconds or more later means another process that reused the process id; earlier means the long job wrote the pid file late, and it is still the job) is it confirmed as this long job, and its process group is terminated (result `terminated`); a process that no longer exists is recorded as `gone`; without a pid file (`no_pid_file`), with a file that cannot be understood (`bad_pid_file`) or when it cannot be confirmed (`unconfirmed`, e.g. a reused process id) it is left alone and listed as "not terminated, it may still be running". At the same time, any other `<name>.pid` in the dispatch's output directory whose `<name>` does not exist or is 2 seconds or more older than the pid file (a marker left by an earlier long job, whose path was reused; not the record's `marker` or `marker_seen`, and not the `claude` or `code` runner's own `agent-<n>.pid`) is confirmed the same way and terminated (start time no earlier than the `started_at` at which this dispatch was created): when a check-in restarted watch and has not handed back a new completion marker yet, the engine knows only the old marker, and this is how the new watch is found. The results go into the dispatch record's `long_job_stop` (the marker's pid file at the top level, the others in `others`), and `run.jsonl` records `long_job_stopped`, `long_job_gone` or `long_job_left` for each pid file (with `context`; those in `others` with `orphan: true`); the reason printed when `rsi run` ends (`reason` with `--json`) says which long jobs were terminated and which were not (with the reasons, asking the user to end them by hand), and the "Stop status" section of `REPORT.md` lists them one by one (process id, completion marker; those in `others` whose process no longer exists are not listed, nor in the event log of the progress pages). Long jobs whose completion marker has appeared are left alone.
5. Before the run ends (`done`) it checks once more that no dispatch is left `pending` or `running`, and the pages no longer show any agent running.

So after a stop, running `rsi run` once more (also after `rsi run` was killed) stops the agents left behind, closes the records, writes the report and exits with code 0.

## Returns to the same session

After a failed gate, a refused registration or a failed hand-back, the engine by default lets **the original session** carry on: it is launched with `--resume <session id>`, its input is the feedback file `feedback-<n>.md` (the reason, the changes to the brief, the failed gates and their values (for a trainset's failed `generated_matches_heldout` check, at most 20 ids of its rows that match held-out inputs, never those inputs: datasets.md, "Generated rows and the held-out sets"), the error texts, the notes of the last hand-back, the user's answers to its last questions, and what to do), the dispatch record's `returns` goes up by 1, and the log gets a `resume` line.

The same session also has four kinds of continuation that are not returns and do not count in `flow.max_returns`: the wrap-up after a long job ends (`continue`, `continued` plus 1, log `resume` with `mode` `continue`); the second part of a two-part hand-back (`followup`: train writing the search after its trial candidates are registered, compare writing the comparison after its baselines are registered, judge writing the plan after the evaluation's decision; `followups` plus 1, log `followup`; the feedback file's first line is "# Continue: the second part of the hand-back", and it lists each artifact the first part registered: subdirectory in the hand-back → registered id (e.g. `` `cand-t3` → candidate-0007 (candidate) ``); the same content goes into `registered-<n>.json` beside the feedback file: `[{"dir", "kind", "id"}, …]`, n being this launch's number; it lists every artifact this dispatch registered in this round after the latest search, over all launches, so it is complete even when the first part took two launches to register; a return (`resume`) lists them and writes this file the same way); sending back the user's answer to its questions (`answer`, `answered` plus 1, log `resume_with_answer`); and a long job's check-in (`checkin`, `checkins` plus 1, log `checkin`; the feedback file's first line is "# Check-in", it gives the completion marker and the check-in's number, and what to do is to check the environment, handle anything wrong first, and while the long job still runs hand back `long_job`: the same completion marker when it did not restart trials, or a new completion marker when it restarted trials and started a new trsi watch, which the engine accepts). Check-ins happen only when the task's `flow.checkin_minutes` is on: while the dispatch is `long_job` and its completion marker has not appeared, once every that many minutes from its latest hand-back; once there have been `flow.max_checkins` and another is due, the user is asked (`ask`, `what` `checkin`, `ref` the dispatch id, options `continue` for that many check-ins more, `wait` for no more check-ins and only waiting for the completion marker, `stop` to stop the run); once the completion marker appears the question is dropped and there are no more check-ins; `rsi status` prints one line for each such long job (check-ins done, the limit, the time of the next one). The second part is free only once, after the launch that registered the first part (the record's `registered` says which launch handed back each artifact); if something is still missing after the second part's hand-back (e.g. still no search), asking again is a return. A user's request to change the plan (`revise`) is a return. When the session cannot be carried on (the runner reports the session no longer exists or cannot be loaded) or there is no session id, a new session is opened whose input is `history-<n>.md` (the previous brief, each hand-back's `handback-<k>.json` and this feedback) plus the rebuilt brief, and the log gets `fresh_session`. `new_session` (an option of a decision) is something else: it closes this dispatch and opens a new dispatch.

**Every continuation (return, long-job wrap-up, followup, answer, check-in, a new session taking over) rewrites the brief from the workspace as it is now.** The workspace may have changed meanwhile (e.g. data was dispatched for a new trainset, the evalset was refreshed, train has new trial candidates): `brief.md` and `brief.json` are built again, the previous ones are kept as `brief-<k>.md` / `brief-<k>.json` (k being the launch they belonged to), the feedback file's section "The brief has changed" lists what changed (`ids`, inputs, attempts used, budget left), and new artifacts must refer to the new ids.

**Recovery after an interruption.** A record in status `pending` has not been launched yet; the next `rsi run` launches it. When a record has `launched_at` but the runner finds no trace of any launch (`claude`: no pid, pid file or log; `mock` and `code`: no log; `manual`: no `prompt-<n>.md`), it was interrupted before the launch: the engine launches this once more, and it is no return. When a registration made it into `registry.jsonl` but STATE was not saved in time, before the next step the engine adds it to this round's artifact list and applies the registration's effect on STATE (current artifacts, budget, evalset uses, plan, the one-time approval it used), and logs `repair`. When a decision's dispatch was interrupted before its `feedback-1.md` was written, the launch rewrites it from the reason saved in the record.

## While waiting: page refresh, GPU snapshot and status line

**Refresh.** While the engine waits (`wait_agent` polling agents; with check-ins on, `wait_long_job` waiting for the completion marker), after each poll it checks: once `flow.page_refresh_seconds` (default 60) seconds have passed since the progress pages were last written, it takes a GPU snapshot first and then rewrites the pages. After each step the pages are written as before (without a GPU snapshot). The pages are still static HTML and can be rsynced to another machine to look at. Without check-ins, `rsi run` still stops with exit code 11, and after that the pages are updated only by the next `rsi` command or `rsi dashboard`.

**Pages.** After the workflow diagram and the three cards, the overview has four panels updated with each refresh: "What is running now" (each open dispatch: stage, dispatch id, skill, status, which launch and how, number of returns, check-ins c / limit and the time of the next check-in, the long job's completion marker, and the `progress.json` in the output directory: summary, facts, table, notes and update time, with staleness (the dispatch alive and no update for 5 minutes or more) and format problems marked), "Agent judgement" (`handback.json` and `handback-<n>.json` of each dispatch's output directory, the latest 6 by file time: the first 300 characters of the notes, expandable to the full text, and the questions), "GPU" (the snapshot below: the task's `resources.gpu_ids`, or all GPUs when not written; a snapshot older than 3 × `page_refresh_seconds` is marked "Stale") and "Recent events" (the latest 10 entries of the event log). The current stage of the workflow diagram has one more line: the first fact of the stage's open dispatch, or for a long job without one "long job · c check-ins". "Current best" adds the best candidate of this round on the valset, and the attempts row of "How far from the stop" adds " (N in progress)" while this round has open train dispatches. Rendering only reads these files; it calls no external command and writes no file.

**GPU snapshot** `<ws>/work/gpus.json` (`rsi/gpus.py`, written atomically): `nvidia-smi` is called twice (`--query-gpu=index,uuid,name,memory.used,memory.total,utilization.gpu` and `--query-compute-apps=gpu_uuid,pid,used_memory`, both with `--format=csv,noheader,nounits`, each with a 5-second timeout; a process that times out is killed, and if it has not exited 1 second after the kill (e.g. stuck in the kernel) it is not waited for any longer, so waiting never hangs on `nvidia-smi`; while an `nvidia-smi` left that way still runs, no new one is started and the snapshot is an `error` right away, "the previous nvidia-smi has not ended"), and all GPUs are written:

```json
{"at": "2026-11-24T12:46:23Z", "status": "ok", "error": null, "uid": 1001,
 "gpus": [{"index": 0, "uuid": "GPU-…", "name": "NVIDIA A100-SXM4-80GB", "memory_used_mib": 37000,
           "memory_total_mib": 81920, "utilization_pct": 97,
           "processes": [{"pid": 4242, "memory_mib": 36000, "owner": "ours", "user": "alice"}]}]}
```

`status` is `ok`, `missing` (no `nvidia-smi`) or `error` (an error or timeout, with the reason in `error`; GPUs read before the error are kept). A process's `owner`: `ours` (owner uid equal to `uid`, i.e. the user of the `rsi run` that took the snapshot), `other` (`user` is the owner's user name), `unknown` (the owner cannot be found, e.g. a process in another pid namespace); the owner is read from `/proc/<pid>`, or with `ps -o uid= -p <pid>` without `/proc`. Values such as `[N/A]` (MIG) are recorded as null. Only this timed refresh calls `nvidia-smi`; `rsi dashboard`, other commands and page rendering only read the latest snapshot. The framework only shows it: it does not choose GPUs by it and touches no process.

**Status line.** `rsi run` prints status lines on stderr (`now_line` in `rsi/live.py`, from the same data as the pages); stdout is unchanged, and with `--json` it still holds only the one JSON object:

```
20:23 round 1 ② Train & tune d-0001 · training 3 trials (GPUs 0, 4, 6) · configs 3/3 · GPU hours 1.3/8 · incumbent c4339e55d6 (lr 5e-6) · next check-in 20:46 | budget: GPU hours 1.3/8 · agent $ 4.20/–
```

- It starts with the local time HH:MM and the round; then one segment per open dispatch (`pending`, `running`, `long_job`, `handed_back`): "stage dispatch-id · what it does · the first 3 facts · next check-in HH:MM", the segments joined by " | ". After "HH:MM round N" the line continues in lower case.
- "What it does": while STATE waits on a question tied to this dispatch (`waiting`'s `ref` or `dispatch_id` is its dispatch id, of any kind: a question in a hand-back, a hold over the budget, the check-in limit, a decision about it) it is `waiting for the user (q-NNNN)`, placed before the progress, and then there is no "next check-in" (ruling R5: a user watching `.err` must be able to see that the run waits for them); otherwise the summary of the `progress.json` in the dispatch's output directory (see progress.md) when it has one, with " (no progress update for N minutes)" added when stale (the dispatch alive and no update for 5 minutes or more); otherwise by status: `not launched yet`, `rsi-<module> running (launch k)` (a continuation adds its launch mode, e.g. " · check-in"), `long job running, waiting for completion marker <file name>`, `long job done, waiting for rsi run to wrap it up` (the marker is there), `handed back, waiting to be registered`. The facts are the first 3 of `progress.json`; "next check-in" appears only for a long job with check-ins on. A moot question (`rsi.flow.stale_waiting`) does not count as waiting.
- When the run has stopped and dispatches are still open (agents or long jobs the stop has not terminated yet): the overview's stop title comes before these segments (e.g. "stopped, 1 agent and 1 long job still running"), then the segments joined by " | ".
- Last, after " | budget: ", the spend ledger's short form (`ledger_short`, spend.md): the resources with a budget or a use and the count of spend-file lines with problems; left out when there is none.
- With no open dispatch: `waiting for the user (q-NNNN)` while STATE waits on a question; "waiting for the user to answer N questions in Claude (listed on the progress page)" while the pages list other questions (a milestone not asked yet, those written in `work/notes.md`); otherwise the title of the overview's "What the run waits for" (e.g. "Next: ④ Deliver", "Stopped: …"), which the line continues in lower case ("next: ④ Deliver").

**When it prints.** After each step it computes `now_key`: the round, whether stopped, the id of the waiting question, the type, step and dispatch id of `next_action`, and (dispatch id, status, launches) of each open dispatch; when it differs from the last printed one and the line's text also differs from the last line, it prints a line. This covers dispatches, launches and continuations (check-ins included), agents ending (hand-back, long job, failure), registering or holding a hand-back, decisions, questions, promotion decisions, closing a round, moving on to the next round, the report and the end, and stops; a change in progress numbers alone does not count. The first step of every `rsi run` always prints a line (when the first step is a wait, before it waits). While waiting, when no line has been printed for `flow.status_minutes` (default 5) minutes, it prints one more (a heartbeat), which carries the progress numbers.

**Errors.** An error while writing the pages, taking a GPU snapshot (including a snapshot whose `status` is `error`; no `nvidia-smi` does not count) or printing a status line only prints `warning: <reason>` on stderr (`dashboard not updated: …`, `GPU snapshot failed: …`, `status line failed: …`) and never interrupts the wait. The same kind of error is warned about only once per run: judged by where it happened, the exception's type and errno, not by the text (which may hold a temporary file name that changes every time). When a status line cannot be written out (e.g. stderr's pipe is broken) it warns once and prints no more status lines; an error in printing the warning itself does not affect the run either.

The first line of `rsi status` is `now: <the same line>`; the other lines are unchanged.

## Run log

`<ws>/work/run.jsonl`: one `{"at", "event", ...}` per line. Events are `action`, `result`, `launch`, `recover`, `agent_end` (with `cost_usd`, what the runner reports: the session's cumulative cost so far), `register`, `resume` (a return, or a long-job wrap-up with `mode` `continue`), `followup` (the second part of a two-part hand-back, shown as "Continued" on the pages), `resume_with_answer` (the user's answer sent back to the session), `checkin` (a long job's check-in), `asked` (a hand-back with questions; `held` lists the subdirectories not registered for now), `budget_held` (a hand-back held over the budget: `dispatch_id`, `launch`, `question_id`, `dirs`, `cost`, `used`, `budget`), `budget_released` (a held hand-back registered after the approval: `dispatch_id`, `launch`, `by` `approve`), `spend_invalid` (a line of a spend file that breaks its rules: `dispatch_id`, `file`, `line`, `error`, `counted` (its amounts counted all the same), `text`; see spend.md), `resume_failed`, `fresh_session`, `session_mismatch`, `clear_waiting`, `decision` (every decision, with `by`, `reason`, `quote`), `decision_reused`, `decision_agent`, `decision_agent_failed`, `approval`, `continue_capped`, `closed`, `agent_stopped`, `long_job_stopped`, `long_job_gone`, `long_job_left`, `exit`; `rsi answer` and `rsi approve` append `answer` and `approve`. The event log page of the progress pages shows these together with registrations and approvals.

## Exit codes

`rsi run` prints one line of reason (`{"status", "reason"}` with `--json`), and its exit code says where it stopped:

| Exit code | `status` | Meaning |
|---|---|---|
| 0 | `done` | Stopped, report written |
| 10 | `waiting_user` | Waiting for the user's answer (the reason holds the question and the options; next step `rsi answer`) |
| 11 | `waiting_long_job` | Waiting for a long job's completion marker |
| 12 | `waiting_manual` | Waiting for a manual hand-back (`--runner manual`) |
| 13 | `max_steps` | `--max-steps` used up; running it again goes on |
| 1 | `error` (`--json`) | Refused or an error; state unchanged |

## Locks

- `<ws>/work/run.lock`: while `rsi run` runs it holds an exclusive non-blocking `flock` on it (the file holds the process id, as a hint), and a second `rsi run` is refused. The progress pages read this process id: only while it names a live process does the top bar show "● running"; otherwise it shows "waiting for rsi run" or what the run waits for (the user's answer, the long job, a manual hand-back); after `rsi run` exits and releases the lock, the pages are rewritten once more. However the process ends, the kernel releases this lock, so the file a killed `rsi run` leaves behind is no lock, and two processes never race to take over. On platforms without `fcntl` the file is created with `O_CREAT|O_EXCL`, and when its process id no longer exists the old file is moved away by an atomic rename and created again.
- `<ws>/STATE.lock`: every read-change-write of STATE.json (registration, approvals, `rsi answer`, `rsi stop`, the engine's dispatch and decision records) happens under its exclusive `flock`: read from disk again, change, save once. So `rsi approve`, `rsi answer` and `rsi stop` can write while `rsi run` runs, and no update is lost. Readers need no lock (STATE.json is replaced atomically). On platforms without `fcntl` (not POSIX) there is no lock, but writes are still atomic.
