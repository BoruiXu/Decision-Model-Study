# RSI operator skill

## Overview

The main flow is written in code: the flow engine in `rsi run` decides the next step from the workspace state, dispatches the module agents itself (four modules: data, train (train & tune), deliver and judge, each a headless Claude Code session; when the task definition has a `compare` section, ③ Compare also runs between train and deliver as fixed code, a report and never a gate), validates and registers their hand-backs, makes the promotion decision, closes the round, moves to the next round, checks the stop and writes the run report. You do not decide the flow and do not dispatch modules; you do only four things:

1. Talk with the user, draft the task definition and, once the user confirms it, create the workspace ("Task intake").
2. Run `rsi run` and read its exit code and its one-line reason ("Running").
3. Relay the question the run waits on and its options to the user, record the user's own words with `rsi answer`, then run `rsi run` again ("Answering questions").
4. When the user asks how it is going, read `rsi status` and the progress page and relay them ("Progress").

The rules are judged by code: the task definition, the valset, the evalset, the sealed testset, version registration, promotion and the stop are all in `rsi`. Do not judge yourself whether to promote, whether to stop or whom to dispatch next; do not run promote, next, close-round or the artifact-registering commands yourself (except for a new version of the task definition): the engine runs them. Do not edit `STATE.json`, `registry.jsonl` or the files under `artifacts/` by hand; do not do a module's work (no making data, training, packaging, scoring or writing plans). When `rsi` refuses, act on its error message.

Below, `rsi <subcommand>` always means `PYTHONPATH=<repo root> python3 -m rsi <subcommand>`, where `<repo root>` is the framework repository root, i.e. the directory that holds `rsi/cli.py`, and `<ws>` is the workspace directory. Before the first use, find `<repo root>`: from the real path of this file (symbolic links resolved), go up to the directory that holds `rsi/cli.py`; when there is none, ask the user; then check with `PYTHONPATH=<repo root> python3 -m rsi --help` that it runs. Once the workspace exists, write `<repo root>` into the work notes `<ws>/work/notes.md`, and take it from there in a new session.

## Entry points

- A new task: start at "Task intake".
- Continuing an existing workspace: read `<ws>/work/notes.md` for `<repo root>`, run `rsi dashboard <ws>` to open the progress page again, run `rsi status <ws>` to see the current state, then start at "Running". `rsi run` can be resumed: after its process exits, the machine restarts or the session breaks, run it again and it goes on, without dispatching or registering anything twice.
- The user answered the question the run waits on: "Answering questions".
- The user asks how it is going: "Progress".

## Task intake

1. Go through the sections of `templates/TASK.md`, find the information the user has not given and ask for all of it at once, not in several rounds of follow-ups. Often missing: the labels and their meanings, the inputs the model can see, the data sources, the thresholds of the data quality checks, the primary metric and the baselines, the target, the promotion rule, the stop conditions, the budget and the resources. `templates/task.example.json` is a filled-in example. Write the data sources as `data.sources` entries `{"path", "about"}`: the absolute path of the raw data on this machine and one sentence about it (the data module reads it in round 1 and writes a preprocessing script; every later dispatch is denied it). Also tell the user: once the corpus is registered you will make these paths unreadable (`chmod 000`, see "Running"); to rerun the preprocessing for an audit or to redo the data later, restore the permissions for that time and lock them again when done; meanwhile the agents of the run cannot read the raw data.
2. When you set a default for the user, say why. `approvals` checks `plan`, `over_budget` and `delete` by default (every round's plan needs the user's confirmation); remove them only when the user clearly does not want them. The train command defaults to `<repo root>/modules/train/train`; the task definition's `resources.train_command` (an absolute path) can replace it. The optional `flow` (`max_returns`, `max_continues`), `decisions` (which decision points an agent judges; by default code chooses all of them by rule) and `runner.claude` (command, extra arguments, timeout; module agents use Opus 5.5 with effort xhigh by default, and `--model` / `--effort` in `args` change that) and `runner.code` (the command of a code module such as compare, default `<repo root>/modules/<module>/run`) take their defaults when left out; the fields are in `docs/interfaces/task.md`.
3. Create a task directory outside the workspace and write `task.json` and `TASK.md`, the two matching item by item, with `version` 1. The split rule `data.split` may be left out or written in part (e.g. only the row counts of the sets, `sizes`): rsi-data fills it in from the data in round 1 and records it as a new version of the task definition, without asking the user. Run `rsi validate task <dir>` and fix until it passes.
4. Show `TASK.md` to the user. Once the user clearly confirms, run `rsi init <ws> --task <dir>`; after `rsi init` the progress page `<ws>/dashboard.html` is already written and open in the browser, refreshing every 5 seconds, and from then on every `rsi` command that changes the workspace and every engine step updates it. Tell the user this path (without a graphical interface the user opens it themselves). Then create `<ws>/work/notes.md` and write `<repo root>` in it. From then on the task definition is fixed; changing it goes through `task_change` (see "Approval points").

## Running

Run `rsi run <ws>`. The default is `--runner claude`: each module is a headless Claude Code session with full permissions; `--runner manual` only writes the briefs and waits for a person or another session to fill the output directory; `--runner mock` with `--mock-dir <dir>` is for tests only. It runs for a long time and keeps waiting while module agents work, so run it in the background and do not let the session get stuck in it: run the line below in the background (`PYTHONPATH=<repo root> python3 -m rsi run <ws> --json`, with `<ws>` and `<repo root>` replaced by the real paths). It first prints the name of this run's output file (no suffix; the time plus the shell's pid, so two runs never share a name), then runs, writing the result to `<file name>.json`, the status lines (stderr) to `<file name>.err` and the exit code to `<file name>.exit`:

```
out=<ws>/work/run-out-$(date +%Y%m%d-%H%M%S)-$$; echo "$out"; PYTHONPATH=<repo root> python3 -m rsi run <ws> --json > "$out.json" 2> "$out.err"; echo $? > "$out.exit"
```

When the task has `data.sources` and the corpus is not registered yet, after the first start of `rsi run` also run the line below in the background: as soon as the corpus of round 1's data dispatch is registered, it makes the raw data unreadable (the read-deny list only stops the agent's own file tools, not the subprocesses it starts). First write each path's original permissions into `<ws>/work/notes.md` with `ls -ld <path>`, and note the lock there too once it is done:

```
until grep -q '"kind": "corpus"' <ws>/registry.jsonl; do sleep 60; done; chmod 000 <each path of data.sources>
```

Later, to rerun the preprocessing (to audit the corpus's sha256) or to redo the data, `chmod` back to the original permissions, `chmod 000` again right after, and delete the labelled rows the rerun wrote.

The output of the background job is this file name: note it (write it into `<ws>/work/notes.md` before changing sessions); the shell variable `$out` is gone by the next call. Each run has its own file, and a second run that the run lock refuses writes to its own file, never overwriting the result of the run before it; so do not guess the latest `run-out-*.json`, which may be exactly the refused one. You are notified when it ends; then read `<file name>.json` (`{"status", "reason"}`) and `<file name>.exit` (the exit code) and decide the next step by the table below. While it runs, see the progress with `rsi status` or the progress page, and the latest status lines with `tail -n 3 <file name>.err` (`rsi run` prints a line when the state changes, and while waiting prints another one when it has printed none for `flow.status_minutes` minutes (default 5)); do not poll logs and do not dispatch a subagent to watch.

When it stops it prints one line with the reason; the exit code says where it stopped:

| Exit code | Status | Meaning and next step |
|---|---|---|
| 0 | run ended | Stopped; the run report is in `<ws>/REPORT.md`. Give the user the stop reason, the current best version and its primary metric, and the model package and evaluation report paths the report lists (always the registered paths from the report, never those in module output directories). When no version was promoted, the report starts with "No releasable version was produced": tell the user truthfully where it got stuck, and present no candidate as a usable version |
| 10 | waiting for the user | The reason line holds the question and its options: `Waiting for the user to answer question q-NNNN: … (options: a / b). Run rsi run again after the answer.` Follow "Answering questions", then run `rsi run` again |
| 11 | waiting for a long job | A module's long job (training, search, large batch inference) runs in the background; the reason holds the path of its completion marker. Once the marker is written, run `rsi run` again and the engine has the same session finish up. Wait for the marker with a background command, e.g. `until [ -e <marker> ]; do sleep 300; done`; when the marker is on a remote host, `until ssh <host> test -e <marker>; do sleep 300; done`, writing `<host>` and the marker path into `<ws>/work/notes.md`. When there is still no marker after twice the expected time, look once at the end of the log and at whether the process is still there, then decide whether to keep waiting or ask the user |
| 12 | waiting for a manual hand-back | Only with `--runner manual`: the reason holds the output directory and the brief path; the brief `brief.md` is in the output directory. Once the output directory is filled and `handback.json` written, run `rsi run` again |
| 13 | `--max-steps` used up | Not a fault: run `rsi run` again to go on |
| 1 | refused or error (with `--json`, the status is `error`) | Act on the error message; when another `rsi run` is still running on this workspace, wait for it to stop |

With `--json` it prints `{"status": ..., "reason": ...}`; the status is `done`, `waiting_user`, `waiting_long_job`, `waiting_manual`, `max_steps` or `error`. Every action, decision and answer is recorded in `<ws>/work/run.jsonl`, and the "Events" page of the progress pages shows them together with the registrations.

## Answering questions

When `rsi run` exits with 10, the question is in its reason line and also in "What the run waits for" on the progress page's overview, which also lists the options and the commands to run.

1. Relay the question and its options to the user: what is asked and what each option means (the question text already says so). A decision point's question says why the code passes it to the user (e.g. the return cap is reached); approval questions (plan, evalset refresh, over budget), the milestone and the questions a module asks in its hand-back are the user's to decide anyway and have no code default; do not say they have one. Do not choose for the user; when the user asks for your opinion you may give it, but the answer must come from the user.
2. Once the user answers, run `rsi answer <ws> <option> --by <name> --quote "<user's words>"`: `<option>` is one of the options the question gives, `--by` is who answered, and `--quote` is the user's own words, not paraphrased or shortened. Also add `--ref <qid>`: the id of the question you relayed (`q-NNNN`, shown when `rsi run` stops and on the page); when the question has been replaced, `rsi answer` refuses, so the answer never lands on another question. When the option is not one the question gives, the question has been replaced, or no question is waiting, `rsi answer` refuses and says why.
3. Approval questions (plan, evalset refresh, over budget) are answered with `rsi answer` too: `approve` records the approval, `stop` stops the run, and the plan's `revise` sends the user's words back to rsi-judge to revise the plan; once judge hands back the new plan, the question is asked again. Before approving a plan, explain it to the user: which module it enters at, the evidence for each issue, what will change, the expected gain. The registered plan is at `<ws>/artifacts/<plan_id>/manifest.json` (`<plan_id>` is in the question text); the plan has no cost estimate. A plan can also be approved with `rsi approve <ws> plan --ref <plan_id> --by <name> --quote "<user's words>"`, with the same effect; while the run waits for this approval, it also counts as the answer.
4. The over budget (`over_budget`) question comes in two forms: asked once when the use of any resource with a budget (GPU hours, data LLM dollars, agent dollars, annotation items: the spend ledger, `docs/interfaces/spend.md`) has reached it and a new trainset, training or the comparison is still to be dispatched; and asked on the spot when a module's hand-back holds candidates that would take the compute used over the budget, in which case that hand-back is not registered for now. Relay the question word for word to the user (the held form says which dispatch, which candidates, how much compute they need, how much is used and the budget; both forms say what happens after each choice); do not estimate for the user and do not change the wording. When the user approves, run `rsi answer <ws> approve --ref <qid> --by <name> --quote "<user's words>"`, or `rsi approve <ws> over_budget --by <name> --quote "<user's words>"` with the same effect (it also counts as the answer); when the user does not approve, run `rsi answer <ws> stop --ref <qid> --by <name> --quote "<user's words>"`: the run stops, and the candidates of that hand-back are not registered (they were trained, so their compute still counts as used). Tell the user: once approved, the round goes on until it is decided (for a held hand-back, the next `rsi run` registers the candidates already handed back, without training again), and after the decision the run stops because compute has reached the budget (or whichever budget the question names).
5. The milestone release (asked once when the stop conditions are met and there is a best version; it uses the sealed testset twice, and with ③ Compare on once more for each baseline scored on its inputs): the options are `yes` or `no`. The engine quotes the user's words into each `use_testset` approval, so `--quote` must be the user's own words.
6. A question a module asks in its hand-back (the option is `answered`): none of the artifacts of that hand-back is registered before the answer. `--quote` holds the user's answer to these questions; the next `rsi run` sends it back to the same session of the module that asked, the module changes its work by the answer and hands back again, and only then is it registered.
7. After recording the answer, run `rsi run`. `close_round`, `stop` and `skip` take effect at `rsi answer`; the other answers are carried out by the next `rsi run`.

A decision point's question (train gate not passed, quality gate not passed, hand-back refused or not finished) has the options `resume` (back to the same session, to do it again with the reason), `skip` (only about a compare dispatch: close it and go on without ③ Compare, which is report only), `new_session` (a new session), `close_round` (close this round; only while the round can still be closed) and `stop` (stop the run), and, when the train gate was not passed, also `train` and `data` (which module to go back to). By default the code chooses; it comes to the user only when a cap (`flow.max_returns`, `flow.max_continues`) is used up (not for a compare dispatch: the code skips it then), there is no session to go back to, or the task definition has an agent judge it and the agent chose to ask you. The train gate question has no `resume`; this is by design: choosing `train` goes back to this round's train session to search again.

## Progress

You may write what you want to ask the user, one line each, in the `## Questions for the user` section of `<ws>/work/notes.md` (delete them once asked); the progress page shows these lines as questions waiting for the user. Questions the run waits on need not be written down; the page reads them from STATE.

- `rsi status <ws>`: the first line `now:` says what is happening now (the same line as the status line of `rsi run`), then come the round, the current best version and its primary metric, the attempts this round, the evalset uses, the registered artifacts and their gate results. `rsi check-stop <ws>` only prints whether the run would stop, without changing the state.
- The status lines of the background `rsi run`: `tail -n 3 <file name>.err` (`<file name>` is the output file name noted in "Running") shows the latest three, e.g. `20:23 round 1 ② Train & tune d-0001 · training 3 trials (GPUs 0, 4, 6) · configs 3/3 · GPU hours 1.3/8 · incumbent c4339e55d6 (lr 5e-6) · next check-in 20:46`: the local time, the round, what each open dispatch is doing (the progress the module writes, or its state) and the time of the next check-in. While waiting, the engine rewrites the progress page every `flow.page_refresh_seconds` seconds (default 60).
- The progress page `<ws>/dashboard.html`: the overview's "What the run waits for" shows the agents running (module, session, start time, runner), the questions waiting and the commands to run, and in the workflow diagram the running module is marked "● running"; "What is running now" shows each open dispatch and the `progress.json` its module writes (trial table, update time), "Agent judgement" the latest hand-backs' notes and questions, "GPU" the GPU use `rsi run` samples while it waits, and "Recent events" the latest 10 entries of the event log; the top bar shows "● running" only while an `rsi run` is running, else "waiting for rsi run" or what the run waits for; under `<ws>/dashboard/` are the "Rounds & artifacts" page (which agents each round dispatched and how many times each was sent back), the "Events" page and the "Run report" page. `rsi dashboard <ws> --no-open` rewrites the pages without opening the browser.
- Answering the user: in a few sentences, relay the round, the current best version and its primary metric, what the run waits for, and how far it is from the stop conditions. For the full progress, `rsi report <ws>` prints the run report so far.

## Approval points

The engine stops at these points to ask the user; record the answer with `rsi answer` as in "Answering questions". `--by` is the approver and `--quote` the user's own words, not paraphrased; never approve for the user.

| Approval | Who asks | How to record it |
|---|---|---|
| Confirming the task definition | You, before `rsi init` | Once the user confirms, `rsi init <ws> --task <dir>` (the workspace does not exist yet) |
| `task_change` | You, when the user wants to change the fixed task definition | `rsi approve <ws> task_change --by <name> --quote "<user's words>"`, then register the new version (see "Handling problems") |
| `plan` | The engine, once judge has written the plan and the task requires approval | `rsi answer <ws> approve --by <name> --quote "<user's words>"` |
| `over_budget` | The engine, when a resource's use has reached its budget (spend ledger) and a new trainset, training or the comparison is still to be dispatched, or when a module's hand-back holds candidates that would take the compute used over the budget (that hand-back is not registered for now) | `rsi answer <ws> approve --by <name> --quote "<user's words>"`, or `rsi approve <ws> over_budget --by <name> --quote "<user's words>"`; once approved, the round goes on until it is decided, then the run stops on the budget |
| `use_testset` | The engine, at the milestone release; deliver's test predictions and judge's test scoring each need one, and both follow from the milestone's `yes` | Answer the milestone question; the engine writes the two approvals |
| `refresh_sets` | The engine, when the evalset's uses reach the limit and a new evalset is needed | `rsi answer <ws> approve --by <name> --quote "<user's words>"` |
| `delete` | You, before deleting model files, intermediate results or any other artifact; the current best version's model and `<ws>/artifacts/` are never deleted | `rsi approve <ws> delete --by <name> --quote "<user's words>"`, then delete. Deletion does not go through `rsi`, so when the task requires the `delete` approval, ask the user first, record the approval, then delete. Exception (the user's decision): rsi-train's `trsi collect` deletes unneeded checkpoints by itself (the unchosen checkpoints of packed trials, all checkpoints of failed or replaced trainings), whether or not `approvals` has `delete`, without approval |

Which approvals are required, how many times one approval can be used and in which round it is valid are all judged by code; when an approval is missing, the step concerned is refused, naming the missing item.

## Handling problems

- A module fails, a hand-back is refused, a gate is not passed: the engine handles it by decision point, by default going back to the same session with the reason to do it again, and asks the user only once the cap is used up. Do not dispatch again yourself, and do not change a module's output.
- The user changes the requirements mid-run: first judge whether it changes the task definition, i.e. any field of `task.json`.
  - It does not change the task definition, e.g. they only want the next round to focus on one kind of error: give such views with `revise` when the engine asks about the plan, or in the answer to a module's question; do not change the brief yourself.
  - It changes the task definition: start from the current version, not from the task directory you first wrote: the line `task: <task_id> vN (task-000N)` of `rsi status <ws>` gives the current version; copy `task.json` and `TASK.md` from `<ws>/artifacts/task-000N/` into a new directory and change them there. When rsi-data has filled in the split rule, the current version has the complete `data.split` and the "Split rule" section at the end of `TASK.md`: keep them as they are (once the evalset or the sealed testset is registered, a version that changes `data.split` is always refused). Once `task.json` and `TASK.md` in the new directory are written, add 1 to `version`, run `rsi validate task <dir>`, have the user confirm it once it passes, record the `task_change` approval, then `rsi register <ws> task <dir>`. Later artifacts are produced under the new version. When the labels or the inputs changed, the data sets may no longer apply; settle with the user, one by one, whether to redo them by the new definition; replacing a set needs the `refresh_sets` approval, which the engine asks for.
  - Switching to another task (a different `task_id`): use a new workspace and start from task intake.
- After an evalset refresh, the stop condition's `target` is still judged by the primary metric of the best version's original evaluation, i.e. its score on the old evalset, which may be too high or too low. Tell the user this when the refresh is approved.
- The user wants to end the run: first confirm that they mean ending the whole run, not pausing (to pause, nothing needs doing; go on later from "Entry points"). Then run `rsi stop <ws> --by <name> --quote "<user's words>"`, which prints `stop: user requested: <words>`. While the background `rsi run` waits for an agent, it notices the stop within a second or two, terminates the running module agents (and decision agents), closes their dispatch records, writes the run report and exits with 0; when no `rsi run` is running (or it was killed), run `rsi run` once more: it terminates the agents left behind, closes the records and writes the report (while one `rsi run` is still running, a second is refused by the run lock; just wait for the first to exit). The modules' background long jobs are terminated too (when the module wrote `<marker>.pid` next to the completion marker); those that could not be terminated are listed in the reason of `rsi run` and in `REPORT.md`: give the user their pids and completion markers, and let the user decide how to end them. Deliver as for exit code 0 in "Running". After a stop, only registering a late `record` and cleaning up after a `delete` approval are still possible.
- Once the run report is written, you may add a section "## Interpretation" at the end of `<ws>/REPORT.md`: what this run learned, where the issues mainly lie, what to try first if it goes on. Only relay existing evidence (judge's evaluation reports and plans, the conclusions of the modules' `record`s), each item with its source, and do no new analysis of your own; after adding it, run `rsi dashboard <ws> --no-open`, so that the "Run report" page shows the interpretation.
- The session breaks: load this skill again and go on from "Entry points".

## Common mistakes

| Mistake | Consequence | Right way |
|---|---|---|
| Judging promotion, the stop or whom to dispatch next yourself | Bypasses the rules in code; the version register can no longer be trusted | Only run `rsi run`, and act on the reason and the questions it prints |
| Answering for the user, or putting a paraphrase or a shortening in `--quote` | A forged approval; the engine quotes this sentence into the sealed testset's approvals and the modules' feedback | Relay the question to the user, and put the user's own words into `--quote` as they are |
| Editing `STATE.json`, `registry.jsonl` or the files under `artifacts/` by hand | Registration and the rule checks stop working | Every change of state goes through `rsi` commands |
| Doing a module's work yourself (changing data, tuning, filling in an evaluation or a plan), or registering a module's artifacts by hand | The module owner cannot improve their module, and nobody answers for the artifacts; it bypasses the engine's validation and spot checks | Leave it to the engine, which goes back to the session of the module concerned |
| Two `rsi run` on one workspace at the same time | The second is refused, with the other's pid in the error | Wait for the first to stop; a killed `rsi run` leaves no lock behind (`<ws>/work/run.lock` is a `flock` held by the process), so never delete it by hand |
| Having the session watch a long job, or reading logs again and again | Wastes quota | `rsi run` stops with exit code 11; run it again once the marker is there |
| The user says to end it, and you only stop running | The workspace has no stop record, and the next session runs on; the user gets no report | Record the user's words with `rsi stop`, then `rsi run` for the report |
| Giving the user the path of a model package in a module's output directory | Output directories get cleaned or rewritten, and what you hand over is not the registered copy | Use the registered paths `rsi report` lists |
