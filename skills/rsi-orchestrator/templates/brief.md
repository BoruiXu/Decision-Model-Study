# Brief

Every time the engine dispatches a module agent, code (`rsi/briefs.py`) builds this dispatch's brief from the workspace state and writes it into the dispatch's output directory: `brief.md` (for people; its structure is below) and `brief.json` (the same content, structured). The module agent's prompt is the full text of the module skill plus `brief.md`. The operator session writes no briefs and dispatches no work; to see what brief a module would get now, run `rsi brief` (it only prints, and needs no dispatch record).

When sent back, the same session gets `feedback-<k>.md` (`<k>` is the launch number): why it was sent back (the errors word for word, the gates not passed and their values), what it should do, and the user's answers to the questions it asked last time. Continuations that are not a return also use `feedback-<k>.md`: the second half of a two-part hand-back (`# Continue: the second part of the hand-back`), the user's answers to its questions (`# The user answered your questions`), the wrap-up after a long job (`# Long job finished`). When the session cannot be resumed, a new session gets `history-<k>.md` (the last brief, hand-back and feedback) plus the rebuilt brief.

## Fields of `brief.json`

| Field | Meaning |
|---|---|
| `module`, `skill`, `purpose` | The module, its skill's name, the purpose of this dispatch (`sets`, `trainset`, `refresh`, `train`, `compare`, `deliver`, `judge`, `plan`, `milestone_deliver`, `milestone_compare`, `milestone_judge`) |
| `dispatch_id` | The id of this dispatch (d-NNNN; null for a brief not built through a dispatch) |
| `round`, `task_id`, `task_version`, `task_json` | The round, the task's id and version, the path of the task definition |
| `ids` | The registered ids of the current trainset and valset (the ids of the evalset and the sealed testset appear only for the modules and purposes that need them); manifests refer to these sets by these ids |
| `inputs`, `input_notes` | Input name to absolute path, and one sentence on each; only these paths may be read, and the workspace root is not among them. data, producing a trainset, gets the training pool `pool` and, when there is a best version, its candidate `best_candidate` (dgen scores the pool with it), never anything of the evalset or the testset; refreshing the evalset, `corpus` and the `inputs.jsonl` of every earlier evalset (`evalset_inputs_<id>`, unlabelled); continuing round 1, the registered `corpus` and `pool`. Besides each module's own inputs, data, train and deliver also get this module's `record`s of earlier rounds (only their own; train's include those of tune in old workspaces), and judge's evaluation also gets the `plan` that opens this round |
| `outdir` | The output directory, one subdirectory per artifact |
| `progress_file` | The absolute path of `<outdir>/progress.json`: the progress file the module may write; the progress page and the status line of `rsi run` show it as it is; format in `docs/interfaces/progress.md` |
| `rsi` | The prefix of the `rsi` commands the module may run (only `validate` and `score`) |
| `budget_left`, `attempts` | The budget left of each resource of the spend ledger (`compute_hours`: GPU hours, `api_usd`: dollars of the LLM calls that generate or review data, `agent_usd`: dollars of the agent sessions, `annotation_items`; null when the task sets no budget for it; see `docs/interfaces/spend.md`) and the attempts this round |
| `spend_file` | The absolute path of `<outdir>/spend.jsonl`: the module appends one JSON line for each spend it causes outside its own agent session (GPU hours of work it runs, LLM calls that generate or review data, annotation items); never the hours a candidate manifest records in `cost.compute_hours`, which are counted from the manifest; the engine counts the new lines when it processes the hand-back, a failure or a stop, and counts the agent session's own cost itself; format in `docs/interfaces/spend.md` |
| `goal` | What to do this time: in round 1 from the task definition, later from the issues the plan assigns to this module |
| `handback` | The hand-back format (see below) |
| `train_command` | train and compare only: the train command (compare trains the team's recipe as a baseline with it; data does not train and does not have it) |
| `sources` | data's round-1 sets only: the raw data (the paths of the task definition's `data.sources`), read in this dispatch only and denied to every later dispatch; not in `inputs` |
| `dset` | data only: the command prefix of the split tool, `PYTHONPATH=<repo root>/modules/data python3 -m dset`; its use is in the skill of rsi-data |
| `dgen` | data's trainset purpose only: the command prefix of the data generation tool, `PYTHONPATH=<repo root>/modules/data:<repo root>/modules/common:<repo root> <python> -m dgen` (`<python>`: the task's `resources.onejev.python`, else `python3`); its use is in the skill of rsi-data |
| `search_space`, `search`, `resources`, `checkin_minutes` | train only (`resources` also compare and data's trainset purpose, whose dgen score-pool runs on an idle card of `gpu_ids`): the task's search space, its search settings, `resources.onejev` and `resources.gpu_ids`, and the check-in interval (minutes; null: no check-ins) |
| `compare`, `policy` | compare only: the task's compare settings with their defaults (`rsi.rules.compare_settings`; null when ③ Compare is off) and its `policy` section (null when absent) |
| `features` | compare and data's trainset purpose only: the task's features settings (`adapter` as an absolute path, null for the generic views; `constraints`) |
| `best` | judge only: the current best version's name, evaluation and delivery (`best_before` is written from it) |
| `comparison`, `strongest` | judge only: ③ Compare's comparison whose baselines the evaluation reports (the round's comparison of the evaluated candidate on the current evalset; at the milestone the best version's comparison the milestone scored), null when there is none; and `{"name", "id"}` of its strongest baseline on the valset, or null. Each baseline to report is an input: `baseline_eval_<id>` (in `baselines_eval`, on the evalset), at the milestone `baseline_test_<id>` (in `baselines_test`, on the testset) |

## Structure of `brief.md`

These are the items of `brief.md`; code fills in what is in angle brackets:

- Skill: `<one of rsi-data, rsi-train, rsi-deliver, rsi-judge>` (in `modules/<module>/SKILL.md`)
- Task definition: `<path of task.json>`; the version for people is `TASK.md` in the same directory
- Round: `<n>`. In every artifact's manifest write this number as `round`, `<task_id>` as `task_id`, `<version>` as `task_version` and null as `id`.
- Current registered ids: trainset `<id or none>`, valset `<id or none>`, and the evalset and testset when needed.
- Current best version (rsi-judge only): version name, evaluation, delivery; when the evalset was refreshed, also the best version's delivery on the current evalset.
- ③ Compare (rsi-judge only, when the brief has a `comparison`): the comparison and its strongest baseline on the valset, and that every baseline given as `baseline_eval_<id>` (at the milestone `baseline_test_<id>`) is reported in the evaluation's `baselines_eval` (`baselines_test`): the object `rsi score` prints with `--baselines-on evalset` (`testset`) and one `--baseline <dir>` per baseline, written as it is; report only, never a gate.
- Train command: `<the absolute path of resources.train_command; <repo root>/modules/train/train when the task definition gives none>` (rsi-train only). Call it with `PYTHONPATH=<repo root>` in the environment.
- Raw data (the task's `data.sources`; read it in this dispatch only, every later dispatch is denied it): `<paths>` (only rsi-data's round-1 sets, when the task gives raw data paths).
- Split tool: `PYTHONPATH=<repo root>/modules/data python3 -m dset`; see this module's skill for its use (rsi-data only).
- Data generation tool: `PYTHONPATH=<repo root>/modules/data:<repo root>/modules/common:<repo root> <python> -m dgen`; see this module's skill for its use; it reads only the inputs below (rsi-data's trainset purpose only).
- What to do this time: `<goal>`
- Budget left (each resource of the spend ledger) and the attempts this round.
- Spend file: `<outdir>/spend.jsonl`, with the line format, the rule that `api_usd` is only for LLM calls that generate or review data (source `llm:<tag>`), and that the hours a candidate manifest records in `cost.compute_hours` are never written there (they are counted from the manifest); the agent session's own cost is counted by the engine.
- Input artifacts (read only these; do not look for or read any artifact or directory not listed): a table of name, path and description.
- Output directory: `<outdir>`, one subdirectory per artifact.
- Progress file (optional): `<outdir>/progress.json`. To have the progress page and the status line of `rsi run` show how far you are, rewrite it whole at any time (write a temporary file, then `os.replace`); the format is in `<repo root>/docs/interfaces/progress.md`. You may leave it out.
- Gate numbers to report: every item the "Gates" section of the module's skill lists, each with its value, threshold and whether it passed; also report the actual cost.
- Metrics, baselines, deltas and intervals to report: compute them with `PYTHONPATH=<repo root> python3 -m rsi score --task <task.json> --labels <label-rows-file> --predictions <predictions-file>` (add `--train <trainset rows.jsonl>` for the baselines; to compare with another set of predictions add `--compare <other predictions>` together with `--clusters <inputs.jsonl>` for the clusters of the intervals; also add `--clusters <inputs.jsonl>` to compute `group_prior` when the label rows have no `meta.state_id`; the full form is in the module skill), and write the numbers it prints into the manifest as they are. Their definitions are fixed in code: registration recomputes them the same way and refuses any mismatch.
- Before handing back: run `PYTHONPATH=<repo root> python3 -m rsi validate <kind> <dir> --task <task.json>` on every artifact and hand it back only once it passes. The only `rsi` commands you may run are `rsi validate` and `rsi score`; the engine registers.
- When an artifact must refer to the registered id of another artifact of this dispatch (e.g. `search` refers to `candidate`, `plan` to `evaluation`), hand back the one referred to first; once it is registered, the engine has the same session go on (`feedback-<k>.md` starts with `# Continue: the second part of the hand-back`, not a return), and the registered ids are in it.
- When something needs the user's decision, stop and report it (in the `questions` of `handback.json`), e.g. going over budget, changing the task definition, using the sealed testset, refreshing the valset or the evalset, deleting artifacts, a problem with the inputs. Do not decide it yourself and do not work around it.
- Hand-back format: write `handback.json` in the output directory: `status` (`ok`, `failed` or `long_job`), `artifacts` (subdirectory names in the output directory, one per artifact), `marker` (the absolute path of the long job's completion marker; required with `long_job`, else null), `notes` (gate numbers, cost, problems met; with `failed`, the reason) and `questions` (what the user must decide; `[]` when nothing). When `questions` is not empty, none of the artifacts of this hand-back is registered: once the user answers, the answer goes back to the same session (the feedback starts with `# The user answered your questions`, not a return); change or confirm by the answer, then hand back again every subdirectory to register; the questions of a `long_job` hand-back are asked only once the completion marker is there, and when it lists no artifact, the answer comes with the `# Long job finished` feedback. A long job (expected to take more than 10 minutes) is started in the background and handed back at once as `long_job`; when it ends, succeeded or failed, it must write the completion marker, whose first line is `ok` or `failed`; do not wait or poll. If the completion marker is already there when you would hand back `long_job` (the long job has already ended), do not hand back `long_job`: the engine never accepts a marker older than this launch; read the results, finish the work, then hand back. Before handing back `long_job`, write `<marker>.pid` next to the completion marker: the first line is the long job process's own pid (written by the long job itself, e.g. `$$` in a shell or `os.getpid()` in Python), the second line its start time (Unix seconds, `date +%s`); when the run is stopped, the engine terminates the long job by it. Use a new marker path for every long job (e.g. `<name>-<k>.done`, `<k>` one more each time), and run `rm -f <marker> <marker>.pid` before starting it: a marker file older than this launch does not count as this long job's end.
- Do not dispatch other subagents. rsi-train's brief goes on: train every trial through `trsi launch` as this module's skill says; the train command is for reference only (candidates write it as `code_version.entry`, and the owner calls it for a single run by hand). rsi-data's brief goes on: this module does not train; whether a new trainset is better is judged by this round's train module training on it and the judge module comparing the result with the current best version.
