# rsi-data: data module

Get or generate data, check it and improve its quality. Do only this module's work and dispatch no other subagent; how the module works inside is up to its owner, this skill fixes only the interface.

## Inputs

The brief is built by code and placed in the output directory: `brief.md` (for people) and `brief.json` (the same content, structured: `module`, `purpose`, `round`, `task_json`, `ids`, `inputs`, `outdir`, `budget_left`, `goal` and more; the fields are described in `skills/rsi-orchestrator/templates/brief.md` under the framework repository root). The brief's `inputs` are authoritative: read only the paths listed there. When sent back, the same session gets `feedback-<k>.md` (`<k>` is the launch number), which says why it was sent back and what to change: fix that, then write `handback.json` again. The same session also gets two kinds of `feedback-<k>.md` that are not a return: one starting with `# Continue: the second part of the hand-back` (the second half of a two-part hand-back, e.g. train first hands back the trial candidates and judge the evaluation; once they are registered, it gets their registered ids here and then writes the search or the plan), and one starting with `# The user answered your questions` (see "Outputs").

Read only the artifacts listed below; do not look for or read any artifact or directory not listed; do not read the workspace or the registry.

- `task`: the task definition (always given).
- The round-1 dispatch that produces the sets (sets): the brief's `sources` lists the raw data (the paths of the task definition's `data.sources`, not in `inputs`), read in this dispatch only and denied to every later dispatch; when continuing (the corpus is registered) it also gets the registered `corpus` and `pool`, and does not change them.
- Optional: the previous `trainset`; `plan` (the issues in it attributed to data); `feedback` with real outcomes.
- Later rounds, producing a trainset, get the training pool `pool` (all labelled rows of the training period), from which the new trainset is drawn; no corpus, and no reading of the raw data.
- Later rounds, producing a trainset, when there is a best version, also get its `candidate` (input name `best_candidate`): `dgen score-pool` runs its `model.predict` on the pool rows outside the trainset, and `dgen diagnose` takes the errors from those decisions. The brief of every later-round trainset dispatch also carries `dgen` (the data generation tool's command prefix), `features` (the task's features settings, the adapter as an absolute path) and the task's `resources.gpu_ids` and `resources.onejev` (score-pool runs on an idle card of `resources.gpu_ids` unless `CUDA_VISIBLE_DEVICES` is set). Nothing of the evalset or the testset is given, not even their inputs.
- The brief's `budget_left` and `spend_file`: dgen bills its own spend into `spend_file` (the GPU hours of `dgen score-pool`; one `api_usd` line per LLM call of data generation, review and paraphrasing) and stops at `budget_left` (`compute_hours` for score-pool, `api_usd` for the LLM calls). That data-LLM account is separate from the cost of your own agent session, which the engine counts.
- Every round after the first also gets `valset`, for the duplicate check (the new trainset must not overlap it).
- An approved evalset refresh (refresh) gets `corpus` (the new evalset is drawn from it) and the `inputs.jsonl` of every earlier `evalset` (unlabelled, input name `evalset_inputs_<id>`); the new evalset must not overlap them. It does not get `pool`, the sealed testset or the evalset labels, and does not read the raw data.
- The brief's `dset` (every purpose has it): the command prefix of the split tool; its use is in the steps below.
- This module's `record`s of earlier rounds (only its own): what was tried before and why it was changed that way; whether it worked is not in them, see "Module metrics".

## Outputs

- `trainset`: a new version every time, with its data quality report. From round 2 on it may hold rows dgen generated (`meta.source` `dgen:<method>`) and prompt-variant rows (their specs in the manifest's `prompt_variants`), next to the real rows.
- Round 1, producing the sets, also produces `corpus` and `pool`: `corpus` is the preprocessing script and all the full labelled rows it writes (the manifest gives the command that runs the script, the raw data paths read and the label sources); at registration the whole directory is moved into the workspace. `pool` is all full rows of the training period, from which the trainsets are drawn. Fields in [datasets.md](../../docs/interfaces/datasets.md).
- `task`: handed back only when the split rule was filled in: the new task version `dset sets` writes in the output directory (task.json's version + 1, with only the filled-in data.split added; TASK.md gains a section "Split rule (`data.split`)" at the end). The engine registers a new task version only when it fills in the split rule; one that changes anything else is always refused (even with a task_change approval not yet used); once it is registered, the manifests of this hand-back's other artifacts carry the new version number (dset has written it).
- Round 1 or an approved refresh also produces `testset`, `evalset`, `valset`. Besides rows.jsonl with the full rows, the valset has an unlabelled inputs.jsonl (each row of rows.jsonl keeping only the five top-level keys id, state, question, meta and split, so no target; meta keeps only state_id, cluster, source and n_obs), which deliver uses to reproduce the candidate's valset predictions. The inputs.jsonl of the evalset and the sealed testset are full rows processed the same way, and labels.jsonl has one `{"id", "target", "meta": {"label_source"}}` per row (meta holds only label_source). Input rows with other top-level keys or other meta keys are refused at registration, and label rows may have only the three top-level keys id, target and meta: extra top-level keys and other meta fields may be derived from the labels (label_source too: how a label was made may correlate with the label, so it lives only in the full rows and the label rows), and no field kept in the input rows may carry a value derived from the labels.
- Every row is a OneJev row: id, state (the model's input, formatted as the task definition's input section says), question, target, meta (state_id, cluster, source, label_source, n_obs; other fields allowed) and split. question must equal exactly the question derived from the task's decision (a yes/no binary is a noul question with criteria `{"true": meaning of yes, "false": meaning of no}`; a choice's criteria are label_meanings; a score's criteria are the list of the levels' meanings; instructions copy decision.instructions), and target's keys are the task's labels, summing to 1 (tolerance 1e-6). External OneJev data is used as it is once its meta fields are completed and its question checked, with no other conversion, except that input rows drop the meta fields derived from the labels (e.g. f, mode_score, mode_idx) and the top-level keys other than id, state, question, meta and split; the split of trainset and valset rows must not start with test (onejev-harness does not read such training and validation rows, and registration refuses them). Format and mapping table in "Decision rows" of [README.md](../../docs/interfaces/README.md).
- `record`: one per improvement experiment.

Write each artifact as a subdirectory of the output directory, with null as the manifest's id and round, task_id and task_version as the brief says; fields in [datasets.md](../../docs/interfaces/datasets.md). The row format and directory layout of the data artifacts are in that document, `record` in [record.md](../../docs/interfaces/record.md).

Hand-back order: in round 1, `artifacts` lists, in this order, `task` (only when the split rule was filled in), `corpus`, `testset`, `evalset`, `valset`, `pool`, `trainset`, `record`, and the engine registers them in this order: the new task version first, so every later manifest carries the new version number; the corpus before the sets, and at registration every row of the sets and pool is checked to come from the corpus; evalset, testset and corpus are moved away whole at registration, leaving no labelled copy in the output directory. When one of them is refused, nothing after it is registered (all recorded as refused); fix it by the feedback and hand back again, together, everything not registered. When the corpus is registered (continuing), do not hand back corpus again; `dset sets` uses the one the brief gives and does not change it.

Hand-back: once every artifact is written and validated, write `handback.json` in the output directory: `status` (`ok`, `failed` or `long_job`), `artifacts` (subdirectory names in the output directory, one per artifact), `marker` (the absolute path of the long job's completion marker; required with `long_job`, else null), `notes` (gate numbers, cost, problems met; with `failed`, the reason) and `questions` (what the user must decide; `[]` when nothing). The hand-back counts only once the engine reads this file; a missing or malformed file counts as a failed hand-back, and writing it again correctly is enough. Reading is strict: no field other than those above, `artifacts` holds only subdirectory names (no path separator, no repeats), every item of `questions` is a non-empty string, `marker` is an absolute path or null, and with `failed` `notes` is not empty.

When the hand-back has `questions`, none of the artifacts of this hand-back is registered: the engine asks the user first; once the user answers, the answer goes back to the same session (`feedback-<k>.md` starts with `# The user answered your questions`, not a return). Change or confirm the artifacts by the answer, then write `handback.json` again, listing every subdirectory to register (those listed last time too). The `questions` of a long job (`long_job`) hand-back are asked only once the completion marker is there; when it lists no artifact, the answer comes in the feedback starting with `# Long job finished`, sent back together with the long job's results.

## Gates

- Data quality gate: the checks and thresholds the task definition's `quality_checks` sets (sample size, label distribution, label reliability, near duplicates and so on), each computed with its value, threshold and whether it passed, and written into the `trainset`'s `quality`; `quality.passed` is the AND of all items. `dset` computes five of them itself: `min_rows`, `min_positive_rows` (binary), `max_duplicate_rate` (the share of rows whose input equals an earlier row's), `max_conflict_rate` (the share of rows whose input has two or more hard labels) and `max_synthetic_share` (the share of rows dgen generated, `meta.source` starting with `dgen:`; prompt-variant rows are left out of all five), and writes them with a data profile into the manifest's `quality` and `quality_report.json`. Compute the task's other checks yourself, write them as a JSON file `[{"name", "value", "threshold", "passed"}]` and give it to `dset` with `--checks` to be written together (a check the task lists that neither side computed is an error in `dset`); when the task definition has no `quality_checks`, choose the checks yourself, give them with `--checks` the same way and explain them in the `record`. In the round-1 split, `dset` computes the gate before writing and writes nothing when it fails (see step 6 of the steps); in later rounds, grow and check write even when the gate fails: hand back as it is, and the engine handles it by decision point (by default back to your session with the reason, to redo it); such a trainset, once registered, is evidence only, never becomes the current trainset, and train does not use it. Registration itself adds the failed check `generated_matches_heldout` when generated or prompt-variant rows match evalset or testset inputs (see "Fixed rules" under "Later rounds: trainset").
- No duplicates between sets: `dset` draws in the order testset, evalset, valset, trainset; the ids, inputs and clusters of the rows an earlier set drew do not go into a later set; pool is all the remaining rows in the trainset's range and likewise shares no id, input or cluster with these three sets. At registration the engine checks again, and every row of the sets and pool must also come from the registered corpus. The same `state_id` (the same object, e.g. the same address at different times) in several sets is allowed: `dset` does not refuse it, only reports the count (`shared_state_ids` in the summary and in the trainset's `quality_report.json`), and you write the count into the `record`; only a rule with `unit: state_id` separates by `state_id`, and registration then checks by it too. Later rounds' new trainsets likewise must share no id, input or cluster with the valset, the evalset or the sealed testset (refused at registration).
- Split rule: the keys the task definition's `data.split` writes are used as they are; the missing ones you set from the data in round 1's sets dispatch (`by`, `key`, `ranges` or `fractions`, `sizes`, `stratify`, `unit`, `seed`), and `dset` writes them as a new version of the task definition (a fill), with no approval and without asking the user; why you set them so goes into the `record`. Once the evalset or the sealed testset is registered, the rule is fixed for this run: refresh keeps it, and later dispatches cannot change it (a task version that changes `data.split` is always refused).
- No access kept to labelled sets once handed in: the evalset, the sealed testset and the corpus are generated directly in the output directory, with no copies or labelled intermediate files elsewhere and no symbolic or hard links to files elsewhere (validation and registration refuse them); at registration these three directories are moved whole into the workspace, so they are no longer in the output directory. After the hand-back, keep no copy of the corpus and no copy of the labels of the evalset or the sealed testset, and do not read them again. Later dispatches no longer get the labels of the evalset and the sealed testset: an approved evalset refresh dispatch (refresh) gets the corpus (the only source of the new evalset) and the `inputs.jsonl` of every earlier evalset (unlabelled), so that the new evalset avoids rows already used. The corpus holds all rows and their labels, the rows of the sealed testset and of earlier evalsets included: refresh uses it only through `dset refresh`, never opens it itself and never looks at the rows of the sealed testset or earlier evalsets; labels pass only through the sets and refresh dispatches that produce them. Known limitation: the code only moves directories; the labels in the workspace can still be read on the same machine, and the isolation relies on convention.
- Raw data: only round 1's sets dispatch reads the raw data the brief's `sources` lists (the task's `data.sources`); later dispatches (trainset, refresh) and all other modules are denied it: a trainset comes from `pool`, a refreshed evalset from `corpus`. Once the corpus is registered the operator makes the raw data unreadable (`chmod 000`).
- This module only produces data; it does not train and does not test whether a new trainset is better itself: once the new trainset is registered, this round's ② Train & tune trains on it and produces candidates, and ⑤ Judge & decide compares the candidate sent for evaluation with the current best version (trained on the old trainset) on the evalset; promote or keep is that judgement (see "Module metrics"). This module's gates are the quality gate and the duplicate checks above.
- When the valset or the evalset needs a refresh, or the budget would be exceeded, stop and report; do not decide it yourself.

## Running standalone

The owner runs it in their own sandbox directory, without the orchestrator:

1. Copy the inputs (the previous `trainset`, `valset`, `pool`, `feedback` and so on) from registered artifacts into the sandbox, paths given by hand; the task definition is `<task.json>`. The round-1 split reads the raw data the task's `data.sources` names. No workspace is needed, and the registry is not read.
2. Write the output to an output directory you create in the sandbox, one subdirectory per artifact, with null as the manifest's `id` and a `round` of your choice.
3. Run `dset` as in "Steps and strategy sub-skills", with the prefix `PYTHONPATH=<repo root>/modules/data python3 -m dset` and the output directory above as `<outdir>`. dgen takes its inputs from a brief: write `<outdir>/brief.json` by hand with `inputs` (absolute paths of `task`, `trainset`, `pool`, `valset` and the best version's `best_candidate`), `ids` (`trainset`), `budget_left` (`compute_hours`, `api_usd`; null: no limit) and `spend_file`, and use the prefix `PYTHONPATH=<repo root>/modules/data:<repo root>/modules/common:<repo root> <onejev-harness python> -m dgen`.
4. Validate every artifact with `PYTHONPATH=<repo root> python3 -m rsi validate <kind> <dir> --task <task.json>` (with the new `task.json` when the split wrote `task/`); only an artifact that passes counts as handed in. The only `rsi` commands you may run are this one and `rsi score` (for the metrics, baselines and deltas in the report); do not run `rsi register` or any other command.
5. No training. To know whether a new trainset is better (the owner's job, not a step of this module), give it to the train module to train (its "Running standalone"), then compare with the current best version the way the judge module does.

## Steps and strategy sub-skills

### Commands and paths

- `<outdir>`: the brief's output directory. `<task.json>`: the brief's `task_json`. `<round>`: the brief's `round`. `<trainset>`, `<valset>`, `<pool>`, `<corpus>`: the registered artifact directories of the same names in the brief's `inputs`; `<trainset_id>`, `<valset_id>`: the ids in the brief's `ids`.
- Below, `dset <command> …` always means the brief's `dset` prefix (`PYTHONPATH=<repo root>/modules/data python3 -m dset`) plus the command, run from any directory. `dset --help` lists the five commands (sets, grow, check, refresh, repair); add `--help` to a command for its arguments. Every command prints a JSON summary on stdout; exit code 0 is success, 1 an error in the inputs or the rule (one line `dset: error: …` on stderr, nothing written; `dset repair` alone writes its rows all the same, see step 4 of "Later rounds: trainset"), 2 a failed trainset quality gate (sets only, nothing written). A directory or file to be written must not exist yet: `dset` overwrites nothing; with `--dry-run` it only prints the summary and writes nothing.
- Likewise `dgen <command> …` means the brief's `dgen` prefix (`PYTHONPATH=<repo root>/modules/data:<repo root>/modules/common:<repo root> <python> -m dgen`, `<python>` the onejev-harness venv's, which has numpy and scikit-learn) plus the command, also inside the shell strings of the long-job examples. `dgen --help` lists its seven commands (score-pool, diagnose, generate, filter, neardup, paraphrase, variants) and their arguments. Every command prints a JSON summary on stdout; exit code 0 is success, 1 an error in the inputs (one JSON line `{"error": …}` on stdout and `dgen: error: …` on stderr). dgen reads only the brief's inputs (`--brief <outdir>/brief.json`) and overwrites no diagnosis, arm or output file. Only the later rounds' trainset dispatch has `dgen`.
- Division of work: you write the script that preprocesses the raw data into OneJev rows; splitting and sampling are always done by `dset` by the rule, never by split code of your own. The same rows and rule give the same sets, the summary can be checked afterwards, and refresh relies on this to recompute round 1's allocation. In later rounds your judgement is only which generation recipes and sizes to use and which prompt variants (see "Later rounds: trainset"), and the record; every step that reads, scores, generates, filters, repairs or assembles rows is a `dgen` or `dset` command, never code of your own.

### Round 1: sets

1. **Read the task**: the task definition's `decision`, `input`, `data` (`sources`, `label_sources`, `rows`, `split`) and `quality_checks`. `data.rows.about` says what a row is and where each field comes from; `data.rows.expect` is the exact number of all rows and the row count of each hard label, checked one by one when the corpus is registered.
2. **Look at the raw data**: read only the paths the brief's `sources` lists (not in `inputs`): format, row count, label distribution, the fields usable for the split (time, groups). Read no data elsewhere.
3. **Write the preprocessing script**: write a script in `<outdir>/corpus/`, e.g. `preprocess.py` (a single file, standard library only). It reads only `sources` (absolute paths written in the script), runs in the corpus directory and writes to the relative path `rows.jsonl`: each row is a full OneJev row (format in "Outputs"); `question` is the value of `rsi.rows.question_of(task)` (compute it first with `PYTHONPATH=<repo root> python3 -c 'import json, sys; from rsi.rows import question_of; print(json.dumps(question_of(json.load(open(sys.argv[1])))))' <task.json>` and write it into the script as a constant, so a rerun depends neither on the task file nor on the framework); `meta` has the five framework keys (`state_id`, `cluster`, `source`, `label_source`, `n_obs`; identical or near-duplicate inputs get the same `cluster`, by which `dset` and registration prevent duplicates across sets); the fields the split needs (e.g. the time step) go into `meta.extra`, and upstream fields derived from the labels are not written; follow `data.rows.about`. The output must be deterministic: the same input writes the same bytes (sorted by id, no timestamps, no random numbers without a fixed seed); the operator reruns it by the manifest's `command` and checks the sha256. Run `cd <outdir>/corpus && python3 preprocess.py`; when it is expected to take more than 10 minutes, run it as a long job (see "Long jobs"). The corpus directory holds only the script and `rows.jsonl` (`dset` adds `manifest.json` and `split_report.json`); logs go outside it.
4. **Check the rows**: `dset check --task <task.json> --rows <outdir>/corpus/rows.jsonl` shows the row count, the row count of each label, duplicate inputs and conflicts (two or more hard labels for one input). The row count and each label's row count must equal `data.rows.expect` (otherwise the corpus registration is refused): when they do not, fix the script and rerun it; do not change the task.
5. **Set the split rule**: the keys the task's `data.split` writes are used as they are (`ranges`, `fractions` and `sizes` set by set; `dset` reports conflicts as errors); the missing ones you set from the data, without asking the user:
   - `by`: when there is a time field and the model is for later data, `time`: `key` is the time field, and `ranges` go in time order, trainset earliest, then valset, evalset, testset (one closed interval each, not overlapping; rows outside them are unused). When there are natural groups and one group must not span sets, `group`: `key` is the group field, and whole groups are split at random by `fractions`. When there is neither, `random`: split at random by `fractions`, cluster by cluster.
   - `sizes`: the missing ones by the data. Each set's range, after the rows taken by earlier sets are removed, must hold its size; the evalset's range must leave unused rows for later refreshes (without `sizes.evalset` the range is used up and can never be refreshed); every set needs enough positives (binary) for a stable primary metric.
   - `stratify` (default true: time stratifies by (key value, hard label), the others by hard label); `unit` (default `cluster`. The same `state_id` across sets is allowed and only reported; use `state_id` only to simulate wholly unseen objects); `seed` (default 0).
   Write the part you set into `<outdir>/split.json` (it may hold only the keys the task lacks; a task key you write must equal the task's), and try it first with `--dry-run`:

   ```
   dset sets --task <task.json> --corpus <outdir>/corpus --script preprocess.py --command "python3 preprocess.py" --label-method "<how the labels were made>" --split <outdir>/split.json --round <round> --out <outdir> --dry-run
   ```

   Decide from the summary: each set's `rows`, `label_counts`, `key_span`, `range_rows` (rows in its range), `left_out` (rows left out because an earlier set took them), and `pool`, `unused_rows`, `shared_state_ids` (the number of `state_id`s each pair of sets shares) and `gate` (the quality gate). If not satisfied, change `split.json` and try again.
6. **Split**: run the same command without `--dry-run`. It writes `testset`, `evalset`, `valset`, `pool` and `trainset` under `<outdir>`, and in the corpus directory `manifest.json` (`command`, `sources`, `label_method`, the script and the rows file) and `split_report.json` (the full summary, with each set's label distribution). When the task's rule is incomplete it also writes `<outdir>/task/`: the new version of the task definition (`task.json` version + 1 with only the filled-in `data.split` added; `TASK.md` gains a section "Split rule (`data.split`)" at the end), and every manifest written this time carries the new version number. Do not edit these files by hand.
   - Exit code 2 (quality gate failed, nothing written): adjust the part you set (ranges, sizes, stratification) and try again; when the part the task author wrote is the cause (e.g. `sizes`, the thresholds of `quality_checks`), hand back `questions` and do not change it.
   - Exit code 1: fix by the reason after `dset: error:`. When it says a set's sizes exceed the rows available: lower the size you set or widen the range; when it is the author's size, hand back `questions`.
   - Checks in the task's `quality_checks` that `dset` does not compute: compute them, write them into `<outdir>/checks.json`, and add `--checks <outdir>/checks.json` to the command.
   - When artifacts are refused or sent back after the hand-back and you go on: see "Continuing" below.
7. **Validate**: first validate `task/` (when there is one), then the other artifacts with the new `task.json` (`<task.json>` when there is no `task/`):

   ```
   PYTHONPATH=<repo root> python3 -m rsi validate task <outdir>/task
   PYTHONPATH=<repo root> python3 -m rsi validate <kind> <outdir>/<kind> --task <outdir>/task/task.json
   ```

   `<kind>` is corpus, testset, evalset, valset, pool, trainset in turn. When continuing, validate only the artifacts to hand back: once the corpus is registered, do not validate it again.
8. **Write the record** (see "Experiment records"): what the script does, the row count check, the rule and why it splits this way, the `dset` summary.
9. **Hand back**: delete the temporary files (outputs of trial runs, labelled intermediate files: no labelled rows stay outside the corpus and set directories), write `handback.json` (its `notes` without the label distributions of the evalset and the sealed testset): `artifacts` is `task` (only when `task/` was written), `corpus`, `testset`, `evalset`, `valset`, `pool`, `trainset`, `record` in this order, and the engine registers them in this order. Corpus, evalset and testset are moved whole into the workspace at registration; after the hand-back keep no copy of them and do not read them again.

**Continuing** (some artifacts of the hand-back refused or sent back, or questions answered, and the same session goes on): the feedback and `registered-<n>.json` say which artifacts are registered; in the rebuilt brief, `task_json` is the current task version (the new one once the filled-in rule is registered). `dset` overwrites no directory, so there are two cases, by whether the corpus is registered:
- The corpus is not registered yet (nor anything after it): fix the script or the rows by the feedback (after a change, rerun the script and do step 4 again), delete `task/` and the five set directories under `<outdir>`, and the `manifest.json` and `split_report.json` that `dset` wrote in the corpus directory (keep the script and `rows.jsonl`), then split again from step 6 (`--task` is the brief's current `task_json`).
- The corpus is registered (the brief's `inputs` has `corpus`, and `pool` when pool is registered too): never touch the registered corpus. Split again in a new directory: `dset sets --task <task.json> --corpus <corpus> --split <outdir>/split.json --round <round> --out <outdir>/redo` (delete `redo/` first if it exists; `dset` reads only the corpus's manifest, so `--script`, `--command` and `--label-method` are not needed). The same corpus and rule give the same sets. For every artifact not registered yet (testset, evalset, valset, pool, trainset, and a `task` that is in `redo/` and not registered yet), delete the old directory under `<outdir>` and move the directory of the same name up from `redo/`; then `rm -rf <outdir>/redo`: it holds labelled copies of the redrawn evalset and sealed testset. Hand back only the artifacts not registered yet: the corpus is not handed back again; when only the corpus is registered, pool and all the sets are handed back; when pool is registered too, pool is not handed back again.
Then validate as in steps 7–9 (only the artifacts to hand back), write the record and hand back (only the artifacts not registered yet, in the same order). The `record` of the first hand-back is registered whether or not other artifacts were refused (copied; the one in the output directory stays): write the new record into a subdirectory name never registered before, e.g. `<outdir>/record-2`, and list `record-2` in `artifacts`; rewriting `<outdir>/record` does not register it again.

### Later rounds: trainset

The new trainset is the current one, improved by the issues the plan attributes to data: rows generated for the best version's weaknesses, rows drawn from the pool, cleaned rows, prompt variants. Your judgement is only step 3 (which recipes, how many rows, which prompt variants) and the record; every other step is a fixed `dgen` or `dset` command. Generation works under `<outdir>/gen/` (the diagnosis, the recipes, one arm per recipe `arms/<sha12>/`, the LLM calls `llm/`) and intermediate rows go to `<outdir>/work/`; neither is handed back, and both hold only trainset, pool and generated rows, nothing of the evalset or the testset.

1. **Read** the brief's `goal`, the `plan` (the issues it attributes to data), this module's earlier `record`s (which recipes were tried, by `sha12`, and what the next plan said of them), the task's `quality_checks` (`max_synthetic_share` caps the generated rows) and `budget_left`.
2. **Diagnose** (when the inputs have `best_candidate`; without one, go to step 3 with `smote`, `borderline` and pool rows only). Score the pool rows outside the trainset with the best version's candidate, a GPU long job (see "Long jobs"):

   ```
   mkdir -p <outdir>/gen <outdir>/work
   rm -f <outdir>/score-<k>.done <outdir>/score-<k>.done.pid
   python3 -c 'import subprocess, sys; subprocess.Popen(["sh", "-c", sys.argv[1]], start_new_session=True, stdin=subprocess.DEVNULL, stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)' 'dgen score-pool --brief <outdir>/brief.json --out <outdir>/gen/diagnosis --marker <outdir>/score-<k>.done > <outdir>/score-<k>.log 2>&1'
   ```

   dgen writes `<outdir>/score-<k>.done.pid` itself, takes an idle card of `resources.gpu_ids` (waiting up to `--card-wait` seconds, 600 by default), bills its GPU hours and writes the marker last; it refuses to start when `budget_left.compute_hours` is 0. On a large pool add `--max-rows <N>` (a seeded sample). Wait until the pid file is written (seconds; when it is not, `<outdir>/score-<k>.log` says why), then hand back `long_job` with `marker` `<outdir>/score-<k>.done` and no artifacts. When the session goes on (`# Long job finished`), diagnose the scores:

   ```
   dgen diagnose --brief <outdir>/brief.json --scores <outdir>/gen/diagnosis/pool_predictions.jsonl --out <outdir>/gen/diagnosis
   ```

   and read `<outdir>/gen/diagnosis/diagnosis.md`: the candidate's errors by kind (`<true>→<decision>`; in a binary task `yes→no` are the missed positives), the weakness types of each kind (`<kind>#<g>`, with the features that set them apart from correct rows), their learnability (CLLM easy, ambiguous, hard: a hard failure conflicts with the labels of similar real rows) and the findings, each with `issue`, `evidence` and `try`.
3. **Judge**: choose the recipes, the number of rows of each, and any prompt variants. Every choice cites its evidence, a finding of the diagnosis or an issue of the plan; write the evidence into the record's `hypothesis`. A recipe is one JSON file, `<outdir>/gen/recipes/<name>.json`:

   ```json
   {"name": "missed-positives", "method": "hard", "n": 200,
    "target": {"kinds": ["yes→no"], "types": [], "alloc": "size", "skip_hard_share": 0.3},
    "params": {}, "seed": 0, "max_usd": null}
   ```

   - `name`, `method` and `n` (the rows asked for) are required; the rest have the defaults shown (an unknown key is an error). `seed` is an integer >= 0.
   - `target` (only `hard`, `llm_imitate` and `llm_pattern`; leave it out for `smote` and `borderline`): `kinds`, the error kinds to aim at (`[]`: all); `types`, weakness type keys of `weakness.json` (`[]`: every type of those kinds); `alloc`, `size` (n spread over the types by their number of failures) or `uniform`; `skip_hard_share`, leave out the types whose share of CLLM-hard failures is above it (null keeps every type).
   - `params`: `smote` and `borderline` take `label` (the label to oversample; default the binary task's positive); `llm_imitate` and `llm_pattern` take `model` and `effort` (default the task's agent model and effort, `claude-opus-5-5` at `xhigh`).
   - `max_usd` (the LLM methods): this recipe's cap on its generator and reviewer calls together; null leaves only `budget_left.api_usd`, the account every LLM call of this dispatch draws on.

   | Method | Rows | Needs | Try it for (diagnosis finding) |
   |---|---|---|---|
   | `hard` | the pool's real failure rows of the targeted types, unchanged | the diagnosis | `few_failures`, `confident_errors`, `small_type`, an `unlearnable_type` (hard rows only) |
   | `smote` | interpolations of a real trainset row and one of its 5 nearest real rows of the same label and structure | numpy, scikit-learn | too few rows of a label (an issue of the plan) |
   | `borderline` | `smote`, the anchors weighted towards the rows near the other label | numpy, scikit-learn | `errors_near_threshold` |
   | `llm_imitate` | an LLM writes records the candidate would get wrong the way it got one real failure wrong | the diagnosis, `claude -p`, a long job | `confident_errors`, a `small_type` (a small n) |
   | `llm_pattern` | an LLM analyses each weakness type (12 of its failures against correct rows), then writes records of that pattern | the diagnosis, `claude -p`, a long job | `distinct_pattern` |

   - The findings' `try` lines name recipes the same way: `<kind>_dominates` aims `target.kinds` at that kind; `unlearnable_type` sets `skip_hard_share` (e.g. 0.3) or leaves the type to `hard`.
   - Every generated row keeps its seed's label: its seed's `target`, `state_id`, `cluster` and `label_source`, with `meta.source` `dgen:<method>` and the id `syn<sha6>_<method>_<n>`. Seeds, anchors and partners are always real rows, never rows generated in an earlier round. The LLM never sets a label and is never shown or allowed to edit the `input.verbatim` paths.
   - An LLM row is kept only when an independent reviewer (its own `claude -p` call, which sees only the records) scores its realism at least the threshold it calibrates on 60 real pool rows (about 6 review calls per recipe). Rejected records are retried with the reviewer's reasons for up to 3 rounds; what is still missing is counted as `short`.
   - Size: the generated rows (`meta.source` `dgen:<method>`; `hard` rows keep the pool's source and do not count) may make up at most the share s of `quality_checks.max_synthetic_share` of the new trainset: with T other rows, at most T·s/(1−s) generated rows in all, counted after the filter. Plan the LLM recipes' `max_usd` within `budget_left.api_usd`.
   - A recipe's arm is `<outdir>/gen/arms/<sha12>/`; sha12 is taken over the recipe with its defaults, without `name`. Running an identical recipe again returns the existing arm (`existing: true` in the summary): to retry one, e.g. one stopped short, change its `seed` (or its `max_usd`). Rows whose ids the trainset already holds are refused (an earlier round ran the same recipe): change the `seed`.
   - Prompt variants (only when the plan or the diagnosis says the model leans on the wording of the prompt or on key names): `dgen paraphrase --brief <outdir>/brief.json --n <N> --out <outdir>/gen/specs-<k>.json` asks one generator call for N English paraphrases of the instructions and the label meanings (add `--keys` for new names of the state's keys too) and keeps, as prompt-variant specs, those an independent reviewer scores 8 or more for meaning-equivalence. Run it in the foreground, or as a long job with `--marker <outdir>/para-<k>.done` as in step 2. Choose the specs to use (copy them into a new file) and the share of rows that get one; step 4e adds them. A variant row is its seed rewritten, with the same target, `state_id`, `cluster` and verbatim text, kept next to its seed, in trainsets only.
4. **Mechanics**: always these commands, in this order; a step that starts with "when" runs only then. `<rows>` is the file the last of the row-rewriting steps c, d and e that ran wrote, `<trainset>/rows.jsonl` when none ran.

   a. Generate each recipe. `hard`, `smote` and `borderline` run in the foreground (`smote` and `borderline` need no `--diagnosis`):

   ```
   dgen generate --brief <outdir>/brief.json --recipe <outdir>/gen/recipes/<name>.json --diagnosis <outdir>/gen/diagnosis --out <outdir>/gen
   ```

   An LLM recipe (`llm_imitate`, `llm_pattern`) is a long job and is refused without `--marker`: start the same command in the background as in step 2, with `--marker <outdir>/gen-<k>.done > <outdir>/gen-<k>.log 2>&1` at the end, and hand back `long_job` with `<outdir>/gen-<k>.done`; one LLM recipe per long job. The marker's second line names the arm (`arm <sha12>: <n> of <requested> rows`, then `short` and `stopped` when they apply); the arm's `stats.json` has the details and the spend (`usd`), and its calls are logged in `<outdir>/gen/llm/<sha12>/`. A recipe stopped by a cap (`stopped: "api budget"`) still makes its arm, with fewer rows.

   b. Filter each arm: rules, duplicates and leaks, distance, CLLM (keep CLLM on: unfiltered LLM rows have been found to hurt):

   ```
   dgen filter --brief <outdir>/brief.json --arm <outdir>/gen/arms/<sha12>
   ```

   It writes `verified.jsonl` (the rows kept), `quality_report.md`, `quality_summary.json` and `sample.jsonl` in the arm. Read the report: the rows each check removed, `leak_val` (copies of valset inputs), the distance to real rows.

   c. When the task has `features.constraints`: repair the current trainset's rows (generated rows are already repaired and checked by dgen):

   ```
   dset repair --task <task.json> --rows <trainset>/rows.jsonl --out <outdir>/work/repaired.jsonl
   ```

   Exit code 1 means some rows still break a rule after repair (the summary's `left` names them, and the rows are written all the same): name them in the record and the hand-back's `notes`.

   d. When the plan names near duplicates and the current trainset has no prompt-variant rows: drop them, keeping the first row of each group:

   ```
   dgen neardup --brief <outdir>/brief.json --rows <rows> --write <outdir>/work/neardup.jsonl
   ```

   e. When you chose prompt variants: add them, the last of the steps that rewrite rows (a `dset repair` or `dgen neardup` after it breaks the variants, and registration refuses the trainset):

   ```
   dgen variants --task <task.json> --rows <rows> --specs <outdir>/gen/specs-<k>.json --share <F> --seed <S> --out <outdir>/work/variants.jsonl
   ```

   f. When c repaired rows (its `repaired` > 0), d dropped rows (its `dropped` > 0) or e ran: write `<rows>` as the base trainset to grow from (`--mode drop` also drops repeated inputs and inputs with conflicting labels; when e ran, add `--variants <outdir>/gen/specs-<k>.json`):

   ```
   dset check --task <task.json> --rows <rows> --variants <trainset>/manifest.json --write <outdir>/work/base --mode drop --round <round> --parent <trainset_id>
   ```

   g. Grow the new trainset: the base (`<outdir>/work/base` when f ran, then also `--label-method "<the current trainset's label_method>"`; else `<trainset>`), one `--with` per arm's `verified.jsonl`, and `--add <N>` when you also draw N pool rows:

   ```
   dset grow --task <task.json> --pool <pool> --trainset <trainset> --parent <trainset_id> --with <outdir>/gen/arms/<sha12-a>/verified.jsonl --with <outdir>/gen/arms/<sha12-b>/verified.jsonl --round <round> --out <outdir>/trainset
   ```

   The manifest's `changes` names each `--with` file, whose `arms/<sha12>/` names its recipe. The quality gate (`quality.checks`) holds `max_synthetic_share` when the task sets it; add `--checks <outdir>/checks.json` for the task's checks `dset` does not compute.

   h. Report the rows by source, then validate and hand back:

   ```
   dset check --task <task.json> --rows <outdir>/trainset/rows.jsonl --variants <outdir>/trainset/manifest.json --by-source
   PYTHONPATH=<repo root> python3 -m rsi validate trainset <outdir>/trainset --task <task.json>
   ```

   `by_source` counts the rows by source, label source and label; `synthetic_share` is the generated rows' share. Hand back `trainset` and `record`.
5. **Record** (see "Experiment records"): for each recipe its `sha12`, name, method, the rows asked for, generated and kept by the filter, `short` and why (`stopped`), and its spend; the score-pool hours; `synthetic_share`. The record's `result` is `inconclusive`: this round's ② Train & tune and ⑤ Judge & decide judge the new trainset.

Other changes, alone or with the steps above (each through `dset`):

- Thin coverage (too few rows of some kind, a trainset too small): draw more pool rows, `dset grow --task <task.json> --pool <pool> --trainset <trainset> --parent <trainset_id> --add <N> --round <round> --out <outdir>/trainset`. It draws pool rows whose id and input are both not in the current trainset, stratified by the rule.
- Label noise (several labels for one input, duplicate rows): first look at `dset check --task <task.json> --rows <trainset>/rows.jsonl --against <valset>/rows.jsonl` (duplicates, conflicts and overlap with the valset), then write the cleaned trainset with `dset check --task <task.json> --rows <trainset>/rows.jsonl --write <outdir>/trainset --mode merge --round <round> --parent <trainset_id>`: merge folds the rows of one input into one row, with target the mean weighted by `n_obs`; `--mode drop` deletes all rows of a conflicting input and keeps only the first row of a duplicate input.
- With `feedback` carrying real outcomes: write the outcomes as full rows (`meta.label_source` is `outcome`, which the task's `data.label_sources` must allow; `question` as in round 1; ids not repeating existing ones) into `<outdir>/feedback_rows.jsonl` and give it to `dset grow` as one more `--with <outdir>/feedback_rows.jsonl`.

`dset grow` and `dset check` with `--write` compute the quality gate as they write the new trainset, into the manifest's `quality` and `quality_report.json`; compute the task's checks that `dset` does not into `<outdir>/checks.json` and add `--checks <outdir>/checks.json` to the command. A failed gate is still written and handed back as it is (see "Gates"). No training: whether the new trainset is better is judged by this round's train module and evaluation (see "Module metrics").

**Fixed rules.**

- This purpose never gets the evalset's or the testset's inputs or labels (the refresh purpose keeps the earlier evalsets' `inputs.jsonl`, which it needs for non-overlap). `dgen filter` checks generated rows for leaks against the valset inputs, the pool and the trainset; the framework checks generated and variant rows against the evalset and testset inputs when it registers the trainset. A match fails the trainset's quality gate as `generated_matches_heldout` and comes back as a quality-gate return whose feedback names the trainset row ids to drop (never the held-out inputs). Write the files those rows came from without them (e.g. `python3 -c 'import json, sys; drop = set(sys.argv[3:]); open(sys.argv[2], "w").writelines(l for l in open(sys.argv[1]) if json.loads(l)["id"] not in drop)' <arm>/verified.jsonl <arm>/verified-<k>.jsonl <id> <id>`), grow again with those files into a subdirectory never registered before (`<outdir>/trainset-<k>`) and hand that back.
- Data-LLM spend (generation, review, paraphrases) stops at `budget_left.api_usd`: dgen refuses to start a call once the dispatch's `api_usd` lines reach it. It is a separate account from your own session's cost.
- Verbatim request text (`input.verbatim`) is never changed: generation never edits it and variants keep it byte for byte. Never edit rows by hand.
- All generated and paraphrased text is in English.
- Labels follow the seed; generated rows are never seeds; generated and variant rows go only into trainsets.

### Evalset refresh: refresh

On an approved refresh, the new evalset is drawn from the corpus, avoiding rows already used. The corpus holds the labels of all rows (the sealed testset's included): use it only through the command below; never open it yourself and never look at the rows of the sealed testset or earlier evalsets. `dset refresh --task <task.json> --corpus <corpus> --out <outdir>/evalset --round <round> --exclude <evalset_inputs> --exclude <trainset>/rows.jsonl --exclude <valset>/rows.jsonl`. Give `--exclude` once for every `evalset_inputs_<id>` in the brief's `inputs` (the `inputs.jsonl` of each earlier evalset, unlabelled), plus the rows of the current trainset and valset. `dset` recomputes round 1's allocation by the rule fixed in the task, takes from the evalset's range the rows not taken by any set, the pool or these files, and draws `sizes.evalset` rows. When too few rows are left it reports an error: the rule is fixed and cannot be changed; stop and hand back `questions`. Validate with `PYTHONPATH=<repo root> python3 -m rsi validate evalset <outdir>/evalset --task <task.json>` and hand back `evalset` and `record`; after the hand-back keep no copy of the corpus or of the new evalset's labels. `dset` refreshes only the evalset; when the valset or the sealed testset needs a refresh, build it yourself in the format of "Outputs".

## Module metrics

This round's evaluation against the current best version: once the new trainset is registered, this round's ② Train & tune trains candidates on it, and ⑤ Judge & decide compares the candidate sent for evaluation with the current best version (trained on the old trainset) on the evalset; the delta of the primary metric, its interval and the promote-or-keep decision go into this round's `evaluation`, recorded by judge. This module does not train and does not measure this metric; the `result` of the `record` it hands back has no numbers (see "Experiment records"). At the next dispatch it learns how the previous trainset did this way: this module's `record`s of earlier rounds say what was changed then and why; read the `plan` that opens this round (judge wrote the conclusion on the new trainset from the last round's evaluation). Round 1 has no old trainset and so no such metric: round 1 hands in a reproducible split (script, rule, `dset` summary) and the quality gate.

## Experiment records

Every dispatch hands in one `record` (fields in [record.md](../../docs/interfaces/record.md)), in `<outdir>/record/`, validated with `PYTHONPATH=<repo root> python3 -m rsi validate record <outdir>/record --task <task.json>`. `module` is `data`, `owner` is `rsi-data`, `automation` is `automated`.

- Round 1 sets:
  - `failure`: what the raw data is and what the task wants (no sets yet).
  - `hypothesis`: the split rule and **why it splits this way**: for each key you set (`by`, `key`, `ranges` or `fractions`, `sizes`, `stratify`, `unit`, `seed`), one sentence of evidence from the data (e.g. the time span, the rows and positives per segment, group sizes); keys the task author wrote are marked as used as written.
  - `action`: what the preprocessing script does (which files it reads, how it builds rows, what goes into `meta.extra`, which fields it drops), the command that runs it, the check of the row count and each label's row count against `data.rows.expect`, the `dset` commands run.
  - `result`: `metric` is `val <primary metric>`, `before` and `after` are null (no comparison), `conclusion` is `inconclusive`.
  - `knowledge`: facts of the data (the share of positives, changes over time, duplicates and conflicts, the number of `state_id`s shared across sets) and hints for later rounds.
  - The manifest's `notes`: the `dset` summary: each set's rows, `key` span, rows in range, rows left out for overlap; pool and unused rows, `shared_state_ids`, the quality gate. The label distributions (rows per label) of the evalset and the sealed testset go neither into the record nor into the `notes` of `handback.json`: the `dset` summary and the corpus's `split_report.json` have them, so leave them out when copying (`dset` no longer writes them into the `notes` of those sets' manifests).
- Later rounds' trainset: `failure` is the issue the plan attributes to data, with the diagnosis's error counts by kind and its findings; `hypothesis` is why each recipe, size and prompt variant should work, each with its evidence (a finding or an issue of the plan); `action` is the `dgen` and `dset` commands run and, for each recipe, its `sha12`, name, method, the rows asked for, generated, kept by the filter (and what each check removed), `short` and why (`stopped`), and its spend (`usd` of the arm's `stats.json`), plus the score-pool GPU hours, the rows added and removed and `synthetic_share` from `dset check` with `--by-source`; `result` is `{"metric": "eval <primary metric>", "before": null, "after": null, "conclusion": "inconclusive"}`: whether it is better is judged by this round's ⑤ comparing it with the current best version on the evalset, which this module does not measure, so the numbers are null and the conclusion is `inconclusive` (`result` may have no other fields); the manifest's `notes` say "tested by this round's ② Train & tune and ⑤ Judge & decide", then give the `dset` summary and the quality gate.
- refresh: `action` says which files were excluded, how many unused rows the range still has and how many were drawn; `notes` give the `dset` summary but not the new evalset's label distribution (nor do the `notes` of `handback.json`).
- `artifacts`: the related registered ids (the brief's `ids`); this hand-back's artifacts are not registered yet and go into `action`.

## Long jobs

This module's long jobs: preprocessing of large data (expected to take more than 10 minutes), large batch labelling (e.g. calling a judge model) and, in later rounds' trainset dispatches, `dgen score-pool` (GPU) and every LLM recipe of `dgen generate` (and `dgen paraphrase` when run with `--marker`). dgen's long jobs write `<marker>.pid` themselves (their own pid, in their own process group) and the completion marker last, also when they fail or are stopped, and bill their spend into the brief's `spend_file`: start them as in step 2 of "Later rounds: trainset" (markers `<outdir>/score-<k>.done`, `<outdir>/gen-<k>.done`, `<outdir>/para-<k>.done`), wait until the pid file is written, then hand back `long_job`; an LLM recipe without `--marker` is refused. This module does not train, so it has no training long jobs. During a long job you may write the brief's progress file `<outdir>/progress.json` (format in [progress.md](../../docs/interfaces/progress.md)), which the progress page shows; without a long job, do not write it.

Hand-back of a long job: when it is expected to take longer than the brief allows, start it in the background, write `handback.json` at once with `long_job` as `status` and the absolute path of the completion marker as `marker`, then end the session; do not poll or wait. If the completion marker is already there when you would hand back `long_job` (the long job ended before your hand-back, e.g. one a previous session started): do not hand back `long_job`. The engine only accepts a marker written after this launch; an earlier marker never counts as present and the run would wait forever. Read the results, finish the work, then hand back. When the job ends, succeeded or failed, it must write the completion marker, whose first line is `ok` or `failed`. When the marker is `ok`, the engine has the same session go on (`feedback-<k>.md` starts with `# Long job finished`): it reads the results, writes the artifacts and hands back with `ok`; when the marker is not `ok`, this dispatch is recorded as failed.

Before handing back `long_job`, write `<marker>.pid` next to the completion marker: the first line is the long job process's own pid, the second its start time (Unix seconds, `date +%s`). The pid must be written by the long job itself, e.g. in a shell `sh -c 'printf "%s\n%s\n" $$ "$(date +%s)" > <marker>.pid; exec <command>' > <log> 2>&1 &` (`exec` makes the command keep this pid), and in Python write `os.getpid()` and `int(time.time())` as the job starts; never use the background pid the shell gives instead, which may be a wrapper process and not the long job itself. Preferably run the long job in its own process group (e.g. Python's `subprocess.Popen(..., start_new_session=True)`). Write `handback.json` only after `<marker>.pid` is written. When the run is stopped, the engine checks by this file that the process is this long job, then terminates it (the whole process group); without this file it cannot terminate it and can only list it as possibly still running, for the user to end by hand.

Use a new completion marker for every long job: `<k>` is the count of this kind of long job in this dispatch (1 the first time, then 2, 3, … on redos); preprocessing uses `<outdir>/prep-<k>.done`, other long jobs `<outdir>/<name>-<k>.done` the same way. Run `rm -f <marker> <marker>.pid` before starting, so the marker and the pid file both start clean: the engine only accepts a marker whose modification time is not earlier than this launch; an earlier marker left at the same path does not count as this long job's end.

For example, to run the preprocessing in the background (sh in its own session, so `$$` is the process group id):

```
rm -f <outdir>/prep-<k>.done <outdir>/prep-<k>.done.pid
python3 -c 'import subprocess, sys; subprocess.Popen(["sh", "-c", sys.argv[1]], start_new_session=True, stdin=subprocess.DEVNULL, stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)' 'printf "%s\n%s\n" $$ "$(date +%s)" > <outdir>/prep-<k>.done.pid; cd <outdir>/corpus && python3 preprocess.py > <outdir>/prep-<k>.log 2>&1 && echo ok > <outdir>/prep-<k>.done || printf "failed\npreprocessing failed, see prep-<k>.log\n" > <outdir>/prep-<k>.done'
```

Wait until `<outdir>/prep-<k>.done.pid` is written (e.g. `until [ -s <outdir>/prep-<k>.done.pid ]; do sleep 1; done`), then write `handback.json` (`status` is `long_job`, `marker` is `<outdir>/prep-<k>.done`).

Check-ins: when the task sets `flow.checkin_minutes`, during a long job the engine sends the same session feedback starting with `# Check-in` every that many minutes (not a return; their number is capped by `flow.max_checkins`). Check whether the long job is still there and making progress: the process (the pid on the first line of `<marker>.pid`, `ps -p <pid>`), the log (e.g. `<outdir>/prep-<k>.log`; for an LLM recipe also `<outdir>/gen/llm/<sha12>/gen/llm_calls.jsonl`), `<outdir>/progress.json` when written, the disk. When all is well, hand back the **same** marker as `long_job`, without waiting. When the process is gone without writing the marker, or something failed and must be rerun: first end what is still running (`kill -- -<pid>`: the whole process group), then restart it as above with the next `<k>`, and hand back the new marker.

whether it is better is left to train and judge: the A/B training of the old and new trainsets is gone (the `ab-<k>` draft candidates and markers), and the brief no longer gives the train command; the `result` of a later round's trainset `record` is null and `inconclusive`, tested by this round's ② and ⑤; the module metric is now this round's evaluation against the current best version. 1.1 (2026-11-25) every long job uses a new completion marker (`prep-<k>.done`, `ab-<k>.done`), deleting the old one before it starts; the A/B candidates live in `<outdir>/ab-<k>-old` and `ab-<k>-new` (progress written to `<outdir>/progress.json`); how to do a check-in; `dset` no longer writes the label distributions of the evalset and the sealed testset into the `notes` of their manifests, and the hand-back's `notes` do not have them either. 1.0 (2026-11-25) the flow starts with the data module: in round 1's sets you write the preprocessing script (registered as the corpus) and set the split rule from the data (recorded as a new version of the task definition, with no approval), and `dset` splits off the four sets and the training pool pool; later rounds grow or shrink the trainset from pool, and refresh draws a new evalset from the corpus.
- Known limitations: `dset` refreshes only the evalset; the corpus and pool are read whole into memory at registration and when splitting; raw data is supported only as local paths, and no sha256 is computed over the raw data; registration does not run the preprocessing script (the rerun audit is the operator's, by the manifest's `command`); the read-deny list only stops the agent's own file tools, and the isolation relies on convention and the operator's `chmod 000`; a workspace without a complete rule cannot use refresh; `dgen neardup` compares every pair of rows (slow on very large files); prompt variants are added to the base trainset's rows, not to the rows generated in the same dispatch.

## Common mistakes

| Mistake | Consequence | Right way |
|---|---|---|
| Reading the evalset, the sealed testset or the corpus after handing them in, or keeping copies of their labels | Labels of the evalset and the sealed testset leak into later judgements; the evaluation is no longer independent | Keep no copies and read nothing after the hand-back; refresh uses only the corpus the brief gives and the unlabelled `inputs.jsonl` |
| Reading `data.sources` after round 1's sets (in the trainset and refresh dispatches from round 2 on) | The raw data is on these dispatches' read-deny list; labels read there may leak into new sets, and once the corpus is registered it is unreadable anyway | Draw new trainsets from `pool` and new evalsets from `corpus` |
| Writing split or sampling code yourself, or editing the sets `dset` wrote by hand | The sets cannot be reproduced by the rule, there is no summary to check, and refresh cannot recompute round 1's allocation | Split only with `dset`: the rule goes into `split.json` and sets carries it out |
| A preprocessing script with nondeterministic output (writes times, no fixed seed, unsorted, depends on the order files are listed in) | The sha256 of the rerun audit does not match; the sets cannot be traced back to the registered script | The same input writes the same bytes: sort by id, write no times, fix seeds; run it twice before handing back and compare the sha256 |
| Leaving labelled intermediate files outside the output directory (e.g. /tmp), or labelled rows outside the corpus and set directories | The labels are still there after the hand-back, readable by later dispatches | Write labelled rows only into the corpus and set directories; delete temporary files before handing back |
| Changing a split key the task author wrote (replacing it in `split.json`, or editing `task/task.json` by hand) | `dset` reports a `data.split.<key>` conflict; the engine does not register a hand-edited task version | Use the author's keys as written; when that does not work (too few rows, a gate that cannot pass), hand back `questions` |
| Running the script outside the corpus directory, or writing its output to an absolute path | A rerun by the manifest's `command` cannot write the same file | Run it in the corpus directory, writing to the relative path `rows.jsonl` |
| The row count or a label's row count does not match `data.rows.expect` | The corpus registration is refused: preprocessing lost rows or got labels wrong | Fix the script and rerun it; do not change `expect` |
| Treating the same `state_id` across sets as an error and deleting those rows | Rows thrown away for nothing; this is allowed and only reported | Write the count into the `record`; set `unit: state_id` only to simulate wholly unseen objects |
| `sizes.evalset` unset or equal to the rows in the evalset's range | Later refreshes have no unused rows | Leave room in the evalset's range |
| Writing generation, filtering or assembly code yourself, or editing generated rows by hand | The rows cannot be traced to a recipe, the filters and the held-out check are bypassed, and verbatim text may change | Choose recipes (the JSON) and run `dgen generate`, `dgen filter` and `dset grow`; nothing else touches rows |
| Running `dset repair` or `dgen neardup` after `dgen variants` | Variant rows are no longer rewrites of their seeds (or lose them); registration refuses the trainset | Repair, then near duplicates, then variants last (step 4) |
| Running `dgen score-pool` or an LLM recipe in the foreground | The session blocks for hours, or dgen refuses an LLM recipe without `--marker` | Start it in the background with a new marker and hand back `long_job` |
| Running an identical recipe again to get new rows | dgen returns the existing arm (`existing: true`), no new rows | Change the recipe's `seed` (or `max_usd`) |
| Generating more rows than `max_synthetic_share` allows | The trainset fails the quality gate and is sent back | At most T·s/(1−s) generated rows, counted after the filter |
| Merging several arms into one file, or leaving an arm out of `--with` | The trainset's `changes` no longer names each recipe's `arms/<sha12>/` | One `--with` per arm's `verified.jsonl` |
| `dset` says already exists | The previous output is still there, and `dset` does not overwrite | To redo a split whose corpus is not registered yet: delete `task/` and the five set directories under `<outdir>`, and the `manifest.json` and `split_report.json` in the corpus directory (keep the script and `rows.jsonl`), then run again. When the corpus is registered, split again in `redo/` as in "Continuing", never touching the registered corpus. A run that stopped half way (the corpus's `manifest.json` not written yet) leaves only the new directories already in place, the `split_report.json` in the corpus and entries starting with `.dset-`: delete them and run again |
| grow, check's `--write` or refresh says already exists | That output directory already exists | Not registered yet: delete it and run again; already registered (the copy left in the output directory): use a subdirectory name never registered before, e.g. `<outdir>/trainset-2`, `<outdir>/evalset-2`, and list that name in the hand-back |
| Going on using the evalset or the sealed testset after handing them in, or mixing their samples into the trainset | Evaluation results can no longer be trusted | Trainsets come only from `pool` and from rows written from feedback; registration also refuses overlaps |
| Training yourself to test a new trainset (calling the train command, trsi or other training code) | The data module becomes the judge of its own data; the training is not counted in the budget and duplicates ②'s search; the candidates it makes are refused at registration | Do not train: the `record`'s `result` is null and `inconclusive`; this round's ② Train & tune and ⑤ Judge & decide judge whether it is better |
