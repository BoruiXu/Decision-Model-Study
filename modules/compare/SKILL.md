# rsi-compare: compare module (③ Compare, a code module)

③ Compare trains baselines once per trainset and reports the round's candidate against each of them on the valset. It is a report only, never a gate, and it is on only when the task definition has a `compare` section. It is a *code module* (`rsi.flow.CODE_MODULES`): no agent works on its dispatches. The engine runs a fixed command through the code runner (`rsi/runners/code.py`) and keeps the whole dispatch protocol of the agent modules: the brief, `handback.json`, registration, the two-part hand-back, long jobs with a completion marker, check-ins, returns, a stop. This file is the command's contract. The engine still builds the prompt of a first launch from it, as for every module, and the code runner ignores that prompt. Under `rsi run --runner mock` every module is the mock script `<mock dir>/<module>.py`, compare included (`examples/mock_modules/compare.py`, one baseline: the trainset's class prior), so flow simulations stay self-contained.

## Command

The command is the task definition's `runner.code.commands.compare` (an argv list, for tests and unusual setups), else `<repo root>/modules/compare/run`. `run` is a standard-library launcher: it reads the brief and execs `<python> -m compare run <its arguments>` with `PYTHONPATH=<repo root>/modules/compare:<repo root>/modules/common:<repo root>/modules/train:<repo root>` (`modules/train` for `trsi`, whose card choice and `model.predict` code the GPU baselines use), where `<python>` is the brief's `compare.python`, else `resources.onejev.python` (an absolute path, or a name on PATH). That interpreter needs numpy, scikit-learn, xgboost (or lightgbm) and pyyaml (for `trsi`, which the GPU baselines import): `modules/common/install_deps.sh --python <python>` installs and checks them (`modules/train/install_env.sh` runs it for the ojh venv). Without either setting `run` writes `handback.json` with status `failed` and the notes `compare needs a Python with scikit-learn: set compare.python or resources.onejev.python` (with one that is not an executable, notes that name it), so the engine's decision applies. Every launch of a dispatch runs

```
<command> --brief <outdir>/brief.json --outdir <outdir> --mode <mode> [--feedback <outdir>/<feedback file>]
```

- `--brief`: the dispatch's `brief.json`, built by code from the workspace (rebuilt before every launch after the first).
- `--outdir`: the dispatch's output directory, absolute; it is also the working directory.
- `--mode`: the launch mode of the dispatch record (see "Modes").
- `--feedback`: given whenever the dispatch has a feedback file for this launch: from the second launch on `feedback-<n>.md` (why this launch happens) or `history-<n>.md` for `fresh`, and also at the first launch of a dispatch a decision made (`feedback-1.md`, why it was made).

A relative path as the command's first word is taken from the repository root (the command runs in the output directory); a bare name is looked up on PATH. The command runs in its own process group; its stdout and stderr go to `agent-<n>.log` in the output directory, and a small shell writes its own pid to `agent-<n>.pid` first and the command's exit status to `agent-<n>.exit` at its end (`<n>` is the launch number). When `rsi run` is killed while the command works and is run again, the next run finds the command by the pid in the dispatch record, else by `agent-<n>.pid` (a process whose command line holds `--outdir <outdir>` and that started with this launch), and waits for it; it never launches it a second time. A command still running after `runner.code.timeout_s` seconds (default 21600, 6 hours) is terminated and the dispatch fails. When the command's executable does not exist the launch fails at once (exit code 127, the log says which command).

The command is idempotent: every mode reruns it, and it reads what earlier launches left in the output directory (and the registered baselines the brief lists) instead of redoing finished work. It exits 0 once `handback.json` is written; a crash without `handback.json` fails the dispatch, whose log the engine quotes.

## Modes

| Mode | When | What the command does |
|---|---|---|
| `first` | The dispatch's first launch | Trains each baseline of `compare.baselines` that cannot be reused, scores it, and hands back the baselines; when every baseline is reused, it hands back the comparison at once. GPU baselines run as one long job (see "Long jobs") |
| `resume` | A return: the last hand-back failed or registration refused part of it (`feedback-<n>.md` says why) | Runs again from what the output directory holds and hands back what is still missing |
| `fresh` | The engine opened a new session (`history-<n>.md`); a code module has no session to lose, so this is rare | The same as `resume` |
| `continue` | The long job's completion marker says `ok` (`feedback-<n>.md` starts with `# Long job finished`) | Collects the long job's results and hands back the baselines |
| `followup` | The baselines are registered (`feedback-<n>.md` starts with `# Continue: the second part of the hand-back`; not a return) | Reads `registered-<n>.json` beside the feedback (`[{"dir", "kind", "id"}]`: each handed-back subdirectory and its registered id), adds the reused baselines with their ids from the brief, and hands back the comparison |
| `checkin` | A check-in of the long job (`feedback-<n>.md` starts with `# Check-in`; only with `flow.checkin_minutes`) | Looks at the job's pid (`<marker>.pid`): still running, hands back `long_job` again with the same marker; its marker there, collects as `continue`; gone without a marker, hands back `failed` ("the GPU job <pid> ended without its marker") |
| `answer` | Never: a code module asks no questions | - |

`first`, `resume` and `fresh` fit the CPU baselines inline and start the GPU ones as one long job (see "Baselines" and "GPU baselines"): with a GPU job they hand back `long_job`, else the new baselines with `ok`; `continue` hands back every new baseline of the dispatch, CPU and GPU, in one hand-back. When there is no new baseline (every baseline reused or skipped, or once the brief, rebuilt after the registration, lists them all) they hand back the comparison at once (`["comparison"]`, see "The comparison"), and so does `followup`. `resume` while the GPU job of an earlier launch still runs hands back `long_job` with its marker again (never a second job); a GPU baseline whose result an earlier job of the dispatch left is written from it, never run again (one that failed runs again in a new job on `resume` and `fresh`; `continue` takes its failure as its skip reason). For purpose `milestone_compare` see "Milestone scoring": `followup` and `answer` hand back `failed` there.

## Inputs

`brief.json` (and `brief.md`, the same for people) is the only input; read only the paths in its `inputs`. For purpose `compare` they are the `task`, the round's chosen `candidate`, the current `trainset` and the `valset` (rows with labels: baselines are fitted on the trainset, their settings chosen on the valset), the `inputs.jsonl` of the current `evalset` (each baseline predicts it for the judge) and every registered `baseline` (by id) but those with testset predictions (one whose spec and sets match is reused). For purpose `milestone_compare` (the user said yes to the milestone release) they are the best version's `candidate` and `comparison`, each `baseline` of that comparison, the rows of the trainsets and valsets those baselines name (for refits) and the `inputs.jsonl` of the `testset`. The brief also carries `ids` (the set ids to write into manifests), `compare` (the task's settings with their defaults), `policy`, `features` (the adapter as an absolute path), `resources` (`onejev`, `gpu_ids`), `train_command` (for the team's recipe) and `budget_left`. The labels of the evalset and of the testset are never given and never read. A later launch also gets `feedback-<k>.md` or `history-<k>.md` (`--feedback`).

## Outputs

One subdirectory of the output directory per artifact, each with its `manifest.json` (`id` null, `round` and `producer` `compare` as the brief says): a `baseline` per baseline trained or re-predicted (`bl-<name>/`; at the milestone `bl-<name>-test/`, with `predictions_test` and `reused_from`, for each baseline of the comparison), and the `comparison` of the candidate with them on the valset. The GPU job's files are there too: `gpu-<n>.done` (its marker), `gpu-<n>.done.pid`, `gpu-<n>.log` and `gpu-<n>/` (`job.json`, and per baseline `<name>/result.json` with what it predicted; the team recipe's training under `team_recipe/team/`). Each is checked with `PYTHONPATH=<repo root> python3 -m rsi validate <kind> <dir> --task <task.json>` before it is handed back, and every number is computed with `rsi score` (`rsi.metrics`); registration recomputes them all and refuses a mismatch.

Then `handback.json` in the output directory, the format every module hands back: `status` (`ok`, `failed` or `long_job`), `artifacts` (the subdirectory names to register), `marker` (the completion marker's absolute path with `long_job`, else null), `notes` (what was trained, reused and skipped, and why) and `questions`. With `ok` the engine registers the listed artifacts; `failed` gives the reason in `notes` (the engine sends the dispatch back while `flow.max_returns` allows, then skips ③); `long_job` hands back the `marker` of the long job started in the background. `questions` is always `[]`: compare never asks the user (a baseline it cannot run is skipped, and the comparison says why under `skipped`).

## Baselines

The names compare knows are `lr`, `gbdt`, `mlp` (CPU, fitted inline) and `zero_shot`, `few_shot`, `team_recipe` (GPU, one long job: "GPU baselines"). A name of `compare.baselines` that is none of them is not trained; it goes into `skipped.json` with the reason `unknown baseline <name>`.

The CPU baselines:

| Name | Model | Default grid (`COMPARE_GRIDS`) |
|---|---|---|
| `lr` | scikit-learn `LogisticRegression(max_iter=2000)` after `sign(x)·log1p(\|x\|)` and `StandardScaler` | `C` in {0.01, 0.1, 1, 10} × `class_weight` in {null, `"balanced"`} |
| `gbdt` | `XGBClassifier` when `import xgboost` works, else lightgbm `LGBMClassifier`, on the raw features; `learning_rate` 0.05, `subsample` 0.8, `random_state` = `compare.seed` | `n_estimators` in {200, 500} × `max_depth` in {4, 6} |
| `mlp` | scikit-learn `MLPClassifier(early_stopping=True, max_iter=300, random_state=compare.seed)`, preprocessed like `lr` | `hidden_layer_sizes` in {[64], [128, 64]} × `alpha` in {1e-4, 1e-3} |

- The task's `compare.grids.<name>` (an object: parameter → list of values) replaces that baseline's grid; a parameter of the model's fixed ones listed there takes the grid's values.
- Rows: the trainset's real rows (`features.table.real_rows`: prompt-variant rows are skipped), with `compare.max_train_rows` set a stratified seeded subsample of that size (each label its share, rounded by largest remainder). The label `y` is each row's hard label (`rsi.metrics.hard_label`).
- Features: `features.table.Featurizer` with the task's adapter (`features.adapter`, else the generic model view), its columns fixed on those rows; a column that determines a label (the featurizer's leak check) stops every CPU baseline, with the reason in `skipped.json`.
- The grid point: each point is fitted and scored by the task's primary metric (`rsi.metrics.score`) on the valset's real rows; the best in the metric's direction is kept, a tie going to the first point in grid order (the grid's keys as written, the last varying fastest). Every seed is `compare.seed`, so a refit predicts the same.
- A baseline that cannot be fitted (e.g. the trainset rows have one label only) is skipped with the reason; the others go on.

Each new baseline is `bl-<name>/`: `predictions_val.jsonl` (every valset row), `predictions_eval.jsonl` (every evalset input), each row's `decision` the most probable label and `uncertainty` 1 minus its probability, and the manifest: `spec` (the model, the library that fits it and its version, its fixed parameters, the grid, the seed, `max_train_rows`), `spec_sha256`, `config` (`grid_point`, `val_scores` in grid order, `train_rows`, and `library` for `gbdt`), `features` (the featurizer's signature), `metrics_val` (the primary and the task's other metrics `rsi` computes, on the valset rows), `cost.compute_hours` 0, `testset_id` null and `reused_from`. It is checked with `rsi validate baseline` (`rsi.artifacts.validate_artifact`) before it is handed back.

**Reuse.** `spec_sha256` is the sha256 of the canonical JSON of the name, the resolved spec (with the library and its version: after a change of scikit-learn, xgboost or lightgbm, or a switch between the last two, a CPU baseline is fitted again, never reused or re-predicted), the features key (`features_key`: `FEATURES_VERSION` and the sha256 of the adapter file; null for a GPU baseline), the module's version and the policy key (`policy_key`: the task's `policy` section and `DPOLICY_VERSION`; null without the section). A registered baseline of the brief is reused when its `spec_sha256`, `trainset_id` (any for `zero_shot`), `valset_id` and `evalset_id` match: nothing is trained, and the comparison names it. When only the evalset differs (a refresh) it is re-predicted: a CPU baseline is refitted (deterministic) and handed back as a new baseline with `reused_from` its id. Anything else is trained. Within one dispatch, a `bl-<name>/` an earlier launch left in the output directory is kept when its `spec_sha256`, sets and `reused_from` match and it is valid.

**Decision policy.** With the task's `policy` section every baseline gets a `policy.json` and its predictions carry it: `lr`, `gbdt`, `mlp`, `zero_shot` and `few_shot` fit it on their valset predictions as a candidate does (`dpolicy`, `preds.with_policy`); `team_recipe` keeps its packed candidate's, which its `model.predict` applies; a re-prediction or the milestone applies the source baseline's recorded policy to the new scores (docs/interfaces/compare.md).

**`skipped.json`** in the output directory: baseline name → why it was not compared (an unknown name, a GPU baseline the compute budget does not cover or that failed, a baseline that could not be fitted). Every run of modes `first`, `resume`, `fresh` and `continue` rewrites it; the comparison copies it into `skipped`.

## The comparison

`comparison/` (`compare/report.py`): the brief's `candidate` against each baseline of the round on the valset rows, every number with `rsi.metrics` from the prediction files, as registration recomputes it (docs/interfaces/compare.md): `metrics_val` (the candidate's `predictions_val`, which carry its decision policy, and each baseline's), `deltas_val` (the paired cluster bootstrap of the primary metric, candidate minus baseline, clusters from the valset's `inputs.jsonl`, the task's `metrics.ci` settings; `rsi score --compare` prints the same `delta`), `strongest` (the best primary metric on the valset, a tie to the alphabetically first name) and `skipped` (`skipped.json`, plus a baseline on other sets than the candidate's). The baselines are those registered (followup: `registered-<n>.json`) and those reused (their ids from the brief), in the order of `compare.baselines`; a baseline's predictions are read from the brief's copy, else from this dispatch's `bl-<name>/` (registration copies it unchanged). `report.md` gives the candidate against its strongest baseline, the table (model | primary metric | other metrics | Δ candidate − model [interval]) and the skipped lines. A comparison of no baseline (all skipped) is handed back too, `strongest` null. The comparison is a report: the judge reports the same baselines on the evalset (`baselines_eval`), and nothing gates on it.

## GPU baselines

`zero_shot`, `few_shot` and `team_recipe` run in one long job, never inline (`compare/gpu.py`):

| Name | What it is | GPU hours estimate |
|---|---|---|
| `zero_shot` | The base model `compare.zero_shot.base` (null: `resources.onejev.default_config.base`), untrained, scored on each row as it is | `compare.gpu_hours.zero_shot` |
| `few_shot` | The same scoring with `compare.few_shot.base`, each row's `question.instructions` prefixed with k labelled trainset examples | `compare.gpu_hours.few_shot` |
| `team_recipe` | `compare.team_recipe` trained by the train command (`resources.train_command`, else `modules/train/train`; the brief's `train_command`), then its packed `model.predict` on the evalset inputs | `compare.gpu_hours.team_recipe` when written, else `resources.onejev.estimate[<its base>]`; a re-prediction (only the evalset changed), or a training an earlier job of the dispatch finished whose prediction failed, `compare.gpu_hours.predict` |

- **Budget.** A GPU baseline runs only when `budget_left.compute_hours` is null or at least its estimate; each one that runs takes its estimate from what is left, in the order of `compare.baselines`. Otherwise it is skipped with the reason `needs <e> GPU hours, <r> left` (with a budget and no estimate: `no GPU-hour estimate …`). `team_recipe` without `compare.team_recipe`, or `zero_shot`/`few_shot` without a base, is skipped with the reason.
- **Scoring the base model** goes through ojh's own scorer, never a copy: compare writes a scoring directory with `predict.json` (the scoring settings, `base_scoring`: the kwargs trsi scores a candidate of the base's default recipe with, `trsi.pack.score_kwargs` on that recipe's flags, built as ojh builds a run's (the catalog's one-card default as trsi takes it for recipe null, else its first default recipe; its `onejev` flags, `full_finetune`, `fsdp`, and a LoRA recipe's `lora` fields as `lora_<field>`; e.g. a full fine-tune without FSDP scores in float32 with autocast, a LoRA recipe with `lora.autocast: true` with autocast), so a zero-shot or few-shot baseline and a candidate of that base are scored alike; `multimodal` from `<ojh repo>/catalog/bases/<base>.yaml`; the machine config's `env`; the recipe and kwargs are in the baseline's `config.scoring`), `trsi.pack.PREDICT_PY` as `predict.py` with its `predict` entry, and `model/` linking `<model_dir>/<base>` (`model_dir` from `resources.onejev.machine`; the ojh repo is the parent of the `.venv` of `resources.onejev.ojh_bin`), and runs `predict` with `CUDA_VISIBLE_DEVICES` set to the idle card (under 1 GiB in use) of `resources.gpu_ids` with the least memory in use (`trsi.harness._idle`; it waits up to 10 minutes for one). `compare.gpu.score_base` documents what it found in ojh.
- **The few-shot prompt**: `"Here are <k> labelled examples.\n\n" + examples + "\n\nNow answer for the input below.\n\n" + instructions`, each example `"Example <i>:\nInput: <the state as JSON, sort_keys, cut to max_example_chars with ' …'>\nAnswer: <label>"`. The examples are real trainset rows (`features.table.real_rows`): k/2 per label for a binary task (rounded up for the positive), stratified by label otherwise, drawn with `random.Random(compare.seed)`, in trainset order, the same for every row; their ids are in the baseline's `config.examples`. Everything else in the row is unchanged.
- **The team recipe** is trained with every argument of the train command's contract (`trsi` is imported first, so a missing library fails before any training) (`--task <job dir>/team_recipe/team/task.json`: a copy of the task whose `search_space` also allows the recipe's base, recipe, overrides, seed and max_steps, since packing checks the candidate's `config_request` against it, `--trainset`, `--trainset-id`, `--valset`, `--valset-id`, `--config` (the recipe; a null base takes `resources.onejev.default_config.base`, a null seed the train command's default), `--config-source default`, `--round`, `--producer train`, `--out <job dir>/team_recipe/team/cand`, `--marker <job dir>/team_recipe/team/train.done`) and `PYTHONPATH=<repo root>`. Its `predictions_val` is the packed candidate's; the baseline keeps the model: `model` `{"location", "predict"}` and the candidate's files but its manifest and predictions, hard-linked into `bl-team_recipe/`. Its GPU hours are the candidate's `cost.compute_hours` plus the evalset prediction. A training that finished is never repeated in the dispatch: when a later step fails (no idle card, the prediction runs out of memory), the next job of the dispatch (`resume`) uses that job's candidate again (same item, its `train.done` ok).
- **Spend.** Every GPU baseline the job runs appends `{"at", "source": "compare:<name>", "compute_hours"}` to the brief's `spend_file`: the time it held a card (from the card's pick to the end of its scoring or prediction; never the wait for a card, so one that got no card charges 0; a failed training its wall-clock time on one card); a failed one has a `note`. A finished team-recipe training has its own line (its candidate's `cost.compute_hours`, `note` "the training …"), written as soon as it finishes, so it is billed once even when the job is stopped later or a later job uses it again; the baseline's line then bills only its prediction. The baseline's `cost.compute_hours` is its line's number; for `team_recipe` the training plus the prediction.
- **Re-prediction** (only the evalset changed): `team_recipe` runs the stored `model.predict` of the registered baseline on the new evalset inputs and is never trained again; `zero_shot` and `few_shot` rescore the new evalset inputs. Each copies `predictions_val` from the registered baseline and is a new baseline with `reused_from`.
- **A failure** of one GPU baseline (no idle card, a scoring error, a training that fails) is its reason in `skipped.json` (`<name> failed: …`, with the last lines of the command's output; `OOM: …` when it ran out of GPU memory, `trsi.pack.OOM_RE`); the others go on, and the job's marker still says `ok`. Only an error of the job itself writes `failed`. The output of `predict` and of the train command goes to `gpu-<n>.log` as it comes.
- **Never two jobs.** A job of an earlier launch counts as running unless its process is gone (`rsi.engine.long_job_identity`; a live process it cannot confirm counts as running): `resume` and `checkin` then hand back `long_job` with its marker.

## Milestone scoring

For purpose `milestone_compare` (`compare/milestone.py`) every baseline of the brief's `comparison` is scored on the testset inputs, in one hand-back (the milestone's compare step counts as done once a baseline with `predictions_test` is registered, so none comes later). For each baseline `<name>` (id `<id>`) it writes `bl-<name>-test/`: `reused_from` `<id>`, its `predictions_val` and `predictions_eval` copied, its `spec`, `spec_sha256`, `config` and `features` kept, its sets, `testset_id` the brief's testset and `predictions_test` on the testset's `inputs.jsonl`; no `model`.

- A CPU baseline is refitted inline on the rows of its trainset (the brief's `trainset_rows_<id>`) with its recorded grid point, `max_train_rows` and seed, and must reproduce its registered `predictions_val` exactly; otherwise it is skipped with the reason `refit does not reproduce <id>`.
- `team_recipe` runs its stored `model.predict`; `zero_shot` and `few_shot` rescore (few-shot examples from that baseline's trainset). Both run in the GPU job and write spend lines; milestone scoring only predicts, and the user approved the milestone, so it is not held by `budget_left.compute_hours` (the milestone question says these predictions may use GPU hours beyond the budget).
- The testset's labels are never given or read: the judge computes the testset numbers. With no baseline scored the hand-back is `failed` (the engine's decision applies).

## Gates

None: ③ Compare is a report, and nothing waits on its numbers. What registration checks is the artifacts' validity and their numbers (recomputed with `rsi.metrics`, tolerance 1e-9), the sets each one names, and, for a `baseline` with `predictions_test`, the `use_testset` approval the engine writes at the milestone. A refused or failed hand-back goes back to the command while `flow.max_returns` allows; then the engine skips ③ and goes on to ④ Deliver.

## Long jobs

The GPU baselines run as one long job in the background, never inline. Before starting it, run `rm -f <marker> <marker>.pid` and use a new marker path for every long job (e.g. `<name>-<k>.done`): a marker older than this launch does not count as this job's end. The job itself writes `<marker>.pid` first: its own pid on the first line (`os.getpid()` in Python, `$$` in a shell that then `exec`s the job), its start time in Unix seconds on the second (`int(time.time())`, `date +%s`); preferably it runs in its own process group (`start_new_session=True`). When it ends, succeeded or failed, it must write the completion marker, whose first line is `ok` or `failed`. The command writes `handback.json` with `status` `long_job` and the `marker` only after `<marker>.pid` is there, then exits; it does not wait or poll. If the marker is already there when it would hand back `long_job`, the job has ended: it collects the results and hands them back instead.

Compare's GPU job follows this: `python -m compare gpujob --brief <brief> --outdir <outdir> --marker <outdir>/gpu-<n>.done` (`<n>` one more than any earlier job of the dispatch), started in its own session; it writes `<marker>.pid` first and the marker last, and `run` hands back `long_job` once the pid file is there.

When the marker says `ok`, the engine relaunches the command with mode `continue` (`feedback-<n>.md` starts with `# Long job finished`); a marker that says anything else fails the dispatch. With check-ins on, mode `checkin` (`# Check-in`) comes while the marker has not appeared. When the run is stopped, the engine terminates the job by `<marker>.pid` once it confirms the process is this job.

## Running standalone

The owner runs the command in a sandbox directory, without a workspace or `rsi run`:

1. Copy a dispatch's `brief.json` into the sandbox (or write one with the same fields, its paths pointing at copies of registered artifacts) and set its `outdir` to the sandbox.
2. Run `<repo root>/modules/compare/run --brief <sandbox>/brief.json --outdir <sandbox> --mode first` and read `<sandbox>/handback.json`.
3. After a `long_job` hand-back, wait for the marker, write a `feedback-2.md` and run the command again with `--mode continue --feedback <sandbox>/feedback-2.md`.
4. For the second part, write `registered-<n>.json` (each baseline subdirectory with an id of your choice, e.g. `baseline-0001`) and a `feedback-<n>.md` beside it, then run with `--mode followup --feedback <sandbox>/feedback-<n>.md`.
5. Validate each artifact with `PYTHONPATH=<repo root> python3 -m rsi validate <kind> <dir> --task <task.json>`; do not run `rsi register` or any other `rsi` command.

## Owner and version

- Version: `compare` 1.0.0 (`COMPARE_VERSION` in `compare/__init__.py`; it is part of every baseline's `spec_sha256`, so a new version trains its baselines again). With the task's `policy` section, `DPOLICY_VERSION` (`modules/common/dpolicy/__init__.py`) is part of it too (`reuse.policy_key`): bump it with every change to dpolicy's fitting or applying, and the baselines of policy tasks are fitted again; tasks without a policy section are not affected.
- Changes: 1.0.0 (2026-11-26) the module: the `run` launcher, the CPU baselines `lr`, `gbdt` and `mlp` with their grids, reuse by `spec_sha256` (which records the fitting library and its version) and the sets, `skipped.json`; the GPU baselines `zero_shot`, `few_shot` and `team_recipe` as one long job (budget, spend lines, re-prediction from the stored model), modes `continue` and `checkin`, milestone scoring on the testset inputs, and the comparison (`followup`, or at once when nothing is new).
- Known limitations: `gbdt` runs single-threaded (`n_jobs` 1) so that a refit gives the same bytes; a milestone baseline keeps no `model` (its `reused_from` has it).
- Tests: `<python> -m pytest -q modules/compare/tests` (they skip without scikit-learn; the GPU tests also without pyyaml). The GPU tests need no GPU: a fake `nvidia-smi`, the fake scorer `tests/fake_ojh_score.py` (`COMPARE_TEST_SCORER`, tests only) and a fake train command.
