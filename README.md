# Decision Model RSI framework

This is a general RSI harness that builds a decision model from a one-sentence request and keeps improving it. The user describes the decision task in a prompt (for example "given a transaction, decide whether to allow it, block it or send it to a person"), and an operator session turns the request into a task definition; from there on **the main flow is written in code**: the flow engine in `rsi run` decides the next step from the workspace state, dispatches the modules in the order ① Data → ② Train & tune → ③ Compare → ④ Deliver → ⑤ Judge & decide (each one an agent, except ③ Compare: fixed code that trains baselines and reports the candidate against them, never a gate, on only when the task definition has a `compare` section), validates and registers their hand-backs, decides promotions, moves the rounds on and checks the stop. Every turn of the loop produces a candidate version, and the judge module decides whether it is better than the current best version. An LLM appears in only two places: inside the modules, and at the few decision points the code defines (by default code chooses there by rule). The plan and design of the change are in [docs/plan.md](docs/plan.md), the engine's interface in [docs/interfaces/engine.md](docs/interfaces/engine.md), and the original layered design in [docs/design.md](docs/design.md).

The framework uses only the Python standard library and is not tied to any particular task, machine or model backend; the task definition of each run gives those.

## Layout

| Path | Description |
|---|---|
| `rsi/` | Command-line entry and the code of the mechanical steps (validation, registration, promotion decisions, moving rounds on, the run report, and so on) |
| `rsi/cli.py` | Registration and dispatch of the `rsi` subcommands |
| `rsi/flow.py` | The main-flow state machine: `next_action(ws)` is a read-only pure function that returns the next action (shared by the pages and the engine) |
| `rsi/engine.py`, `rsi/decisions.py` | The main loop of `rsi run` (dispatches, registering hand-backs, returns, long jobs, the run log); decision points, default choices, asking the user and `rsi answer` |
| `rsi/briefs.py` | The module briefs the code builds (`rsi brief`) and the format and checks of `handback.json` |
| `rsi/runners/` | Runners: `claude` (a headless Claude Code session), `mock` (scripts for tests), `manual` (a person fills the output directory), `code` (a code module's fixed command, e.g. compare's; the engine picks it for those dispatches) |
| `rsi/__main__.py` | Lets `python3 -m rsi` work |
| `rsi/schemas/` | JSON schemas of the artifact kinds and the task definition |
| `skills/rsi-orchestrator/` | A thin "operator" skill: drafts the task definition with the user, runs `rsi run`, relays the questions waiting for an answer and records the answers with `rsi answer`, relays progress; it does not decide the flow. `templates/` holds the task description template, a filled-in task definition example and a description of the brief's structure |
| `modules/data/`, `modules/train/`, `modules/deliver/`, `modules/judge/` | One folder per module, each kept by its module owner: the entry skill `SKILL.md` (the engine gives its full text to the module agent when it dispatches it; fixed inputs, outputs, gates and how to run it standalone), plus the module's own code, references and tests. `modules/train/` is the train module: the `trsi` command line, the train command `train` and `reference/`; see its `README.md` |
| `modules/common/` | Standard-library components the modules share, not a module: `features` (a row's state as numbers for baselines and data generation, the task's features adapter) |
| `modules/_template/SKILL.md` | The template of a module skill |
| `docs/design.md` | Top-level design |
| `docs/interfaces/` | Interface descriptions of the artifact kinds: overview, task definition, data, models, delivery, evaluation and plan, experiment records, module inputs and outputs, and the flow engine (`engine.md`: actions, the dispatch and decision records in STATE, decision points, runners, exit codes, locks) |
| `docs/superpowers/plans/` | Implementation plans |
| `tests/` | Standard-library unittest tests |

## Install

No pip install is needed, only Python 3.9 or later. To let Claude Code find the skills, symlink the top-level skill and the four module skills into a Claude Code skill directory: `~/.claude/skills/` for use in all projects, or a project's `.claude/skills/` for use in that project only:

```bash
REPO=/path/to/RSI_code_driven_harness   # absolute path of this repository
mkdir -p ~/.claude/skills
ln -sfn "$REPO/skills/rsi-orchestrator" ~/.claude/skills/rsi-orchestrator
for m in data train deliver judge; do
  ln -sfn "$REPO/modules/$m" ~/.claude/skills/rsi-$m
done
```

Use symlinks, not copies: the operator skill resolves the symlinks of its own SKILL.md to the real path and walks up to the directory that holds `rsi/cli.py`, which it takes as the repository root `<repo root>`; it then calls commands as `PYTHONPATH=<repo root> python3 -m rsi ...` (it asks the user when it finds none). The train command is `<repo root>/modules/train/train` by default, and the task definition's `resources.train_command` (an absolute path) can replace it; it is called with `PYTHONPATH=<repo root>` in the environment. Module agents are dispatched by the engine, which gives them the full text of `modules/<module>/SKILL.md` directly and does not rely on these links; the links let module owners run a module standalone in their own sessions. `modules/_template/` is the template for writing a module skill and needs no link.

## Getting started

**In Claude Code**: once the skills are installed, just state your request, or call `/rsi-orchestrator` explicitly. The operator skill drafts the task definition (`task.json` and `TASK.md`) with you; after you confirm it, it runs `rsi init` and then `rsi run` in the background. When the run stops at a question for you, it relays the question and the options to you, records your own words with `rsi answer`, and runs `rsi run` again. It does not decide the flow.

**From the command line** (at the repository root; `python3 -m rsi --help` lists all commands):

```bash
python3 -m rsi validate task <task dir>          # the task directory holds task.json and TASK.md
python3 -m rsi init <ws> --task <task dir>        # create the workspace, write and open the progress pages
python3 -m rsi run <ws>                            # default --runner claude: each module is a headless Claude Code session
# Exit code 10: waiting for your answer. The question and the options are in the printed line, and in "What the run waits for" on the progress page
python3 -m rsi answer <ws> <option> --by <your name> --quote "<your own words>"
python3 -m rsi run <ws>                            # go on until the end (exit code 0)
```

`rsi run` runs for a long time (it waits while module agents work); you may interrupt it at any time, and running it again picks up where it left off. `rsi brief <ws> <module>` prints the brief a module would get now (built by code from the workspace state, no dispatch record needed), for checking or for dispatching by hand: `rsi run --runner manual` only writes the brief and waits until `handback.json` appears in the output directory. Note that module agents get all permissions by default; see the known limitations below.

Once `rsi init` has created the workspace, it writes the progress pages and opens the overview `<ws>/dashboard.html` in the default browser: at the top are the questions waiting for your answer in Claude (shown only when there are some), then the standing workflow diagram (the five stages, with `③ Compare (off)` when the task has no `compare` section, plus the top-level check and stop & deliver; the current step is highlighted and has one more line of module progress, e.g. "configs 3/3"; ③, once done, has one more line with the round's strongest baseline and the candidate's delta over it on the valset, e.g. "vs gbdt Δ+0.031") and three cards: current best (plus the best candidate of this round on the valset), how far from the stop, and what the run waits for; further down come "What is running now" (each open dispatch: which launch, check-ins, the completion marker, and the module's `progress.json`: summary, facts, trial table and update time, marked when stale), "Agent judgement" (the notes and questions of the latest 6 hand-backs), "GPU" (the task's `resources.gpu_ids` or all GPUs: GPU memory, utilisation, processes of this user and of other users, from `<ws>/work/gpus.json`, which `rsi run` takes while it waits) and "Recent events" (the latest 10 entries of the event log). `<ws>/dashboard/` holds three secondary pages: `rounds.html` (rounds and artifacts: one block per round, the newest round expanded), `events.html` (the event log, newest first) and `report.html` (the run report: `REPORT.md` shown as Markdown). The top bar shows the run status and the run's total time (like the run report, counted from the first `rsi run`, or from `rsi init` when there has been no run; while running it is counted live by the browser's clock); each round's title shows that round's elapsed time. The status is "● running" only while an `rsi run` is running (holds `<ws>/work/run.lock`); otherwise it is "waiting for rsi run" or what the run waits for (the user's answer, a long job, a manual hand-back, stopped). The four pages reload every 5 seconds; after that, a successful `rsi init`, `register`, `promote`, `close-round`, `approve`, `next`, `stop` or `report` rewrites them all (a failed write only prints `warning: dashboard not updated: <reason>` on stderr and does not affect the command). Set the environment variable `RSI_NO_BROWSER=1`, or pass `--no-open` to `rsi init` or `rsi dashboard`, to not open the browser; without a graphical display, open the file yourself.

## Commands

| Command | What it does |
|---|---|
| `rsi init` | Creates a workspace and writes the task definition |
| `rsi validate` | Validates an artifact directory against its kind's schema |
| `rsi register` | Registers an artifact in the workspace registry and prints its registered id; for a delivery with decision-flip rows the task allows, it appends `(decision mismatches: <rows>)` to the line; the artifact directory is copied into the workspace, while an evalset, a testset or a corpus is moved in (after registration the source directory no longer exists, and the producing module keeps no labels); for a trainset, candidate or search, the module gate's result follows the id in brackets. Each round registers at most `stop.max_attempts_per_round` (default 3) searches: one search counts as one attempt, and its trial candidates do not count separately. The metrics, baselines, train gate, deltas and intervals that candidates and evaluation reports state are recomputed by the definitions of `rsi score`, and a mismatch is refused; metric and baseline names `rsi` does not know are not checked, and `(not verified: <names>)` is appended to the line |
| `rsi status` | First line `now: <status line>`: what the run is doing now, the same line `rsi run` prints on stderr; then the workspace state and the current round, the stop settings in effect (defaults marked `(default)`), the attempts of this round (`attempts: <used> of <limit>`, with a hint to run `rsi close-round` when they are used up and no candidate passed the train gate), then a `best delivery on current evalset:` line (the current best version's delivery on the current evalset; after an evalset refresh without one it says to deliver again first), with ③ Compare on a `compare: <comparison id> (vs <strongest baseline> Δ<primary metric> <delta on the valset>)` line for the current round (report only), and last the artifacts registered this round with their gate results (deliveries with `predictions_test` are marked as milestones) |
| `rsi promote` | Decides this round's evaluation by the task definition's promotion rule: prints `promote V<n>: reason` or `keep: reason`; once per round |
| `rsi approve` | Records a user approval (`--by`, `--quote` the user's own words; `--ref <plan id>` when approving a plan); while the run waits for this approval, it also counts as the answer (clears the waiting question and records a decision) |
| `rsi answer` | Answers the question the run waits for: `rsi answer <ws> <option> [--ref <question id>] --by <name> --quote <user's own words>`; the option must be one the question gives (printed when `rsi run` stops, together with the question id `q-NNNN`; a `--ref` that is not the question waiting now is refused). Approval questions: `approve` records the approval, `stop` stops the run, `revise` (plan) sends the user's words back to rsi-judge to change the plan; when a hand-back's candidates would go over the compute budget, that hand-back is not registered for now and `over_budget` is asked first; after `approve` the next `rsi run` registers the same hand-back (without training again), this round goes on to its decision and then the run stops on the budget; decision-point questions: `resume`, `new_session`, `close_round`, `stop` (plus `train` and `data` when the train gate failed, and `skip` for a compare dispatch: close it as skipped and go on without ③), where `close_round`, `stop` and `skip` take effect at once and the others are carried out by the next `rsi run`; milestone: `yes` / `no`; questions a module asks in its hand-back are answered `answered`: none of the artifacts of this hand-back is registered before the answer, the next `rsi run` sends the user's words back to the same session of the module that asked, and only its new hand-back is registered. The answer is recorded in STATE's `decisions` and `<ws>/work/run.jsonl`; prints `answered <question>: <option> (by <name>; <what happens next>)` |
| `rsi next` | Refuses first when this round has a registered evaluation without a promotion decision (asks for `rsi promote`); then checks the stop conditions, and when one holds prints `stop: reason` and stops; otherwise opens the next round and prints `round <n>: <module>`. Refuses when this round has no decision, pointing to `rsi promote` or `rsi close-round` |
| `rsi check-stop` | Only prints `stop: reason` or `continue: reason`; changes no state |
| `rsi close-round` | Closes this round when it has no candidate to evaluate (e.g. the attempts are used up and still no candidate passed the train gate): `--reason` is required; recorded as keep (`keep`), counted in the completed rounds and the rounds in a row without promotion; the next plan's `evaluation_id` is null; the round's dispatches that failed and whose long jobs may still run are closed first, and their long jobs are terminated after the save (see "Stopping mid-run" in docs/interfaces/engine.md) |
| `rsi stop` | Records a stop when the user asks to end the run (`--by`, `--quote` the user's own words); allowed at any time, refused once stopped; prints `stop: user requested: <words>` |
| `rsi report` | Prints the run report (Markdown), or writes it into a file with `--out <file>`; changes no state, but every call rewrites the progress pages. When no version was promoted it opens with "No releasable version was produced"; when the run has not stopped it is a progress report; it includes the total time (from the first `rsi run`, or from `rsi init` when there has been no run, also stating when the workspace was created) and each round's elapsed time; with ③ Compare on, a `### ③ Compare (round n)` subsection per round (the candidate against its strongest baseline on the valset and the evalset, and the comparison's table) and, in the milestone section, a line per baseline on the sealed testset |
| `rsi dashboard` | Rewrites the progress pages: the overview `<ws>/dashboard.html` and `rounds.html`, `events.html`, `report.html` under `<ws>/dashboard/` (it reads `rsi`'s own state and registry, plus `REPORT.md`, the `## Questions for the user` section of `work/notes.md`, `work/run.jsonl`, the process id in `work/run.lock` and the directory listing of `work/`), prints the overview's absolute path and opens it in the browser; `--no-open` only rewrites |
| `rsi brief` | Prints a module's brief (Markdown): input paths, output directory, budget, commands and the hand-back format, all built by code from the workspace state; `--purpose` gives the dispatch's purpose. When the engine dispatches, it writes the same brief as `brief.md` and `brief.json` into the output directory |
| `rsi run` | The engine runs the main flow by itself: it dispatches module agents by `next_action` of `rsi/flow.py` (`--runner claude` by default, a headless Claude Code session; `mock` uses the mock scripts in `--mock-dir`; `manual` only writes the brief and waits for `handback.json` to appear in the output directory), registers hand-backs and makes decisions by the code's defaults, until it must ask the user, wait for a long job, wait for a manual hand-back, the run ends or `--max-steps` (default 200) is used up, and prints why it stopped (one line; with `--json`, `{"status": ..., "reason": ...}`). Each action and result is logged in `<ws>/work/run.jsonl`, and the progress pages are rewritten after each step; while it waits for an agent, and while it waits for a long job with check-ins on (`flow.checkin_minutes`), it takes a GPU snapshot (`<ws>/work/gpus.json`) and rewrites the pages every `flow.page_refresh_seconds` (default 60) seconds; without check-ins, an `rsi run` waiting for a long job stops with exit code 11, and the pages are updated only by the next `rsi` command (or `rsi dashboard`). When the state changes, and every `flow.status_minutes` (default 5) minutes while it waits, it prints a status line on stderr, e.g. `20:23 round 1 ② Train & tune d-0001 · training 3 trials (GPUs 0, 4, 6) · configs 3/3 · GPU hours 1.3/8 · incumbent c4339e55d6 (lr 5e-6) · next check-in 20:46` (stdout is unchanged; with `--json` it still holds only the one JSON object). You may interrupt it at any time; running it again picks up where it left off, without dispatching or registering twice. Exit codes below |
| `rsi score` | Needs no workspace: `--task <task.json> --labels <label rows> --predictions <predictions>` computes the known metrics the task lists by the definitions fixed in code; add `--train <trainset rows.jsonl>` for the baselines, and `--compare <other predictions>` (with `--clusters <inputs.jsonl>`) for the primary metric's delta and its paired cluster bootstrap interval, and `--baselines-on evalset|testset --baseline <dir>`… (with `--clusters`) for ③ Compare's baselines as an evaluation reports them (`baselines_eval` or `baselines_test`, the whole object); prints one JSON object. Modules use it for the numbers they report, and `rsi register` recomputes them by the same definitions at registration and refuses a mismatch (see "Metric definitions" in docs/interfaces/task.md) |

Promotion, the stop and whether the next round may start are all decided by these commands by rule (the rules are in `rsi/rules.py`); the orchestrating agent does not decide them itself. Exit codes: 0 on success (when `rsi register` registered the artifact but something needs a person's attention, e.g. the source directory of an evalset or testset could not be deleted, the id is printed on stdout as usual and a note starting with `warning:` goes to stderr; the exit code is still 0); when a precondition does not hold the command refuses with exit code 1, the error says which step is missing, and the state is unchanged; when the command line is wrong (a missing argument, a missing required option such as `--reason`, `--by` or `--quote`, an unknown subcommand or a value out of its choices) argparse prints the usage and exits with code 2. The exit code of `rsi run` says where it stopped: 0 the run has ended (stopped, with the report written), 10 waiting for the user's answer, 11 waiting for a long job's completion marker, 12 waiting for a manual hand-back, 13 `--max-steps` used up; 1 when refused or on an error (with `--json` the status is `done`, `waiting_user`, `waiting_long_job`, `waiting_manual`, `max_steps` or `error`).

Once the run has stopped (`rsi next` hit a stop condition, or `rsi stop`), only `rsi approve <ws> delete` (cleanup) and `rsi register <ws> record <dir>` (last experiment records) are allowed; other approvals and registrations, `rsi promote`, `rsi close-round`, `rsi next` and `rsi stop` are all refused. The read-only `rsi status`, `rsi check-stop` and `rsi report`, which changes no state (it rewrites the progress pages), work at any time.

## Known limitations

Module agents have all permissions (`claude -p --dangerously-skip-permissions`) and run on the same machine as the workspace, so technically they can read the labels of the evalset and testset in the workspace. The isolation relies on the brief giving only the paths needed, on the module skills' conventions, and on the read-deny rules the `claude` runner passes automatically from the brief (`--disallowedTools`: the whole directory of a registered artifact the brief does not give, the other files of a dataset of which only some files are given, the output directories of data's other dispatches, all denied for both Read and Edit; decision agents have a list too; the list is recorded in the dispatch record's `denied`); the metric recomputation at registration guarantees that the reported numbers are real, but cannot stop "peeking at the labels to tune the model". When stronger isolation is needed later, a runner that runs modules in a container or as a separate user can be added. The deny rules are only a guard against the agent's own tools (Read, Edit and commands such as `cat` that name a file) reading by mistake, not isolation: the child processes it starts (`open()` in `python`, `grep -r`, `find`, `cp`, and so on) are not restricted; a workspace path containing `( ) * ? [` is refused at launch; the `mock`, `manual` and `code` runners only record the list and do not enforce it.

Raw data and labelled copies: after the data module's first round, the raw data (the task's `data.sources`) is kept out only by the operator's `chmod 000` once the corpus is registered (the line in "Running" of the orchestrator skill that waits in the background for the corpus to be registered and then locks it); without the lock, later agents can still read it through child processes. Labelled copies elsewhere on the same machine (copies of the raw data, download directories, workspaces of earlier runs) are not on the read-deny list and are not locked. A data dispatch for an approved evalset refresh gets the whole corpus, which holds the labels of the sealed testset and of earlier evalsets: it uses the corpus only through `dset refresh` and does not open it itself, which rests on convention.

Module agents also carry your Claude Code configuration: `claude -p` reads your user settings (hooks, permissions, MCP servers) as usual, the project settings and `CLAUDE.md` of every directory above the output directory, and your memory. The task definition's `runner.claude.setting_sources` (some of `user`, `project`, `local`, passed to `--setting-sources`) can limit which settings files are read; `CLAUDE.md` and memory are not affected by it (see "Runners" in docs/interfaces/engine.md).

## Walkthrough

`tests/test_e2e.py` uses the fictional binary task `spam-check` and synthetic artifacts generated by `tests/fixtures.py` to go, through real `python -m rsi` commands, through two rounds, a milestone release and a run in which three rounds bring no promotion, without running any real module. The numbers in the synthetic candidates and evaluation reports are computed by `rsi/metrics.py` from synthetic predictions (for example by making a few rows wrong), and registration recomputes and checks them as usual:

```bash
python3 -m unittest discover -s tests -p test_e2e.py -v
```

The flow it shows:

1. Round 1: `init`, then the testset, evalset, valset and trainset are registered in turn (their row ids do not overlap), then a candidate, a delivery and an evaluation; `rsi promote` prints `promote V1`; after a plan (entry module `train`) is registered, `rsi next` is refused while it is not approved, and after `rsi approve ... plan` it prints `round 2: train`.
2. Round 2: a new candidate, delivery and evaluation are registered (the primary metric gets worse); `rsi promote` prints `keep`; after a plan is registered and approved, `rsi next` prints `stop:` because the task definition has `stop.patience: 1`, and `rsi status` shows that the run has stopped.
3. Milestone release: once round 1 has promoted V1, `stop.target` is reached and `rsi check-stop` prints `stop:`; after a `use_testset` approval is recorded, a delivery of the V1 candidate on the evalset and testset inputs is registered, and after another approval a milestone evaluation (`uses_testset` true, with `metrics_test`, recommending keep); `rsi promote` refuses it, and `rsi next` prints `stop:`.
4. Three rounds without promotion: the task definition leaves out `patience` (default 3). Each round registers three searches (each with two trial candidates that fail the train gate, and their search); the fourth search is refused (`3 of 3 attempts used`), `rsi status` hints at `rsi close-round`, and `rsi next` is refused and points to `rsi promote` or `rsi close-round`; `rsi close-round` closes the round. The first two rounds register a plan whose `evaluation_id` is null and move on to the next round after it is approved (entry `data`, which registers a new trainset); after the third round is closed, `rsi check-stop` and `rsi next` both print `stop:` (patience 3), and `rsi report --out` writes a failure report that opens with "No releasable version was produced".
5. Three out-of-order cases: `promote` is refused without an evaluation; an evaluation whose recommendation disagrees with the rule's decision is refused at registration; a trainset that overlaps the evalsets is refused at registration.
