# Elliptic++ example: three rounds starting from the data module

Task: decide whether a Bitcoin address (Elliptic++ address-level data) is illicit. The model's input is the address's transaction history up to the current time step (OneJev txhist rows), and its output the probabilities of `yes` (illicit) and `no` (licit). Train & tune uses joey-1's single-GPU full-parameter default recipe, and the run has **three rounds** (`stop.max_rounds` 3) of ① Data → ② Train & tune → ③ Compare → ④ Deliver → ⑤ Judge & decide. The task turns every optional part of the flow on (see "What the task turns on"): ③ Compare with all six baselines, a decision policy fitted for every candidate and baseline, the features adapter with its constraints, and in rounds 2 and 3 data generation (dgen) under a cap on generated rows and a dollar budget for its LLM calls. ③ Compare and dgen run in onejev-harness's python (`resources.onejev.python`), which needs numpy, scikit-learn, xgboost and pyyaml (`modules/common/install_deps.sh` installs them; `install_env.sh` runs it, step 3).

The flow starts at the data module: round 1's data agent reads the raw data (the task's `data.sources`), writes its own preprocessing script that turns it into OneJev rows (the script and all the labelled rows are registered as the `corpus`), sets the split rule from the data (the task sets only each set's row count), and the split tool `dset` cuts out the testset, evalset, valset, the training pool and the trainset. No set is made or registered by hand.

| File | Content |
|---|---|
| `task.template.json` | Task definition template: the raw data directory and the machine-specific values are placeholders `<…>`; the split rule gives only the debug-scale `sizes` |
| `TASK.template.md` | Its version for people, with the same placeholders |
| `features_adapter.py` | The features adapter of the txhist state (the task's `features.adapter`): the generic model view plus per-role sums; only the transaction fields are editable; `repair` recomputes the summary from the transactions and `check` holds the consistency rules (counts, values >= 0, smallest <= largest <= total output) |
| `README.md` | This file |

Test: `python3 -m unittest discover -s tests -p test_examples.py` (at the repository root).

## What the task turns on

Each of these sections is optional in a task; this example writes all of them (their meaning in `docs/interfaces/task.md`):

- `compare` (③ Compare, a report only, never a gate): the baselines `lr`, `gbdt` and `mlp` (CPU, on the features below), `zero_shot` and `few_shot` (joey-1 scored without training, and with 4 labelled trainset examples in its prompt) and `team_recipe` (the team's existing recipe, trained once per trainset; see "The team recipe"). Each round's comparison reports the candidate against each baseline on the valset, the judge reports them on the evalset, and at the milestone they are scored on the testset inputs. A GPU baseline whose estimate does not fit the compute budget left is skipped with the reason.
- `policy`: `{"objective": "f1"}`. Every candidate (and every compare baseline) fits a calibration and a decision threshold on its valset predictions, chosen by F1 and kept only when it does not lower AUPRC; `model.predict` applies it, so deliveries and evaluations carry the policy's decisions.
- `features`: the adapter `features_adapter.py` (how a txhist state becomes numbers, which fields data generation may edit, and the history's consistency rules) and three declarative `constraints` run before it: every transaction number is 0 or more, `steps_ago` and the address counts are whole numbers, and smallest output <= largest output <= total. `dset repair` and every row dgen builds are repaired and checked by them.
- `input.verbatim`: `[]`: a txhist state holds no request text, so nothing is locked against editing.
- `quality_checks.max_synthetic_share`: 0.3: rows generated by dgen (`meta.source` starting with `dgen:`) may be at most 30% of a trainset; `dset` computes the check and a trainset over it fails the quality gate.
- `budget.api_cost` (`"<API_USD_BUDGET>"`) caps the dollars of the LLM calls that generate or review data and paraphrase prompts; `budget.agent_cost` (`"<AGENT_USD_BUDGET>"`) caps the dollars of the agent sessions. The two are separate accounts; reaching either stops the run after the round's decision. `budget.compute_hours` is 8: three rounds of training, ③'s GPU baselines and the data module's pool scoring.
- `stop.max_rounds`: 3. In rounds 2 and 3 the data agent scores the pool with the best version's candidate, reads the diagnosis of its errors, chooses generation recipes (real failures, SMOTE-style interpolation, LLM rows with an independent reviewer) and builds the new trainset with `dgen` and `dset` (`modules/data/SKILL.md`, "Later rounds: trainset").

### The team recipe

`compare.team_recipe` is elephant-1 with `recipes/elephant_lora_1g.yaml` (LoRA on 1 GPU, in `modules/train/recipes/`), no overrides, seed 0: the training skill's documented start for this task, 0.902 mean val AUPRC over seeds 0–2 (`modules/train/reference/lessons.md`). The teammates' pipelines also name a full fine-tune of elephant-1 at learning rate 5e-6; it is not used here, because it runs out of memory on 2×80 GB GPUs and was unstable through ojh (checkpoints jumping between 0.30 and 0.68 AUPRC). Switching to it is this one field, on a machine with GPUs of more than 80 GB:

```json
"team_recipe": {"base": "elephant-1", "recipe": "examples/recipes/elephant_full_fsdp.yaml", "overrides": {"onejev.lr": 5e-6},
                "seed": 0, "max_steps": null}
```

(the recipe path is looked up under `modules/train`, then in the onejev-harness repository, which has it), with `resources.onejev.estimate.elephant-1` raised to that training's GPU hours.

## Raw data

`01_build_data.sh` (in `pipelines/elliptic_elephant/` of the DM-RSI-Framework repository) writes the data to `$DMRSI_DATA/data/onejev/addr_txhist_noul/`: `train.jsonl` (169,438 rows, 7,859 illicit), `val.jsonl` (24,225 rows, 1,838 illicit), `test.jsonl` (97,756 rows, 5,023 illicit); `val_sub4000.jsonl` is not used. The three files hold 291,419 rows in all, 14,720 of them illicit, which are the numbers of the task's `data.rows.expect`. Each row looks like:

```
{"id": "addr_30_<address>", "split": "val",
 "state": {"entity": "Bitcoin address transaction history", "summary": {...}, "transactions": [...]},
 "question": {"type": "noul", "instructions": "Is this Bitcoin address involved in illicit activity?"},
 "target": {"yes": 0.0, "no": 1.0},
 "meta": {"state_id": "<address>", "step": 30, "y": 0, "post43": false, "seen_in_train": false}}
```

The task definition's `data` section tells the data agent what is wanted; how to do it is up to the agent:

- `sources`: this directory (placeholder `<ROWS_DIR>`). Only round 1's dispatch that produces the sets reads it; later dispatches and the other modules are denied it, and once the corpus is registered you make it unreadable (step 5).
- `rows`: `about` is the row convention: one row per (address, time step), state as it is, `question` the task's question (yes = illicit, no = licit), `meta.state_id` the address, the time step written into `meta.extra.step`, and the upstream `meta`'s `y`, `post43`, `seen_in_train` not written out. `expect` is the count of all rows and of each label's rows, checked one by one when the corpus is registered and refused on a mismatch: the labels go through the script the agent writes, and they pass only when the counts match.
- `split`: only the debug-scale `sizes` (trainset 1000, valset 500, evalset 500, testset 1000). Which field to split by, how to cut the ranges, stratification, unit and seed are set by the agent from the data, with the reasons written into its record; the filled rule is recorded as a new version of the task definition, `task-0002` (only `data.split` added), without asking you and without approval. The same address may appear in several sets; `dset` only reports the counts (it separates them only when the agent sets `unit: state_id`). To scale up, change only `sizes`, with a new task directory and a new workspace.

`data.sources` may also point to Elliptic++'s raw CSVs (those `01_build_data.sh` downloads), from which the agent's script builds the txhist rows itself; then `rows.about` must say how the txhist rows are built (e.g. as `build_addr_txhist.py`, which `01_build_data.sh` calls, does), and `rows.expect` is checked the same way.

## Steps

Below, `<REPO_ROOT>` is the deployed framework repository, `<W>` this run's working directory, and `<ROWS_DIR>` the directory holding the three files above (absolute paths).

### 1. Prepare the raw data

On the machine that runs it, put the three files into `<ROWS_DIR>` (run `01_build_data.sh` on this machine, or copy them from elsewhere and check their sha256), and check the row counts:

```bash
wc -l <ROWS_DIR>/train.jsonl <ROWS_DIR>/val.jsonl <ROWS_DIR>/test.jsonl   # 169438, 24225, 97756
```

Module agents run as the same user as you. Other labelled copies on this machine (`01_build_data.sh`'s intermediate results `$DMRSI_DATA/data/processed/elliptic_pp_addr_sqo/`, the raw CSVs `$DMRSI_DATA/data/raw/elliptic_pp/`, an `addr_txhist_noul` elsewhere) are not on the read-deny list: `chmod 000` them before `rsi run`, or keep them off this machine. `<ROWS_DIR>` itself is locked only in step 5.

### 2. Task definition

```bash
mkdir -p <W>/task
cp <REPO_ROOT>/examples/elliptic_onejev/task.template.json <W>/task/task.json
cp <REPO_ROOT>/examples/elliptic_onejev/TASK.template.md <W>/task/TASK.md
```

Replace the placeholders in both files with one command, so the two files stay the same:

| Placeholder | What to fill in |
|---|---|
| `<ROWS_DIR>` | Absolute path of the raw data directory (the `path` of `data.sources`) |
| `<REPO_ROOT>` | Absolute path of the framework repository (`resources.train_command` becomes `<REPO_ROOT>/modules/train/train` from it) |
| `<OJH_PYTHON>` | onejev-harness's `.venv/bin/python` |
| `<OJH_BIN>` | onejev-harness's `.venv/bin/ojh` |
| `<OJH_MACHINE>` | ojh's `machine.yaml` |
| `<OJH_ENV_FILE>` | ojh's environment file (`ojh-env.sh`) |
| `<CLAUDE_BIN>` | Absolute path of `claude` (the first item of `runner.claude.command`) |
| `"<GPU_IDS>"` (with the quotes) | The list of GPU numbers train & tune may use, e.g. `[0, 1]`; leave out GPUs that `nvidia-smi --query-gpu=index,memory.used --format=csv` shows someone using |
| `"<JOEY1_GPU_HOURS>"` (with the quotes) | The GPU hours one joey-1 training is estimated to take (a number). There is no smoke training (there is no trainset before the run starts); for a 1000-row trainset start with 0.3 (0.18 measured on an A100, loosened a little) |
| `"<API_USD_BUDGET>"` (with the quotes) | The dollars the data module's LLM calls may spend in the whole run (a number; `budget.api_cost`): generation, its review and prompt paraphrases, e.g. 20. A recipe stops short when it is reached |
| `"<AGENT_USD_BUDGET>"` (with the quotes) | The dollars the agent sessions may spend in the whole run (a number, or `null` for no cap; `budget.agent_cost`), e.g. 100 for three rounds |
| `"<ELEPHANT1_GPU_HOURS>"` (with the quotes) | The GPU hours one training of ③ Compare's team recipe (elephant-1 LoRA, 1 GPU) is estimated to take, with packing and scoring (a number). ③ skips the baseline (and says why in the comparison's `skipped`) when the compute budget left is less. Not measured through the harness yet: one epoch of the full 169k-row trainset takes 7–7.5 h on an A100 (3–4 h on an H200), so for a 1000-row trainset start with 0.5 (loading, merging and scoring the 9B model take most of it) |

```bash
cd <W>/task
sed -i -e 's#<ROWS_DIR>#/abs/path/addr_txhist_noul#g' -e 's#<REPO_ROOT>#/abs/path/rsi#g' \
       -e 's#<OJH_PYTHON>#/abs/path/.venv/bin/python#g' -e 's#<OJH_BIN>#/abs/path/.venv/bin/ojh#g' \
       -e 's#<OJH_MACHINE>#/abs/path/machine.yaml#g' -e 's#<OJH_ENV_FILE>#/abs/path/ojh-env.sh#g' \
       -e 's#<CLAUDE_BIN>#/abs/path/claude#g' -e 's#"<GPU_IDS>"#[0, 1]#g' -e 's#"<JOEY1_GPU_HOURS>"#0.3#g' \
       -e 's#"<ELEPHANT1_GPU_HOURS>"#0.5#g' -e 's#"<API_USD_BUDGET>"#20#g' -e 's#"<AGENT_USD_BUDGET>"#100#g' \
       task.json TASK.md
grep -n '<[A-Z][A-Z0-9_]*>' task.json TASK.md    # should print nothing
PYTHONPATH=<REPO_ROOT> python3 -m rsi validate task <W>/task
```

After `rsi init` the task definition is fixed, and changing `resources.onejev.estimate` or `delivery.*` later needs a `task_change` approval and a new version, so settle them here: `reproduction_tolerance` uses the template's 1e-4 (fully reproduced across GPUs on an A100), and `max_decision_mismatch_rate` uses 0.001. The split rule the data agent fills in is the only new version that needs no approval.

### 3. Create the workspace

```bash
export PYTHONPATH=<REPO_ROOT> RSI_NO_BROWSER=1
bash <REPO_ROOT>/modules/train/install_env.sh --ojh <ojh repo> --machine <OJH_MACHINE> --env-file <OJH_ENV_FILE>   # installs and checks the libraries training needs; go on only with exit code 0
bash <REPO_ROOT>/modules/common/install_deps.sh --python <OJH_PYTHON> --check   # numpy, scikit-learn, xgboost, pyyaml for ③ Compare and dgen: every line ok
python3 -m rsi init <W>/ws --task <W>/task --no-open
printf '# Working notes\n\nrepo root: %s\n' <REPO_ROOT> > <W>/ws/work/notes.md
python3 -m rsi status <W>/ws
<CLAUDE_BIN> -p 'reply ok' --output-format json      # ok in the result: module agents can start
```

`<ojh repo>` is `<OJH_PYTHON>` without the trailing `/.venv/bin/python`; `install_env.sh` is safe to rerun (it changes nothing on a machine that is ready); usage in "Installing the environment" of `modules/train/README.md`. It also runs `modules/common/install_deps.sh --python <OJH_PYTHON>`, which installs the libraries ③ Compare and dgen import into onejev-harness's venv; the `--check` line above only confirms them (run `install_deps.sh --python <OJH_PYTHON>` without `--check` to install them alone).

Register no set by hand: the four sets, the corpus and the pool are all produced and registered by the data dispatch in the run. Keep `<ROWS_DIR>` readable; round 1's data dispatch reads it.

### 4. Run in tmux

As in "Running" of `skills/rsi-orchestrator/SKILL.md`: one output file per run, its name set in the shell that starts it and written into `<W>/ws/work/notes.md`.

```bash
cat > <W>/run.sh <<'EOF'
#!/bin/bash
# One `rsi run` on workspace $1 with the framework at $2; result in $3.json, status lines in $3.err, exit code in $3.exit.
PYTHONPATH=$2 python3 -m rsi run "$1" --max-steps 1000 --json > "$3.json" 2> "$3.err"; echo $? > "$3.exit"
EOF
out=<W>/ws/work/run-out-$(date +%Y%m%d-%H%M%S)-$$; echo "run output: $out" >> <W>/ws/work/notes.md
tmux new-session -d -s rsi-elliptic "bash <W>/run.sh <W>/ws <REPO_ROOT> $out"
until [ -e $out.exit ]; do sleep 300; done; cat $out.exit $out.json
```

Handle the exit code by the skill's table, then run once more (run the last three lines again, with a new `out`):

- `0`: the run has ended; the report is in `<W>/ws/REPORT.md`.
- `10`: waiting for the user's answer (plan, milestone and so on). Relay the question and the options to the user and record the answer with `rsi answer <W>/ws <option> --ref <q-NNNN> --by <name> --quote "<user's own words>"`. The split rule is never asked about; after V1 the milestone is.
- `11`: waiting for a long job (training, a large preprocessing). The reason holds the completion marker; run again after `until [ -e <marker> ]; do sleep 300; done`.
- `13`: `--max-steps` used up (1000 here; each check-in takes about 3 steps, so the default 200 is not enough); not a fault: run the same command again (the last three lines).
- `1`: refused or an error; handle it as the error message says.

Watch the progress with `python3 -m rsi status <W>/ws` (the first line `now:` is what it is doing now), `tail -n 3 $out.err` for the latest status lines of `rsi run`, or open `<W>/ws/dashboard.html` (rewritten every `flow.page_refresh_seconds` seconds while waiting, 60 by default).

### 5. Lock the raw data once the corpus is registered

Once the hand-back of round 1's data dispatch is registered (`corpus-0001` is in the registry), later dispatches no longer read the raw data, and the run goes on as usual. The read-deny list only holds back the agents' own file tools, so make it unreadable now:

```bash
until grep -q '"kind": "corpus"' <W>/ws/registry.jsonl; do sleep 60; done
chmod 000 <ROWS_DIR>
head -c1 <ROWS_DIR>/test.jsonl                       # should be Permission denied
```

(The first line may wait in the background as soon as the run is started in step 4.) To rerun the preprocessing or redo the data later, `chmod 755 <ROWS_DIR>` first, and lock it again when done.

The data agent's LLM calls (`claude -p`, the same `runner.claude.command`) run with no tools, in an empty directory, with no MCP servers and only project settings; they see only their prompts.

### 6. Check round 1's data

- Registration order: `task-0002`, `corpus-0001`, `testset-0001`, `evalset-0001`, `valset-0001`, `pool-0001`, `trainset-0001` (the trainset's quality gate is passed in `python3 -m rsi status <W>/ws`), then the data dispatch's record; STATE's `approvals` has no `task_change`.
- `task-0002` differs from `task-0001` only in `version` and `data.split`; `data.split` is complete, with `sizes` 1000, 500, 500, 1000. The four sets have these row counts too.
- The corpus's manifest has `rows`, `script`, `split_report`; the trainset's `quality_report.json` has `split.shared_state_ids` (how many addresses the sets share); the data dispatch's record gives the rule and why it splits so (`hypothesis`).
- Rerun audit (optional): `chmod 755 <ROWS_DIR>` for a while, copy the registered script in `<W>/ws/artifacts/corpus-0001/` into a new directory `<W>/audit/`, run the corpus manifest's `command` there, and the new `rows.jsonl`'s sha256 should equal `files.rows` of the `corpus-0001` line in `<W>/ws/registry.jsonl`; when done, `chmod 000 <ROWS_DIR>` at once and delete `<W>/audit` (it holds labelled rows).

### 7. Check rounds 2 and 3

- Each round has a `comparison` (`python3 -m rsi status <W>/ws` and the dashboard show ③ Compare's baselines against the candidate) and its evaluation reports the baselines on the evalset; every candidate has `policy.json`.
- The trainsets of rounds 2 and 3: their `changes` name each dgen arm (`arms/<sha12>/verified.jsonl`), their `quality.checks` hold `max_synthetic_share`, and the data dispatch's record names each recipe, its kept and short rows and its spend.
- The spend: `python3 -m rsi status <W>/ws` shows `GPU hours`, `data LLM $` and `agent $` apart, against `compute_hours`, `api_cost` and `agent_cost`.

Only in an acceptance run, once the results are saved and the run has stopped, delete the model weights outside the run, and only these paths: under each trial's ojh run directory (the `run_dir` of `<W>/ws/work/round-*/train/trsi/trials/<trial>.json`), `runs/*/ckpt-step*` and `runs/*/final`, plus `<W>/ws/artifacts/candidate-*/model/` and `<W>/ws/work/round-*/train/cand-*/model/`; and the team recipe's (③ Compare's `team_recipe` baseline): `<W>/ws/artifacts/baseline-*/model/`, in each compare output directory `<W>/ws/work/round-*/compare*/` the `bl-team_recipe/model/` and `gpu-*/team_recipe/team/cand/model/`, and under its ojh run directory (the `run_dir` of `gpu-*/team_recipe/team/cand.trsi/trsi/trials/<trial>.json`) `runs/*/ckpt-step*` and `runs/*/final`. A real run does not delete this way: the current best version's model and `<W>/ws/artifacts/` are never deleted, and any other deletion by hand first records a `delete` approval (see "Approval points" in `skills/rsi-orchestrator/SKILL.md`); unusable checkpoints are deleted by `trsi collect` automatically.
